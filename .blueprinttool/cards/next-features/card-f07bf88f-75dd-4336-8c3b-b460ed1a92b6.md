## A. Current Ledger Model

1. **Cards.** Cards are stored in `ledger.cards[]`. A card owns identity, title, type, status, geometry, labels, and a `comment` object.
2. **Card body.** Long card markdown is usually stored outside JSON through `card.comment.contentFile`, for example `.blueprinttool/cards/<ledger>/<card-id>.md`.
3. **Inline fallback.** Card content can also appear as `comment.what`, `comment.body`, or `comment.description` in older or hydrated paths.
4. **Zones.** Zones are stored in `ledger.annotations[]`. Regular zones are annotations where `variant !== "group"` and `color` is a string.
5. **Zone title.** The visible zone name is `annotation.label`, with fallbacks in some export code to `title`, `name`, then `id`.
6. **Zone membership.** A card is attributed to a zone by geometry overlap, not by a durable `zoneId` field on the card.

---

## B. Current Zone Attribution

1. **Frontend helper.** `resolveLedgerCardZone(card, annotations)` computes card-zone membership from rectangle overlap.
2. **Best overlap wins.** If a card overlaps several regular zones, the zone with the largest overlap area owns the card for attribution.
3. **Groups are excluded.** `variant: "group"` annotations are not treated as zones for card context.
4. **CLI export parity.** The markdown export path also groups cards under zones by geometric overlap.
5. **Implication.** A watcher context command can reproduce current behavior without adding a new card-zone relationship field.

---

## C. Proposed Summary Fields

1. **Zone summary field.** Add `summary?: string` to regular zone annotations.
2. **Card summary field.** Add `summary?: string` to card records.
3. **Length.** Summaries should be one to three sentences maximum.
4. **Purpose.** Summaries describe what the zone or card is generally about, not the full implementation detail.
5. **Persistence.** Summaries live in the ledger JSON beside zone/card metadata so `ledger-cli` can read and update them without opening every Markdown sidecar.

```ts
interface LedgerZoneAnnotation {
  id: string;
  variant: "zone";
  label: string;
  color: string;
  x: number;
  y: number;
  width: number;
  height: number;

  /**
   * One to three sentence summary of the zone's purpose and contents.
   */
  summary?: string;
}

interface LedgerCard {
  id: string;
  title: string;
  cardType?: string;
  status?: string;
  x: number;
  y: number;
  w: number;
  h: number;
  comment?: {
    contentFile?: string;
    what?: string;
  };

  /**
   * One to three sentence summary of the card's durable content.
   */
  summary?: string;
}
```

---

## D. Summary Content Rules

1. **Zone summary.** State the zone's topic, the workflow or problem it contains, and the kind of cards inside it.
2. **Card summary.** State the card's objective, the main contract or decision, and any important implementation boundary.
3. **Avoid restating title only.** A summary must add useful context beyond the visible label or card title.
4. **Avoid transient status.** Do not use summaries for temporary progress notes such as `working`, `blocked today`, or `needs reply`.
5. **Use plain language.** Summaries should be readable in watcher prompts without requiring the full card body.

---

## E. Ledger CLI Updates

1. **Set card summary.** Add a command path to write `card.summary` by card id.
2. **Set zone summary.** Add a command path to write `annotation.summary` by zone id.
3. **Watcher context.** The lean watcher payload should include the target zone summary and sibling card summaries.
4. **Fallback behavior.** If a summary is missing, the CLI can fall back to the title plus a short excerpt from the card body or zone card list.
5. **Tests.** Cover card summary writes, zone summary writes, missing summaries, geometry-based zone attribution, and watcher payload context.
