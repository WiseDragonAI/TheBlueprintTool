## A. Required Outcome

1. **Single durable selection:** The Codex model and reasoning effort shown in the card run widget and the active card thread must represent the same configuration, stored on the card as `codexRunModel` and `codexRunEffort`.
2. **Immediate persistence:** Changing either selector must persist the complete model-and-effort pair immediately, without waiting for `Continue`, `New session`, `Shift+X`, voice orchestration, or another Codex command.
3. **Bidirectional synchronization:** After a successful change in either surface, the widget and thread selectors must both display the persisted values.
4. **New default:** A card with no persisted Codex selection must initialize to model `gpt-5.6-sol` and effort `high`.
5. **Command inheritance:** Every later Codex entry point for that card must use the persisted selection, including thread launch, `Shift+X`, `Continue`, `New session`, and voice-triggered orchestration.

---

## B. Current Problem

1. **Widget-only browser state:** `frontend/src/runtime/codex/component/render-card-skill-run-widget.ts` renders `codexRunModel` and `codexRunEffort`, but its selectors have no change handler. A selection remains only in the current `<select>` element until a continuation command starts.
2. **Thread-only runtime state:** `frontend/src/runtime/thread/effect/render-thread-panel.ts` writes selector changes only to `state.threadCodexPreferencesByThreadId` and the launch button dataset.
3. **Independent defaults:** The thread surface currently initializes to `gpt-5.5` and `xhigh` instead of reading the active card fields.
4. **Missing durable mutation:** `frontend/src/runtime/persistence/effect/persist-state.ts` does not serialize `threadCodexPreferencesByThreadId`, and the thread selector does not issue a backend request.
5. **Command-boundary persistence:** `frontend/src/runtime/codex/effect/poll-card-skill-run.ts` sends the widget values only when `Continue` or `New session` is selected. `backend/src/business/codex/controller/continue-card-skill-run-controller.ts` then persists the resolved values.
6. **Observed result:** The widget, thread launcher, and card can each hold different values. Refreshing or remounting restores the last command's values rather than the latest selector change.

---

## C. Existing Behavior To Preserve

1. **Durable card fields:** Initial Codex launches and continuation commands already write `codexRunModel` and `codexRunEffort` to the card.
2. **Existing inheritance:** `Shift+X` and voice orchestration already read those card fields when present.
3. **Widget hydration:** The card run widget already renders persisted card values when it mounts.
4. **Allowed values:** Model and effort validation must continue to use `codexModelOptions` and `codexEffortOptions` from `shared/schemas/codex-pipeline-types.ts`.

---

## D. Implementation Contract

1. **Canonical state:** Use the active card's `codexRunModel` and `codexRunEffort` as the only durable preference source. Remove `threadCodexPreferencesByThreadId` as an independent Codex preference authority.
2. **Ledger mutation:** Extend the existing `patch-card` contract in `frontend/src/runtime/ledger/effect/commit-active-ledger-mutation.ts` and `backend/src/business/ledger/helper/apply-ledger-mutation.ts` to validate and persist `codexRunModel` and `codexRunEffort` together.
3. **Selector writes:** Bind both widget selectors and both thread selectors to that mutation. Each change must submit the newly selected value together with the current value of its paired selector.
4. **Reconciliation:** On mutation success, reconcile from the returned ledger and update both mounted surfaces from the returned card fields.
5. **Failure behavior:** On mutation failure, restore both surfaces to the last durable card values and expose the existing ledger-mutation failure telemetry.
6. **Initialization:** When the active card lacks either field, both surfaces must display `gpt-5.6-sol` and `high`; the first selector change or Codex launch must persist the complete pair.
7. **Backend fallback:** Change the built-in fallback in `backend/src/business/codex/helper/resolve-codex-command.ts` from `gpt-5.5` / `xhigh` to `gpt-5.6-sol` / `high` while preserving explicit valid configuration precedence.

---

## E. Acceptance Criteria

1. **Widget persistence:** Change the widget selection, remount the widget, and verify the new pair remains selected without starting a Codex command.
2. **Thread persistence:** Change the thread selection, close and reopen the thread panel, and verify the new pair remains selected without starting a Codex command.
3. **Widget-to-thread sync:** Change either widget selector and verify the open thread controls update to the persisted pair.
4. **Thread-to-widget sync:** Change either thread selector and verify the mounted widget controls update to the persisted pair.
5. **Refresh persistence:** Change a selector, reload the ledger, and verify both surfaces restore the persisted pair.
6. **Shortcut inheritance:** Change a selector without launching Codex, invoke `Shift+X`, and verify the command uses the persisted pair.
7. **Continuation inheritance:** Verify both `Continue` and `New session` use the persisted pair.
8. **Default coverage:** For a card without persisted fields and without an explicit valid runtime configuration, verify both surfaces and the launched backend command use `gpt-5.6-sol` and `high`.
9. **Failure coverage:** Reject a selector mutation, verify both controls return to the durable pair, and verify no unsaved selection is used by the next command.
10. **Regression coverage:** Preserve the existing tests for persisted widget initialization, initial launch persistence, continuation persistence, `Shift+X` inheritance, and voice orchestration inheritance.
