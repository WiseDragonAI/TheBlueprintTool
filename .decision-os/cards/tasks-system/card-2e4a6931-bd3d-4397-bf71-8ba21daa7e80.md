2. **No scroll.** Each view uses a fixed square board and hides overflow so it stays within one stakeholder review screen.

4. **Navigation.** Each view includes a small numbered view switcher so the operator can move across the five report surfaces.

## E. Research Objective

1. **Purpose.** Define a reusable Product Owner goal-analysis report format that records facts related to a requested goal.
2. **Required output.** The report must include a compact summary, one context section with product, technical, and UX subsections, technical, platform, and UX constraints, evidence, risks, unknowns, and source registers.
3. **Research base.** The research reviewed more than 30 sources covering PRDs, requirements quality, Product Owner responsibility, Product Manager decision work, product discovery, UX research, opportunity mapping, stakeholder communication, risk framing, and AI-assisted product workflows.
4. **Skill base.** The research reviewed 15 public PM-oriented `SKILL.md` files from `pmprompt/skills`, including PRD writing, JTBD, opportunity solution trees, feedback synthesis, prioritization, stakeholder updates, OKRs, Working Backwards, Shape Up, shaping, experiments, competitive analysis, design sprints, breadboarding, and thinking in bets.
5. **Report stance.** The report is an analysis document: it records goal-linked facts, context, constraints, evidence strength, risks, and unknowns.

---

## F. Research Synthesis

1. **Facts first.** Open with `goal`, `top facts`, `context summary`, `constraint summary`, `evidence strength`, `main unknowns`, and `scope boundary`.
2. **Need before solution.** Capture `target user`, `job`, `trigger`, `pain`, `frequency`, `current workaround`, `desired outcome`, and `evidence strength` before naming a feature.
3. **Unified context section.** Put `product context`, `technical context`, and `UX context` under one `Context` section so the current state is read as a single analysis block.
4. **Technical reality.** Record `platform`, `architecture`, `APIs`, `data model`, `state owner`, `integration points`, `permissions`, `performance limits`, `security constraints`, and `known debt`.
5. **UX reality.** Record `current journey`, `screens`, `states`, `user roles`, `entry points`, `handoffs`, `cognitive load`, `missing feedback`, `accessibility constraints`, and `copy risks`.
6. **Constraint register.** Split constraints into `technical`, `platform`, `UX`, `data`, `legal`, `operational`, `timeline`, and `dependency` rows, each with `impact` and `workaround`.
7. **Risk register.** Score `value`, `usability`, `feasibility`, `viability`, `delivery`, `adoption`, and `alignment` risks with owner, evidence, mitigation, and validation step.
8. **Possibility inventory.** Record possible solution shapes as `observed option`, `source`, `expected outcome`, `cost signal`, `dependency`, `risk`, and `evidence gap`.
9. **Requirement quality.** Record observable behavior, acceptance criteria, edge cases, non-goals, analytics events, accessibility requirements, and release checks without selecting a path.
10. **Validation plan.** Define `success metric`, `guardrail metric`, `instrumentation`, `research or experiment method`, `validation threshold`, and `review date`.
11. **Open questions.** End with `unknown`, `why it matters`, `evidence needed`, `owner`, and `blocking level`.

## I. Analysis Quality Bar

1. **Summary.** The first screen states the requested goal, top facts, context summary, constraint summary, evidence strength, and unknowns.
2. **Evidence-backed.** Every major claim should be tied to evidence, discovery, technical inspection, UX observation, or an explicit assumption.
3. **Constraint-aware.** The report must show the current platform and UX reality before proposing a solution.
4. **Risk-honest.** The report should expose uncertainty rather than hiding it inside confident requirement language.
5. **Execution-useful.** The report should be easy to transform into specs, implementation slices, acceptance criteria, and validation tasks once a path is chosen outside the analysis report.
