## A. Product Context

1. **Current product state.** `decision-os` is a local browser canvas, a TypeScript backend ledger server, and workspace-local `.decision-os` data. The active repo workspace is dogfooding the product through `.decision-os/state.json`, which currently exposes `specs`, `data`, `performances`, and `tasks-system`.
2. **Surface area.** The current surface includes route-addressed ledger tabs, a ledgers overview canvas, cards, zones, groups, relationships, canvas pan/zoom, selection, clipboard copy/paste, card resize, card Markdown, card fields, image carousels, HTML card assets, right-side threads, voice notes, transcription retry, live refresh, the `ledger-cli`, and the `generator-cli`.
3. **Active workflows.** Operators inspect and edit ledgers on the canvas, create or move cards/zones/groups, review specs and performance evidence, paste images/files into threads, record voice notes, ask agents to treat unanswered notes, maintain card and zone summaries, and use report/mockup cards for PO analysis work.
4. **Actors and roles.** The **operator** owns decisions, notes, approvals, and workspace intent. The **agent** reads threads, changes repo or ledger state, and replies in `# AGENT` sections. The **watcher** concept monitors unanswered notes. The **backend server** owns filesystem hydration and mutation. The **frontend runtime** owns transient interaction state. The **ledger CLI** is the maintenance and agent queue surface. The **OpenAI transcription provider** is optional and configured per workspace.
5. **Adoption state.** Adoption evidence is internal and active: the repo workspace contains `289` spec cards, `40` data-model cards, `9` performance cards, and `27` task-system cards. No external customer analytics, production usage metrics, or support evidence were found in this research pass.
6. **Active specs.** `specs.json` covers boot, navigation, canvas rendering, zones, selection, cards, threads, voice, refresh, groups, relationships, media, CLI tooling, generator tooling, and implementation architecture. `tasks-system.json` is the current Next Features surface and contains work around watcher loops, summary maintenance, task queues, report UX, and goal-object UX.
7. **Known friction.** Threads currently carry too many responsibilities: conversation history, work queue, lock, status model, progress log, and recovery surface. Performance notes show drag and pan risk around browser frame production, layout-position writes, zone label reads, overlay rerenders, rich card surfaces, and relationship routing. Report UX notes show unresolved product boundaries for whether reports should be a card view, ledger type, goal cockpit tab, or embedded reader.

## B. Technical Context

1. **Platform.** The backend is a Node/TypeScript HTTP server run through `tsx`; the frontend is a frameworkless TypeScript browser runtime served without a bundler; tests use Node's native test runner and Playwright-style browser specs; card syntax highlighting uses `highlight.js`.
2. **Architecture.** The repo is split into `backend`, `frontend`, `ledger-cli`, `generator-cli`, `shared`, `tests`, `operations`, and workspace `.decision-os` files. The launcher `bin/decision-os-server.mjs` derives `DECISION_OS_FRONTEND_ROOT` and `TSX_TSCONFIG_PATH`, then starts `backend/src/server.ts` from the target workspace cwd.
3. **Services and APIs.** The backend serves app routes `/`, `/ledgers`, and `/<ledgerId>`, state and ledger APIs under `/decision-os/state`, `/decision-os/<tab>`, `/decision-os/ledgers`, and `/decision-os/ledgers-canvas`, live refresh at `/api/ledger-content-events`, uploads at `/api/thread-image-upload`, `/api/thread-file-upload`, and `/api/voice-upload`, and transcription at `/api/transcribe` plus `/api/transcribe/retry`.
4. **Data model.** `.decision-os/state.json` owns the ledger registry. Each ledger JSON owns `cards`, `annotations`, `relationships`, `viewport`, `threadFiles`, and related structured fields. Card bodies are durable Markdown files referenced by `comment.contentFile`. Thread histories are durable Markdown files under `.decision-os/threads/...`. Image layout persists through `imageSizes` in card JSON.
5. **State ownership.** The filesystem is the canonical state store. The backend hydrates card Markdown and thread files into ledger responses, strips hydrated notes before writing, validates mutations, writes ledger JSON, writes card content files, and writes thread content files. The frontend owns transient state such as `activeTab`, `viewport`, `selection`, active tool, card tab state, open thread, draft text, scroll position, clipboard, and voice capture state.
6. **Integrations.** Workspace settings in `.decision-os/.settings.json` can configure transcription with `OPENAI_API_KEY` or `openaiApiKey` and `gpt-4o-mini-transcribe`. The server also integrates with local filesystem watchers, local static asset serving, browser media capture, and the local CLI tools.
7. **Permissions and security.** The default server host is `127.0.0.1`. Workspace asset serving is constrained to the active `.decision-os` root and allowed image, thread-file, or active-card asset paths. API keys and uploaded voice files are intended to stay local and uncommitted.
8. **Observability.** The frontend and generator surfaces emit local telemetry facts. Performance evidence is stored in `operations/canvas-performance-study-2026-05-29.md` and `.decision-os/cards/performances/...`. Verification surfaces include `npm run typecheck:frontend`, `npm run typecheck:backend`, `npm run test:browser`, `npm run test:front-back`, and live verification scripts under `tools/live-verify`.
9. **Deployment.** Current deployment is local workspace execution, not hosted SaaS. Operator-facing sessions should run the detached launcher from the target workspace cwd, redirect logs under `/tmp`, and verify the HTTP route before reporting a URL.

## C. UX Context

1. **Journeys.** A user opens a ledger route, reviews the canvas, selects or creates cards/zones/groups, edits geometry or content, opens the thread panel with `A`, writes or records notes, receives agent replies, reviews card media or report mockups, and can use CLI workflows for maintenance or agent treatment.
2. **Screens and regions.** The main UX includes the tab registry, full-canvas ledger surface, toolbox, canvas controls, card detail layer, card overview layer, card description and fields tabs, relationship overlays, zone/group labels, deletion confirmation modals, right-side thread inspector, terminal-style composer, voice dock, telemetry/status copy, and the hidden ledgers overview.
3. **States.** Important UI states include route mode, active ledger, viewport, zoom/detail mode, active tool, selection, grouped selection, clipboard, open card tab, low-detail versus hydrated card rendering, thread open/closed, draft restored, scroll restored, optimistic note pending, voice recording, transcription uploading, transcription failed, retry available, modal open, and external refresh received.
4. **Entry points.** Primary entry points are `/`, `/ledgers`, `/<ledgerId>`, the tab registry, card/zone/group controls, the toolbox, keyboard shortcuts, thread buttons, thread upload/paste controls, voice controls, `ledger-cli`, and server launch commands.
5. **Handoffs.** Operator notes hand off to agents through thread files. Agent replies hand back through `# AGENT` notes and durable card edits. Voice capture hands off from browser media capture to upload, transcription, optimistic note update, and retry. External filesystem edits hand off to the client through server-sent refresh events. Card Markdown hands off to backend hydration and frontend Markdown/media rendering.
6. **Information architecture.** The current workspace separates **Specs** for behavior contracts, **Data** for base classes and relationships, **Performances** for measured canvas performance evidence, and **Tasks System** for Next Features. At the object level, cards, zones, groups, relationships, and threads are the main navigable units.
7. **Accessibility.** The implemented keyboard contract includes `A`, `X`, `Esc`, `Del`, `Ctrl+C`, `Ctrl+V`, and `Ctrl+D`. Deletion confirmations support keyboard handling. Some rendered controls expose labels or titles. Full WCAG coverage, screen-reader behavior, focus order, and color-contrast audits were not verified in this pass.
8. **Copy and language.** Agent replies must be English. Thread copy uses `# OPERATOR` and `# AGENT` sections. Durable card content should stay concrete, implementation-ready, and traceable to source files or ledgers. The in-app Keys panel should remain the operator-facing keyboard contract.
9. **Interaction constraints.** Expensive card detail is hydrated only when detail is visible. Pan/zoom and drag must preserve responsive frame production. Delete actions require confirmation. Thread and voice tooling must not steal editing keystrokes. Media dimensions must persist independent of canvas zoom. HTML embeds must stay under allowed card asset paths.

## D. Context Boundaries

1. **In scope.** This context covers the current `decision-os` repo, the active repo-local `.decision-os` workspace, existing code, existing docs, active ledgers, task cards, performance notes, thread model, CLI model, and local runtime behavior visible from source inspection.
2. **Out of scope.** This context does not cover a hosted deployment, multi-tenant permissions, billing, external customer research, market positioning, production analytics, support tickets, or non-repo workspaces.
3. **Unverified areas.** This pass did not start a browser session, run automated tests, inspect live decision-os workspace state, validate a real transcription API key, measure current browser performance, audit accessibility with assistive technology, or confirm external operator adoption beyond repo evidence.
4. **Source gaps.** There is no discovered analytics baseline, customer interview set, support ticket sample, hosted deployment runbook, centralized telemetry sink, or current CI result attached to this note. Some README examples still describe older `tabs` wording while current state uses a `ledgers` registry.
5. **Cross-team dependencies.** The only confirmed dependency outside the local repo is optional OpenAI transcription configuration. Product-boundary decisions for reports, work queues, watcher agents, and goal objects remain operator-owned unless a future card assigns explicit ownership.
6. **Evidence sources.** Primary evidence came from `README.md`, `.decision-os/state.json`, `.decision-os/specs.json`, `.decision-os/data.json`, `.decision-os/performances.json`, `.decision-os/tasks-system.json`, `backend/src/business/server/helper/create-http-server.ts`, `backend/src/business/ledger/helper/apply-ledger-mutation.ts`, `frontend/src/runtime/boot/controller/boot-surface.ts`, `frontend/src/runtime/ledger/effect/render-ledger-surface.ts`, `frontend/src/runtime/input/controller/handle-keyboard.ts`, `frontend/src/runtime/thread/effect/render-thread-panel.ts`, `.decision-os/cards/tasks-system/card-agent-autonomy-work-queue.md`, `.decision-os/cards/tasks-system/card-2395850a-c528-4689-a138-73a30b684602.md`, and `.decision-os/cards/performances/...`.
