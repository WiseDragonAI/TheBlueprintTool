## Goal-Linked Spec Analysis Prompt

```text
You are creating a goal-linked spec analysis from an existing context report.

Inputs:

- Base goal: <paste the exact goal statement, source, scope, and any known non-goals>
- Context report: <paste the full context report or provide the document/card/file reference to read>
- Spec sources: <paste or reference existing specs, requirements, tickets, cards, docs, or code evidence if available>

Task:

Create a neutral analysis report that correlates the context report with the base goal and identifies the specs, requirements, constraints, risks, gaps, and unknowns that matter to that goal.

Use the context report as factual input. Do not treat it as complete truth when evidence is missing. Do not invent facts, spec IDs, owners, metrics, or implementation details. If something is not supported by the provided material, mark it as unknown or inferred.

Analysis Procedure:

1. Extract the base goal.
   - Capture the goal statement, source, intended user or actor, target workflow, scope, and explicit non-goals.
   - If the goal is ambiguous, preserve the ambiguity as an open question instead of resolving it by assumption.

2. Parse the context report.
   - Extract product context, technical context, UX context, context boundaries, active specs, known friction, constraints, and evidence sources.
   - Keep source names, IDs, file paths, dates, and quoted labels exactly where available.

3. Build a context-to-goal map.
   - For each relevant context fact, state how it affects the goal.
   - Classify relevance as direct, enabling, blocking, constraining, adjacent, or unrelated.
   - Classify fact strength as observed, measured, reported, inferred, or assumed.

4. Build a specs and requirements inventory.
   - List every existing spec or requirement candidate mentioned by the context report or supplied spec sources.
   - Preserve existing spec IDs and titles. If no ID exists, mark the ID as `unidentified`; do not invent one.
   - For each spec, identify the linked surface, current behavior, user behavior, system behavior, acceptance signal, status if known, and relevance to the goal.

5. Derive goal-linked requirement candidates.
   - Convert only supported context facts into requirement candidates.
   - Link each candidate to a goal need, context fact, source, affected user, affected system, and acceptance signal.
   - Mark whether the candidate is an existing requirement, an implied requirement, a missing requirement, or a non-goal.

6. Identify contradictions, gaps, and unresolved decisions.
   - Record any conflict between the goal, context report, existing specs, implementation facts, UX facts, constraints, or source boundaries.
   - For each gap, state why it matters to the goal and what evidence would resolve it.

7. Identify risks and constraints.
   - Separate technical, platform, UX, data, security, operational, timeline, dependency, and product-boundary constraints.
   - For each risk, state category, likelihood if supported, impact, evidence, current control, and missing proof.

8. Produce traceability.
   - Every material claim must trace to the base goal, a context fact, a spec source, an evidence source, a constraint, a risk, or an open question.
   - Do not include generic process commentary that does not add a concrete requirement, constraint, decision, evidence, risk, or action.

Output Format:

## A. Goal Snapshot

- Goal:
- Source:
- Scope:
- Non-goals:
- Affected users or actors:
- Affected workflows:
- Ambiguities:

## B. Context-to-Goal Map

| Context fact | Context section | Source | Relevance | Strength | Goal impact |
| --- | --- | --- | --- | --- | --- |

## C. Specs And Requirements Inventory

| Spec ID | Title or requirement | Source | Linked surface | Current behavior | Status | Goal relevance | Confidence |
| --- | --- | --- | --- | --- | --- | --- | --- |

## D. Goal-Linked Requirement Candidates

| Requirement candidate | Requirement type | Source fact | Affected user | Affected system | Acceptance signal | Goal link |
| --- | --- | --- | --- | --- | --- | --- |

Requirement type must be one of: existing requirement, implied requirement, missing requirement, non-goal.

## E. Constraints

| Constraint | Type | Source | Impact on goal | Verification status | Owner if known |
| --- | --- | --- | --- | --- | --- |

## F. Risks And Unknowns

| Item | Type | Why it matters | Evidence | Missing proof | Blocking level |
| --- | --- | --- | --- | --- | --- |

Type must be one of: risk, unknown, contradiction, source gap, unresolved decision.

Blocking level must be one of: blocks understanding, blocks scoping, blocks implementation, non-blocking.

## G. Evidence Register

| Source | Claim supported | Evidence type | Strength | Limitation |
| --- | --- | --- | --- | --- |

## H. Open Questions

| Question | Category | Why it matters | Evidence needed | Source to inspect |
| --- | --- | --- | --- | --- |

Quality Rules:

- Keep the report neutral and product-agnostic.
- Do not recommend a selected path, implementation plan, approval gate, or roadmap unless explicitly requested.
- Do not restate the whole context report; extract only facts that affect the base goal or specs.
- Preserve uncertainty instead of smoothing it over.
- Prefer concrete source-linked claims over broad summaries.
- Use `unknown`, `unverified`, or `not provided` when evidence is absent.
- Write concise English.
```
