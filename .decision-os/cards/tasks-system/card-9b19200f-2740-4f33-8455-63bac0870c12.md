## A. Source Boundary

1. **Allowed source set.** This card uses the `Decision OS Context`, `PO Goal Analysis Format`, and `Goal Object UX` cards, the operator thread on this card, source files, tests, and `README.md`. It does not use `.decision-os/specs.json` or any spec-ledger card body as a source for linked specs.
2. **Spec-id rule.** A `spec id` is preserved only when the id appears in code or test evidence, for example `frontend/index.html` `data-spec` attributes or executable test headers. If the codebase shows behavior but no durable id, the `spec id` is recorded as `unknown`.
3. **Base goal.** Create an interface inside Decision OS that lets a human operator read and inspect PO goal-analysis report results for the current goal. The current goal is recursive: build the process and interface for seeing how a goal fits into the existing product.
4. **Context report fact.** Decision OS is a local browser canvas, TypeScript backend ledger server, and workspace-local `.decision-os` state. The current Next Features surface is `tasks-system`, shown as `Tasks System` in `.decision-os/state.json` and as `Ledger: Next Features` in `.decision-os/ledgers-canvas.json`.
5. **Goal-object fact.** The existing `Goal Object UX` card defines `Goal`, `Reports`, `Specs`, and `Tasks` as separate objects, and its global goal cockpit direction exposes `Specs`, `Reports`, and `Tasks` as tabs.

## B. Goal Spec Link

1. **Goal need.** The operator needs a readable goal-analysis interface that shows how the active goal relates to product context, technical context, UX context, linked specs, missing specs, and gaps.
2. **Affected product area.** The affected surface is the Decision OS ledger canvas, especially the `tasks-system` Next Features ledger, card Markdown rendering, thread inspector, report-card assets, and potential goal-cockpit navigation.
3. **Affected workflow.** The workflow is: operator creates or states a goal, agent/context report extracts facts, Decision OS presents linked specs and reports, operator inspects rows or opens threads, and later work can derive tasks or report ledgers from that factual state.
4. **Affected actor or role.** The primary actor is the **operator**. Supporting roles are the **agent** that extracts and writes durable state, the **frontend runtime** that renders the interface, and the **backend server** that hydrates and persists ledger files.
5. **Relevant context fact.** The context card states that report UX boundaries are unresolved: reports could be a card view, ledger type, goal cockpit tab, or embedded reader. The codebase already supports route-addressed ledgers, Markdown cards, image carousels, HTML embeds, threads, and voice notes.
6. **Current behavior.** Report facts can be stored in card Markdown, report mockups can be shown through adjacent images or active-ledger HTML embeds, threads attach operator feedback to cards, and ledgers load through `/decision-os/state` and `/decision-os/<tab>`.
7. **Expected behavior.** The goal-linked spec surface should show the base goal, goal/spec link fields, linked specs with source and relevance, missing specs, and gaps. It should remain facts-only: no recommendation, selected path, approval gate, or implementation plan.
8. **Acceptance signal.** The `Goal Linked Specs` card contains source-traceable entries for `goal need`, `affected product area`, `affected workflow`, `actor`, `context fact`, `current behavior`, `expected behavior`, `acceptance signal`, linked specs, missing specs, and spec gaps, with no direct spec-ledger extraction.

## D. Missing Specs

1. **Goal object data spec.** **Implied requirement:** a goal needs durable identity, current statement, linked surfaces, and generated objects. **Missing acceptance signal:** no code-defined `Goal` object type or route was found. **Missing data spec:** `shared/schemas/core-types.ts` has `Card`, `Thread`, and `CanvasLedger`, but no `Goal`.
2. **Goal/spec link schema.** **Implied requirement:** persist `goal need`, `affected product area`, `workflow`, `actor`, `context fact`, `current behavior`, `expected behavior`, and `acceptance signal`. **Missing technical spec:** no `SpecLink` schema, mutation action, or renderer was found in source.
3. **Spec row review UX.** **Implied requirement:** each goal-linked spec row can expose approve, rephrase, reject, and thread actions. **Missing UX spec:** the code supports generic threads and voice, but no spec-row component, row-level thread target, or row review state exists.
4. **Report container boundary.** **Implied requirement:** report results need a durable readable surface. **Missing product-boundary spec:** the source evidence does not settle whether reports are cards, ledgers, goal-cockpit tabs, embedded readers, or a combination.
5. **Report ledger navigation.** **Implied requirement:** report cards can open report ledgers and zooming out can return to the global goal view. **Missing technical spec:** current code has ledgers-canvas zoom behavior and route state, but no report-ledger return contract tied to a goal object.
6. **Task flow representation.** **Implied requirement:** tasks can be list-first, grouped into flows, and optionally opened as a graph. **Missing data spec:** no task-flow object, system-prompt link, or formatted-output object was found in the current shared schema.
7. **Source policy enforcement.** **Implied requirement:** some research passes must extract specs only from a context card and codebase, not from a spec ledger. **Missing operational spec:** no CLI or runtime source-filter contract was found for enforcing this policy.
8. **Measurement and validation.** **Implied requirement:** acceptance for "visualize correctly" needs evidence. **Missing acceptance signal:** no analytics, usability observation, screen-reader audit, or live browser verification is attached to this card.

## E. Spec Gaps

1. **Contradiction.** Durable card formatting prefers numbered lists, but `parse-ledger-card-markdown.ts` only parses unordered `-` or `*` list syntax as a list block. Numbered lines render as paragraphs in the current card Markdown renderer.
2. **Unknown.** The codebase does not show a first-class `Goal`, `Report`, `SpecLink`, or `TaskFlow` object in `shared/schemas/core-types.ts`; this may be intentionally pending because the object model is still being designed.
3. **Unverified fact.** The context card states workspace counts and active adoption evidence, but this card did not run a live browser session or analytics check. Treat those counts as context-card evidence, not external usage proof.
4. **Source gap.** `frontend/index.html` contains many `data-spec` ids without titles; executable tests provide titles for many but not all ids. Rows above use test titles where available and mark unsupported titles as `unknown`.
5. **Ownership gap.** The context card says product-boundary decisions for reports, work queues, watcher agents, and goal objects remain operator-owned unless a future card assigns explicit ownership.
6. **Product-boundary decision.** The report surface is still unresolved between card view, ledger type, goal cockpit tab, and embedded reader. The current code supports all adjacent primitives but does not choose one.
7. **Technical constraint.** HTML embeds must live under `.decision-os/cards/<active-ledger>/assets/` and end in `.html`; `render-ledger-card-html-embeds.ts` rejects other locations.
8. **UX constraint.** Card detail rendering is expensive and hydrated only for visible cards. A long goal-analysis report must remain usable when the canvas is in low-detail or overview mode.
9. **Data constraint.** Current thread target kinds are `card`, `zone`, `group`, and `canvas`; there is no confirmed section-level or spec-row-level thread target.
10. **Dependency constraint.** Voice rephrase behavior depends on browser capture and optional OpenAI transcription configuration; the context card marks transcription as workspace-local and optional.
