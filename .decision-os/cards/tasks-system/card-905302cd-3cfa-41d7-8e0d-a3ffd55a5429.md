## A. Object List

- **Logs:** execution evidence used to replay, debug, and audit a session. The useful information is the ordered chain of tool calls, outputs, errors, retries, and proof artifacts.
- **Goal:** the one-sentence outcome that starts the system. The useful information is what durable surface the goal should create next: ledger, task queue, report, question gate, or artifact set.
- **Tasks:** schedulable sub-work derived from the goal. The useful information is status, owner, lease expiry, blocker, dependency, and next runnable action.
- **Work:** concrete changed state. The useful information is what files, diffs, generated assets, and mockups changed during execution.
- **Mockups:** reviewable visual artifacts. The useful information is the source file, capture state, screenshot output, and which UX state the operator is reviewing.
- **Analyses:** uncertainty-reduction artifacts. The useful information is the question, hypothesis, evidence, test, confidence, and decision impact.
- **Learning:** reusable lessons from the session. The useful information is what should be kept, avoided, promoted into instructions, or reused in the next run.
- **Questions:** structured operator gates. The useful information is the exact decision, available choices, rationale, linked task, and optional free-text constraint.
- **Proposals:** agent-authored correction options. The useful information is the problem, recommended approach, alternatives, expected impact, risk, and approval action.
- **Reports:** completion packets. The useful information is what changed, what passed, what failed, residual risk, evidence links, and the next action.
- **Specs:** implementation contracts. The useful information is object contracts, state transitions, runtime routes, acceptance checks, and the bridge into Master Ledger execution.

## B. Object UX Mockups

1. **Source HTML:** `.decision-os/ui-mockups/goal-object-ux-mockups.html` contains all object mockups in one file.
2. **Source CSS:** `.decision-os/ui-mockups/goal-object-ux-mockups.css` contains the extracted base styling, with five global goal shape variants in `.decision-os/ui-mockups/goal-object-ux-style-01.css` through `.decision-os/ui-mockups/goal-object-ux-style-05.css`.
3. **Visual language:** the mockups use decision-os dark canvas styling, terminal panels, card/zones, cyan/orange status accents, compact operator controls, and a UI-designer polish pass for cleaner hierarchy, alignment, spacing, and surface treatment.
4. **Different UX per object:** each object gets a purpose-shaped surface instead of a repeated section layout: logs use a trace console, goal uses an object map, tasks use a queue board, work uses a diff viewer, mockups use a capture gallery, analyses use an evidence matrix, learning uses a promotion path, questions use an operator gate, proposals use a comparison view, reports use an outcome digest, and specs use a contract editor.
5. **Capture model:** each object is rendered as a separate `1120 x 720` screenshot from that single HTML source.
6. **Global goal cockpit:** the final screen uses the current goal as the page title and exposes `Specs`, `Reports`, and `Tasks` as tabs. The `Specs` tab shows a searchable/filterable spec list where each row is one sentence; clicking the row opens its thread, while compact square icon actions handle approve and reject. The `Reports` tab shows expandable analysis-result reports with a report-ledger side action. The `Tasks` tab shows task flows as lists first, with graph mode as a secondary action.
7. **Card rendering:** the images below are intentionally adjacent so decision-os renders them as a carousel.

## C. Product Direction

1. **Goal creation should produce durable objects.** Creating a goal should not only start a chat; it should create the right working surface, such as a ledger, task queue, report, or artifact set.
2. **The operator needs object navigation.** The UX should let the operator move from the goal to logs, tasks, work, analyses, learnings, questions, proposals, reports, specs, and mockups without searching through conversation history.
3. **Questions are operator gates.** They should be structured objects, not loose notes, so the operator can answer, dismiss, or add free-text constraints.
4. **Work and reports should close the loop.** The final state should show what changed, what was verified, what was learned, and what still needs a decision.
