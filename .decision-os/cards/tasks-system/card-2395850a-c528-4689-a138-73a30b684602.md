## A. Format Contract

1. **Purpose.** Produce a PO goal-analysis report that records facts related to the requested goal.
2. **Excluded content.** Do not include a recommendation, selected path, approval request, implementation commitment, or operator gate.
3. **Allowed content.** Include goal facts, product context, technical context, UX context, constraints, evidence, risks, unknowns, source quality, and open questions.
4. **Reader outcome.** A reader can understand the current state and missing facts without being pushed toward a path.

---

## B. Analysis Summary

1. **Goal.** `goal statement`, `goal source`, `goal scope`, `out-of-scope area`.
2. **Top facts.** `fact`, `source`, `evidence strength`, `link to goal`.
3. **Context summary.** `product state`, `technical state`, `UX state`, `active specs`.
4. **Constraint summary.** `constraint`, `type`, `impact`, `owner`, `workaround if known`.
5. **Unknowns.** `unknown`, `why it matters`, `evidence needed`, `blocking level`.
6. **Confidence.** `high confidence facts`, `medium confidence facts`, `low confidence assumptions`.

---

## C. Context

1. **Product context.** `current product state`, `surface area`, `active workflows`, `actors`, `roles`, `adoption state`, `active specs`, `known friction`.
2. **Technical context.** `platform`, `architecture`, `services`, `APIs`, `data model`, `state ownership`, `integrations`, `permissions`, `observability`, `deployment`.
3. **UX context.** `journeys`, `screens`, `states`, `entry points`, `handoffs`, `information architecture`, `accessibility`, `copy`, `interaction constraints`.
4. **Context boundaries.** `in scope`, `out of scope`, `unverified area`, `source gap`, `cross-team dependency`.

---

## D. Goal-Linked Facts

1. **Fact row.** `fact`, `source`, `evidence type`, `date`, `affected user`, `affected system`, `goal relevance`.
2. **Fact strength.** `observed`, `measured`, `reported`, `inferred`, or `assumed`.
3. **Contradiction row.** `conflicting fact`, `source A`, `source B`, `resolution status`, `evidence needed`.
4. **Traceability.** Every fact links back to the goal, the context section, a constraint, a risk, or an open question.

---

## E. Need Understanding

1. **User segment.** `segment`, `role`, `frequency`, `environment`, `permissions`, `workflow position`.
2. **Job.** `situation`, `trigger`, `task`, `desired progress`, `current workaround`.
3. **Pain.** `pain`, `severity`, `frequency`, `affected workflow`, `evidence`, `sample size`.
4. **Outcome.** `user outcome`, `business outcome`, `baseline`, `target signal`, `measurement availability`.

---

## F. Evidence Register

1. **Source row.** `source`, `claim`, `segment`, `date`, `sample size`, `method`, `strength`, `limitations`.
2. **Evidence types.** `customer feedback`, `analytics`, `support ticket`, `interview`, `usability observation`, `technical inspection`, `competitive reference`.
3. **Quality flags.** `freshness`, `representativeness`, `bias risk`, `missing counterexample`, `confidence`.
4. **Usage.** Each evidence row supports a fact, constraint, risk, unknown, or metric in the report.

---

## G. Constraints

1. **Constraint row.** `constraint`, `type`, `source`, `impact`, `severity`, `owner`, `workaround`, `verification status`.
2. **Types.** `technical`, `platform`, `UX`, `data`, `security`, `legal`, `operational`, `timeline`, `dependency`.
3. **Impact fields.** `affected workflow`, `affected component`, `affected user`, `affected metric`, `affected release condition`.
4. **Verification.** Mark every constraint as `verified`, `partially verified`, or `unverified`.

---

## H. Risks And Unknowns

1. **Risk row.** `risk`, `category`, `likelihood`, `impact`, `evidence`, `current control`, `missing proof`, `owner`.
2. **Categories.** `value`, `usability`, `feasibility`, `viability`, `delivery`, `adoption`, `alignment`.
3. **Unknown row.** `unknown`, `why it matters`, `where to inspect`, `evidence needed`, `blocking level`.
4. **Residual uncertainty.** Record what remains unclear after the available research is exhausted.

---

## I. Specs And Requirements Inventory

1. **Existing specs.** `spec id`, `title`, `status`, `owner`, `linked surface`, `relevance to goal`.
2. **Observed requirement.** `requirement`, `source`, `system behavior`, `user behavior`, `acceptance signal`, `edge case`.
3. **Non-goal.** `excluded behavior`, `reason`, `source`, `affected stakeholder`.
4. **Trace.** Link every requirement candidate to a fact, constraint, risk, evidence row, or open question.

## J. Measurement And Validation Facts

1. **Metric row.** `metric`, `baseline`, `current availability`, `instrumentation owner`, `data quality`, `goal relevance`.
2. **Guardrail row.** `guardrail`, `current value`, `risk covered`, `collection method`, `missing instrumentation`.
3. **Research row.** `method`, `participant or sample`, `question`, `observed signal`, `limitation`.
4. **Review row.** `review date`, `data source`, `required evidence`, `unresolved unknowns`.

---

## K. Open Questions

1. **Question row.** `question`, `category`, `owner`, `blocking level`, `evidence needed`, `source to inspect`.
2. **Categories.** `goal`, `user`, `technical`, `UX`, `data`, `constraint`, `metric`, `scope`.
3. **Blocking level.** Use `blocks understanding`, `blocks scoping`, `blocks implementation`, or `non-blocking`.
4. **Resolution trace.** When answered, move the result into the relevant fact, context, constraint, evidence, or risk section.

---

## L. Appendix Contract

1. **Source register.** Preserve article links, documentation links, inspected specs, screenshots, tickets, and research notes.
2. **Skill register.** Preserve the PM skill files used and the exact fields imported from each skill.
3. **Raw evidence.** Preserve excerpts, quotes, analytics screenshots, technical findings, and UX observations.
4. **Versioning.** Record format revisions with timestamp, reason, and changed sections.

## R. Constraints

1. **Asset path constraint.** Live HTML report mockups must be under `.decision-os/cards/tasks-system/assets/po-goal-analysis-format/` to pass the active-ledger embed validator.
2. **Image route constraint.** Markdown carousel screenshots must use allowed image extensions and remain inside the workspace `.decision-os` directory.
3. **Markdown constraint.** Tables, headings, code, images, and HTML embeds are supported; ordered-list rendering is not a first-class markdown block in the current parser.
4. **Canvas constraint.** Report cards must remain useful when low-detail canvas mode hides expensive detail layers.
5. **Thread constraint.** Operator feedback is attached to `thread-card-2395850a-c528-4689-a138-73a30b684602`; the report UI must preserve the thread as part of the review surface.
6. **Report-content constraint.** The report body must stay analysis-only and must not include a selected path, recommendation, approval ask, or implementation commitment.

---

## S. Risks And Unknowns

1. **Unknown report container.** The codebase supports report cards and ledgers; the final product object boundary for report results is not yet proven by implementation.
2. **Unknown section addressing.** The current thread model attaches notes to cards, zones, and groups; it does not yet show section-level report threads.
3. **Risk: long report readability.** Markdown card bodies can become dense; screenshots and HTML readers reduce scanning cost but do not replace structured product state.
4. **Risk: asset drift.** Screenshots can drift from live HTML; storing the source HTML/CSS beside screenshots reduces audit risk.
5. **Risk: parser mismatch.** Durable formatting guidelines prefer numbered lists, while the current renderer recognizes unordered lists; report readability should rely on headings, tables, and screenshots.
