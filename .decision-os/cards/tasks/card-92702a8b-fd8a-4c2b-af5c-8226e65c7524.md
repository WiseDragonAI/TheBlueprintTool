## B. Canonical Ownership Contract

1. `codexThreadRunId` owns the current durable thread session.
2. `codexThreadRunIds` owns ordered thread-session history, and `codexThreadRunOutputFiles[runId]` owns each session's persisted artifact location.
3. `codexActiveRunId` exists only while the card owns a pending or running execution.
4. `codexActiveExecutionId` identifies the exact pending or running attempt and is allocated before admission.
5. The queue item owns scheduling and carries the same `runId` and `executionId`.
6. `runtime.codexSkillRuns[runId]` owns the live process handle and carries the same `executionId`.
7. Pipeline manifests own pipeline structure; every pipeline execution uses the same card execution lease and lifecycle transitions.
8. JSONL and log artifacts own durable execution events and repeat the admitted `executionId`; automatic capacity retry remains the same execution.
9. Frontend summaries, selections, pollers, terminal caches, and Control Room rows are disposable projections of durable ownership.
10. History selection owns displayed content and metrics. Canonical active ownership independently owns the Codex Log activity indicator and `STOP` or `CANCEL` action.
11. A card owns at most one pending or running execution across thread launch, continuation, direct skill launch, and pipeline launch.
12. Settlement clears ownership only when `runId` and `executionId` both match and the process has exited with its output stream closed.

## C. Verified Backend and Lifecycle Findings

1. **The screenshot failure is deterministic:** `codex-pipeline-runner.ts` projects the pipeline run onto the source card, while its runtime record owns the step output card. `cancel-card-skill-run-controller.ts` rejects the source-card request before pipeline cancellation, producing `Active run not found.`
2. **History selection is treated as active ownership:** `card-codex-run-id.ts`, `render-thread-panel.ts`, and `render-thread-codex-log.ts` derive action state from selected Run 2 while Run 3 is live.
3. **Start replaces a recoverable session:** `start-thread-codex-process-controller.ts` supersedes a retained non-live run and allocates another `runId`; `start-thread-codex-process-admission.test.ts` asserts this obsolete behavior.
4. **`codexActiveExecutionId` has no production admission writer:** persisted inventory found 46 cards with `codexActiveRunId`, zero with `codexActiveExecutionId`, and 45 active pointers unmatched to the single running queue item. The current queue payload also lacks `executionId`.
5. **Continuation admission is not idempotent:** `continue-card-skill-run-controller.ts` rejects only `running`; a second pending click adds another queue item and replaces runtime state. Cancellation removes only the first match.
6. **Admission is not atomic:** start and continuation persist partial ownership before queue success; pipeline launch creates step cards and a queued source pointer before manifest persistence.
7. **Recovery is fenced only by `runId`:** `codex-process-queue.ts` can adopt an older execution, clears ownership without execution identity, and reconstructs runtime without it. Pending-only recovery does not rebuild runtime, so cancellation can return 404 after restart.
8. **Adopted process settlement is incorrect:** terminal JSONL is checked before the PID exits. The test named `terminal JSONL wins over a surviving process identity` preserves premature capacity release.
9. **Adopted cancellation is incomplete:** it removes queue and card ownership without `settledAt`; monitoring stops, and later session deletion can return 504.
10. **Dispatch failure strands execution state:** `codex-process-scheduler.ts` drops the failed queue item without settling runtime, clearing exact ownership, writing a finish marker, publishing failure, and advancing later valid work.
11. **Automatic capacity retry changes execution identity:** start allocates `executionId` inside `launch`, then calls `launch` again for retry.
12. **Three execution engines have drifted:** thread start, continuation, and pipeline runner duplicate spawn, stream, marker, runtime, settlement, and retry logic. Pipeline runtime and markers lack the admitted execution ID.

## D. Verified Frontend, Artifact, and Test Findings

1. **Actions are untyped:** cancellation sends only card and run identity; pending work exposes no cancel action; terminal pipeline entries receive thread-session `RESUME` and `Delete session`. A delayed old `STOP` can target a newer same-session execution.
2. **Responsive continuation retains the terminal-cache race:** `responsive/thread.js` omits accepted execution and expected status on both bindings, while desktop supplies them.
3. **Pollers lack a generation fence:** an existing poller emits its cached summary, and later responses are accepted without comparing returned execution to current expected execution.
4. **Server launches cannot establish a fresh consumer:** the turn-started event omits explicit execution and status, and `resumeExternallyStartedCardSkillRun` returns false without an existing poller.
5. **Frontend disposal is incomplete and underscoped:** deletion leaves the exact run poller, responsive close unbinds only the retained thread run, and thread-only cache keys can collide across projects and ledgers.
6. **Historical artifact ownership is missing:** one `codexThreadRunOutputFile` is reused for all history; moved-card deletion derives the current ledger; promotion fabricates a current-ledger path.
7. **Control Room and federation drift:** Control Room compares the runtime execution ID with itself; the local read model omits active execution; the federation replica omits history.
8. **The durable schema is untyped:** `shared/schemas/core-types.ts` has no Codex lifecycle fields, leaving controllers and projections on unchecked `AnyRecord` fields.
9. **Passing tests are insufficient and contradictory:** tests preserve session replacement, premature adopted settlement, cached terminal precedence, and hidden pending cancellation. Cross-boundary coverage is absent.

## E. Remediation Architecture

1. **Typed durable schema:** define session history, per-run artifacts, current session, active run, and active execution in shared card, queue, runtime, event, and projection types.
2. **Single lifecycle kernel:** centralize `admit`, `launch`, `retry`, `cancel`, `settle`, `recover`, and `delete`; thread, continuation, and pipeline code supply prompts and consume results.
3. **Atomic card lease:** serialize card admission, allocate execution identity before writes, persist rollback-safely, and return the existing lease for duplicate admission.
4. **Exact command resolver:** resolve `STOP`, `CANCEL`, continuation, pipeline lifecycle action, and thread-session deletion from typed run kind plus card, run, and execution identity.
5. **Central artifact resolver:** read, continue, promote, move, and delete through `codexThreadRunOutputFiles[runId]`.
6. **One frontend lifecycle coordinator:** share hydration, events, expected-execution generations, polling, selection, and disposal across desktop and responsive surfaces.
7. **One projection DTO:** derive local navigation, federation, Control Room, and server events from the same typed ownership projection.
8. **Startup reconciliation:** compare card lease, queue, runtime, manifest, and terminal artifacts by exact execution identity; retain one valid execution and settle contradicted records.
9. **Data repair:** migrate artifact ownership, clear 45 verified unmatched active pointers, remove three legacy `executionStatus` values, and record deterministic counts.
