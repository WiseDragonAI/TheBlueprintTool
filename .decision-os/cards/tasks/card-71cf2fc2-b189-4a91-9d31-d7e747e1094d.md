## A. Root cause

1. **First incorrect transition:** the responsive thread retained `currentProjectId` locally but did not publish it to shared voice runtime state. Voice upload polling, retry, and restored pending work could therefore derive ownership from the Control Room URL and address the receiving node instead of the task-owning project.
2. **Identity gap:** durable pending uploads and transcription watcher keys did not consistently include `projectId`, allowing equal ledger, thread, and note identities from different projects to collide.
3. **Replica gap:** the federation task-replica cache fingerprint covered Control Room task metadata, not thread resource content. A thread-only mutation could publish a content change while the owner returned its previous cached thread snapshot.

---

## B. Evidence

1. `frontend/src/app/responsive/thread.js` owned the remote project selection while the shared voice request helpers resolved scope from runtime state and the current route.
2. `backend/src/business/federation/helper/federation-task-replica.ts` reused snapshots from `projectSliceFingerprint`; thread Markdown is not part of that projection fingerprint.
3. Focused regressions reproduce project-route loss, cross-project pending-upload identity, and cache reuse after a thread-only change.
