## A. Correct asynchronous launch contract

1. **Shift+X handoff:** the backend accepts and persists the audio, returns HTTP 202 without waiting for transcription, and continues transcription after the card closes.
2. **Active classification:** from HTTP acceptance until Codex launch, the card now persists `executionStatus=transcribing-before-launch` and projects into the Control Room Active column.
3. **Codex queue distinction:** this interval exposes `transcribingBeforeLaunch=true`, `codexQueued=false`, and the label `Transcribing before launch`.
4. **Normal X:** uploads without a Codex launch state and keeps the current card open.
5. **Failure reconciliation:** transcription failure clears only `transcribing-before-launch` and preserves the failed note for retry.

---

## B. Root cause and correction

1. **Verified cause:** the existing pre-launch mechanism reused `executionStatus=pending`; Control Room therefore rendered transcription as ordinary Codex queue waiting.
2. **Correction:** voice acceptance now writes a distinct durable state, and the Control Room projector recognizes that state as Active without assigning a queue position.
3. **Presentation:** the Active row displays `Transcribing before launch` and uses transcription age instead of an invalid execution stopwatch.
4. **Preserved boundary:** Shift+X still navigates only after backend HTTP acceptance; transcription is not part of that acceptance wait.
