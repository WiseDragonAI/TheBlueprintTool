## A. Cause

1. **No prompt tells Codex to put code detail in the master task.** The failure comes from a missing semantic contract. The launch prompt names the ledger commands but never says that the master task is the operator's primary decision surface.
2. **The output fields are ambiguous.** The injected action schema exposes master-task `sections`, subtask `sections`, and a `reply` without defining their audiences. This lets the model place the exhaustive investigation in the master task and the clearer synthesis in the thread.
3. **The workspace rule is correct but insufficiently specific at the write boundary.** `AGENTS.md` says card content must contain verified information needed for the next operator decision, but the runtime does not distinguish master-task content from implementation evidence in subtasks.

---

## B. Verified Origin

1. **Launch instructions:** `backend/src/business/codex/helper/build-thread-codex-prompt.ts` builds the runtime developer prompt. Commit `447c3ea5` minimized it to Decision OS mechanics.
2. **Injected write schema:** `backend/src/business/codex/helper/build-card-launch-context.ts` defines the bare `sections` and `reply` fields. Commit `1acbc98c` introduced this context contract.
3. **Observed result:** card `card-47955f12-4ed3-41dd-aada-7cac51f3e899` contains file paths, symbols, command-filter behavior, and log-pipeline details, while its thread reply contains the shorter explanation visible in the operator screenshot.

---

## C. Required Contract

1. **Master task:** show the verified current state, its meaning for the operator, the material risk, and the next decision.
2. **Subtasks:** hold implementation scope, code locations, tests, and technical acceptance evidence.
3. **Thread reply:** notify the operator of the result and state the next action concisely; it must not be the only readable synthesis.
4. **Next action:** encode this audience boundary in the runtime prompt and protect it with prompt-contract tests.
