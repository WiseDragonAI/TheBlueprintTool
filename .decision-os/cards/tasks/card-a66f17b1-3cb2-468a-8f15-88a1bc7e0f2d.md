## A. Verified Current Chain

1. **Ledger state is persisted as complete mutable JSON documents.** `create-http-server.ts`, `ledger-cli`, Codex controllers, the pipeline runner, project-sync admission, and execution cleanup contain direct aggregate writes.
2. Parallel processes can read different bases and replace the same aggregate because those writers do not submit to one durable issuer.
3. **The current federation replica combines two different workloads.** `federation-task-replica.ts` packages task navigation and lifecycle fields together with hydrated card Markdown and parsed thread notes.
4. `federation-replica-store.ts` persists the combined snapshots and retry queue in `federation-task-replicas-v1.json`; `/api/federation/task-replica`, `content-change`, replica priority frames, and the 15-second refresh timer drive synchronization.
5. Remote Control Room rows and remote card, ledger, and thread reads consume that cached aggregate, so content size and polling health directly affect task-state availability.
6. Git still carries code synchronization and eventual reconciliation of dirty runtime state.

## B. Authoritative Event and Projection State

1. **The immutable event log replaces ledger JSON as the reconstruction authority.** The aggregate becomes a node-local projection that can be deleted and regenerated.
2. Every mutation of replicated fields enters one `local worker` before the projection changes; the worker is the sole issuer for terminal, server, CLI, Codex, pipeline, and synchronization paths.
3. One event represents one atomic mutation: `eventId`, `projectId`, `writerId`, `emittedAt`, `entityType`, `entityId`, `changes[]`, and `checksum`.
4. The worker flushes the event before projection, caller success, publication, or acknowledgement.
5. **Every task reader consumes the worker-owned projection API.** Control Room, canvas, navigation, card metadata, task lifecycle, Codex, pipelines, and diagnostics never parse `.decision-os/tasks.json` as reconstruction authority.
6. `.decision-os/tasks.json` is an atomic compatibility export of the current projection until consumers no longer require the file.

## C. Chronological Reduction

1. The chronological key is `emittedAt`; reducers consume date positions from oldest to newest.
2. A disconnected event received later retains its emission date and is inserted into the affected timeline.
3. Arrival order, writer identity, and transport batch order cannot change the result.
4. Events sharing one date occupy an unordered position: independent fields commute, identical writes collapse, and incompatible writes retain explicit conflict metadata.
5. A later resolution event clears a conflict; tombstones remain dated field events and never delete event history.

## D. Cloudflare Priority State Lane

1. **Reuse the deployed `federation-relay/` Cloudflare Worker as the globally reachable durable federation authority.** Nodes keep authenticated outbound WebSockets and require no inbound public port.
2. Extend the per-federation SQLite `Durable Object` with priority frames for event batches, acknowledgements, bucket summaries, state-snapshot manifests, state-snapshot transfer, missing-event requests, and convergence.
3. The `Durable Object` persists the complete project event set, bounded bucket indexes, and latest verified state snapshot; nodes retain the same state locally for offline operation and reconstruction.
4. Priority state frames bypass content queues and content credit. A saturated or failed content transfer cannot delay event publication, acknowledgement, snapshot bootstrap, or gap repair.
5. If every peer is offline, the relay still retains acknowledged events; any later authenticated node repairs its gap from Cloudflare without requiring temporal overlap with the writer.

## E. State Bootstrap and Reconciliation

1. **A fresh or recovered node bootstraps from a verified state snapshot before requesting the event tail.**
2. Peers advertise compatible snapshot manifests containing `reducerVersion`, projection checksum, covered bucket manifest, size, and content checksum.
3. The receiver requests the newest compatible snapshot, transfers it through the priority state lane, verifies every manifest field and checksum, installs it atomically, then requests uncovered and mismatched event buckets.
4. Events emitted during snapshot transfer and catch-up remain in the outbound event queue and arrive before convergence is declared.
5. If no compatible snapshot exists, the node requests sealed event segments and performs the exceptional genesis rebuild.
6. Periodic bucket reconciliation continues after live convergence and detects missing older events.

---

## F. Snapshot and Checkpoint Lifecycle

1. **A durable state snapshot is a versioned checkpoint derived from one verified event set.** It stores reducer version, creation date, projection checksum, conflict state, and count plus checksum for every covered emission bucket.
2. Snapshot creation follows bounded event-tail size and elapsed tail age; atomic write and checksum verification precede eligibility.
3. Normal startup loads the newest compatible local snapshot and replays only its uncovered tail.
4. A late event inside covered history selects the newest valid snapshot preceding that bucket, invalidates later checkpoints, replays forward, and generates replacements.
5. Corrupt or incompatible snapshots fall back to the preceding valid checkpoint; genesis replay occurs only when no valid checkpoint exists.
6. Sealed historical event segments remain available for reconciliation and Git archival.

---

## G. Asynchronous Content Lane

1. **Content replication is a separate best-effort lane and never gates task-state convergence.** Task metadata becomes available as soon as the state projection converges, with explicit `missing`, `synchronizing`, `available`, and `stale` content states.
2. The owner publishes a lightweight content manifest keyed by project and resource, containing resource type, stable resource key, content hash, byte size, and changed date. Contents never enter task events or state snapshots.
3. A persistent content queue diffs manifests and downloads only missing hashes for card Markdown, thread Markdown, and referenced managed assets. Hash verification and atomic installation precede `available`.
4. Content requests use an independent low-priority queue, credit budget, concurrency cap, and retry schedule. The scheduler yields immediately whenever priority state work exists.
5. A failed or corrupt transfer keeps the last verified local version, records `stale`, and retries independently; it never rolls back task metadata or blocks task acknowledgements.
6. Owner-scoped content mutation and intentional Git commits remain unchanged. The content cache is a replica, not multi-writer content authority.

## H. Legacy Cutover, Git, and Migration

1. **Retire the hydrated task replica as a state path.** Remove `/api/federation/task-replica`, `buildFederationTaskReplica`, `federation-task-replicas-v1.json`, replica snapshot polling, and task-state use of `content-change`, `replica-priority`, and `replica-ack` after event cutover.
2. Replace remote task reads with the local event projection and replace remote content reads with the asynchronous content cache plus owner fallback while online.
3. Remove generated task projections, replay indexes, and content caches from shared-branch authority.
4. Git archives sealed event segments and verified state snapshots through writer-owned refs; content source files retain their intentional Git workflow.
5. Fix task authority at `.decision-os/tasks.json`, migrate misplaced task graphs once, preserve the specification ledger and MasterLedger links, and seed the first event segment and state snapshot.

## K. Implementation Result

1. **Event-first task state is implemented on `main`.** Every task mutation is reduced to immutable field events, persisted before projection or publication, and ordered by `emittedAt` without a sequence field.
2. The node-owned `task-state` store provides append-only segments, bucket manifests, destination-specific acknowledgement state, atomic compatibility projections, versioned verified snapshots, bounded tail replay, and late-event checkpoint invalidation.
3. Task reads and writes now route through the project task-state authority across server mutation routes, Control Room, CLI task operations, Codex execution, pipelines, project synchronization, transcription metadata, and cleanup paths.
4. The legacy hydrated task replica, replica store, polling endpoint, and combined task/content invalidation flow were removed.
5. The Cloudflare protocol now carries a durable priority `state lane`: the `Durable Object` stores the complete event set and latest verified checkpoint, acknowledges after persistence, maintains bucket indexes, repairs missing history, and broadcasts live events only to project members.
6. The independent `content lane` now uses owner manifests, content hashes, atomic cache installation, bounded concurrency, retry backoff, and stale verified fallback. Content work yields whenever priority state work is active.
7. A fresh node verifies and installs a compatible state snapshot before applying the missing event tail; events emitted during bootstrap remain eligible for live delivery and final convergence.
8. `.decision-os/tasks.json` is ignored and untracked. It remains an atomic local compatibility export, while the event log and verified snapshots own reconstruction.
9. Sealed segments and snapshots archive asynchronously through writer-owned Git refs; archive failure does not change local acceptance or peer acknowledgement.
