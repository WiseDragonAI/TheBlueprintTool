## A. Control Room Runtime Problem

1. **Goal:** Give the Control Room current Codex lifecycle state without transferring complete run histories.
2. **Skill-run evidence:** The measured Control Room requested `12` skill runs with `since=0`, returning `10,472,386 bytes` of events and diagnostics.
3. **Pipeline coverage:** `loadControlRoom()` also requests full pipeline-run detail whenever `codexQueuedPipelineRunId` exists.
4. **Scope boundary:** This card changes Control Room lifecycle reads only. Existing desktop and mobile run-log views, cursor polling, cancellation, continuation, and pipeline detail remain unchanged.

---

## B. Compact Summary Contract

1. **Skill route:** Add `GET /api/codex/skills/runs/:runId/status` with required project scope, `ledgerId`, and `cardId` ownership.
2. **Pipeline route:** Add `GET /api/codex/pipelines/runs/:runId/status` with required project scope.
3. **Shared fields:** Return `runId`, run kind, normalized status, `active`, queue position, `startedAt`, `finishedAt`, `elapsedMs`, terminal error summary, and lifecycle revision.
4. **Status vocabulary:** Normalize pending, running, complete, failed, cancelled, stale, and unknown consistently across skill and pipeline runs.
5. **Live source:** Resolve active and queued state from the owning runtime registry and pipeline store.
6. **Restart source:** Persist one compact lifecycle record at queue, start, settle, cancel, and stale transitions so restart recovery never requires serializing run events.
7. **Projection use:** The Control Room projector calls the shared summary helper directly and stores only the compact lifecycle fields.
8. **Log boundary:** Keep current full log endpoints and explicit run-log rendering unchanged.

---

## C. Control Room Cutover

1. **Skill runs:** Remove Control Room requests containing `since=0`.
2. **Pipeline runs:** Remove Control Room requests for full pipeline detail.
3. **Task classification:** Use compact status, queue position, and timestamps for waiting and active classification.
4. **Backlog guard:** Reuse the shared summary helper when validating whether a task can move to backlog.
5. **Invalidation:** Advance the owning project runtime revision on queue, start, settle, cancel, stale detection, and pipeline-step transition.

---

## D. Verification Gates

1. **Payload:** Each status response remains below `2 KB`.
2. **Parity:** Skill and pipeline summaries match existing Control Room lifecycle classification across every normalized status.
3. **No history:** Control Room traffic contains no `events`, `diagnostics`, step bodies, and log output.
4. **Restart:** Active, queued, terminal, stale, missing, and unknown run fixtures produce deterministic summaries after server restart.
5. **Ownership:** Cross-project, wrong-ledger, wrong-card, and unknown-run requests are rejected.
6. **Regression:** Existing log rendering, cursor behavior, cancellation, continuation, pipeline detail, and pipeline progression tests remain unchanged and pass.
