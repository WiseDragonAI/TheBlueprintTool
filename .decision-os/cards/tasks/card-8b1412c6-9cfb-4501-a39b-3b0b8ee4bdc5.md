## A. Requested Queue Contract

1. **Global order:** Build one Control Room Queue order across every local project and every connected federation node; the owning node must not create a grouping boundary.
2. **Timestamp direction:** Among tasks without an explicit operator rank, place the most recently waiting task at the top and the longest-waiting task at the bottom.
3. **Manual override:** Preserve persisted `Queue rank` as the explicit operator-defined order created by the existing drag workflow.
4. **Scope:** Change the Queue ordering contract only; do not alter Exec, Backlog, task rendering, federation ownership metadata, or drag persistence.

## B. Verified Cause

1. **Local projection:** `backend/src/business/server/helper/control-room-projection-store.ts::compareTasks()` sorts the timestamp fallback with `left.waitingTime - right.waitingTime`, which puts the longest-waiting task first.
2. **Federation merge:** `backend/src/business/server/helper/federated-control-room-projection.ts::federatedControlRoomProjection()` concatenates the local projection followed by each remote projection and does not sort the merged Queue.
3. **Rendered path:** `frontend/src/app/responsive/application.js::loadControlRoom()` stores `/api/control-room` directly, and `renderControlRoom()` renders that array without a client-side reorder.
4. **Observed surface:** The supplied Control Room screenshot shows contiguous `Workstation` and `Mobile` task blocks instead of one waiting-time sequence.
