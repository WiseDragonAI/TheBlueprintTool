## A. Scope

1. **Objective:** Bring card processing with the skill library and pipeline library into the mobile interface under `frontend-mobile/`.
2. **Pipeline authoring:** Bring the existing pipeline creation and editing interface into the mobile interface.
3. **Source of truth:** Reuse the existing Codex skill, pipeline, and run contracts already used by the desktop frontend under `frontend/src/runtime/codex/`.
4. **Excluded:** Do not redesign the desktop card-processing and pipeline-management interfaces as part of this work.

---

## B. Mobile Card Processing

1. **Entry point:** Add a visible `Process card` action to the mobile card detail view for the active card.
2. **Selection interface:** Open a mobile-compatible processing interface that exposes both the skill library and the pipeline library.
3. **Skill execution:** Let the operator select a skill, review its available run settings, and start it against the active mobile card.
4. **Pipeline execution:** Let the operator select a saved pipeline, inspect its ordered steps, and start it against the active mobile card.
5. **Run feedback:** Show loading, submission, active-run, completion, cancellation, and failure states in the mobile interface.
6. **Context integrity:** Every run must use the active `ledgerId` and active card ID as its source context.

---

## C. Mobile Pipeline Management

1. **Entry point:** Add a `Pipelines` action to the mobile interface that opens the saved pipeline library.
2. **Library actions:** Support viewing saved pipelines and starting creation of a pipeline from the mobile library.
3. **Pipeline editor:** Support entering the pipeline name and purpose, adding ordered steps, editing steps, removing steps, and reordering steps.
4. **Skill composition:** Support adding skills from the skill library to each step, removing skills, reordering skills, and configuring the existing model and effort inheritance values.
5. **Persistence:** Save pipeline changes through the existing `/api/codex/pipelines` contracts and refresh the mobile library from the server response.
6. **Validation:** Surface skill-catalog failures, invalid references, save failures, empty states, and server warnings as actionable mobile messages.

---

## D. Mobile UX Requirements

1. **Touch layout:** All controls must remain usable on narrow touch screens without horizontal page overflow.
2. **Modal behavior:** Processing, library, editor, and skill-picker layers must provide explicit close and back actions and preserve the parent context when a nested layer closes.
3. **Interaction state:** Disable duplicate run and save submissions while their requests are pending.
4. **Accessibility:** Interactive controls must have accessible names, keyboard focus behavior, and visible focus states.
5. **Desktop parity:** Preserve the ordering, selection, inheritance, validation, and run semantics of the existing desktop interfaces.

---

## E. Acceptance Criteria

1. **Process with a skill:** From a mobile card detail view, the operator can open `Process card`, select a skill, start the run, and see its resulting status.
2. **Process with a pipeline:** From the same interface, the operator can select a saved pipeline, inspect its steps, start the run, and see its resulting status.
3. **Create a pipeline:** From the mobile `Pipelines` interface, the operator can create and save a pipeline containing ordered steps and ordered skills.
4. **Edit a pipeline:** The operator can reopen a saved pipeline, change its metadata and composition, save it, and see the refreshed definition in the mobile library.
5. **Error handling:** Failed catalog loads, failed saves, failed run submissions, invalid references, and server warnings are visible and do not leave the interface in a false success state.
6. **Regression coverage:** Automated tests cover the mobile entry points, skill execution request, pipeline execution request, pipeline creation, pipeline editing, nested navigation, pending-state guards, and failure states.

---
