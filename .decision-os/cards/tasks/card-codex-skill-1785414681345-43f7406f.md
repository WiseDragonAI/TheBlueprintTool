## C. Findings

1. **Root cause — Drift:** `mergeLocalThreadNotes()` treats `optimistic: true` as unconditional authority over an incoming same-ID note. When the incoming thread slice contains the terminal server note and the active ledger still contains the optimistic `uploading` note, `incomingIncludesThreadSlice` is true, the non-optimistic guard at `frontend/src/runtime/ledger/helper/merge-local-thread-notes.ts:64-66` does not apply, and the spread at `frontend/src/runtime/ledger/helper/merge-local-thread-notes.ts:67` writes the entire older local object over the newer server object. The resulting installed note keeps the old message, `uploading` status, and `optimistic: true`.
2. **First incorrect transition:** backend settlement and publication are correct before the failure. `finishVoiceUploadOrchestration()` persists the provider transcript as the same `noteId`, status `transcribed`, and revision `4` through `applyNotePatch()`: `backend/src/business/transcription/controller/start-voice-upload-orchestration-controller.ts:315-383`. Every successful patch emits a scoped `thread-content` event: `backend/src/business/transcription/controller/start-voice-upload-orchestration-controller.ts:96-107`, `backend/src/business/transcription/controller/start-voice-upload-orchestration-controller.ts:110-149`. The responsive frontend receives that event and requests active-thread hydration: `frontend/src/app/responsive/thread.js:480-490`. The first demonstrably wrong transition is therefore **server thread slice → merged frontend slice** at `mergeLocalThreadNotes()`.
3. **Why reload succeeds:** the corrupting merge requires an existing local optimistic object. A fresh page has no pre-reload optimistic `uploading` object to spread over the durable revision, so the persisted `transcribed` note installs and renders.
4. **Why the screenshot matches:** `submitPendingVoiceUpload()` assigns the exact screenshot body and status before upload at `frontend/src/runtime/voice/effect/submit-pending-voice-upload.ts:16-31`. The live hydration path can receive newer durable state while that object is still optimistic, then reinstall the old fields through the faulty merge.
5. **Renderer rejected as cause:** `renderThreadNotes()` reads the installed note body and status, includes body hash, status, revision, timestamps, and optimistic state in its render signature, then rebuilds changed rows: `frontend/src/runtime/thread/effect/render-thread-notes.ts:37-58`, `frontend/src/runtime/thread/effect/render-thread-notes.ts:102-142`. It faithfully renders the stale object supplied by the store.
6. **Targeted reconciliation rejected as cause:** `applyVoiceServerNote()` already uses the forward lifecycle comparator, copies the server lifecycle fields, clears `optimistic`, and rerenders: `frontend/src/runtime/voice/effect/reconcile-voice-transcription.ts:36-46`. Its focused tests prove direct `transcribing` revision `2` to `transcribed` revision `4` reconciliation: `frontend/test/runtime/voice-transcription-reconciliation.integration.test.ts:39-56`. The reported card route boots the responsive application at `frontend/src/runtime/surface-runtime.ts:8-29`, whose event path performs thread hydration instead of targeted voice reconciliation. After the faulty merge preserves `uploading`, `syncVoiceTranscriptionWatchers()` does not restore polling because it admits only `queued`, `transcribing`, and `finalizing`, then removes nonmatching watchers: `frontend/src/runtime/voice/effect/reconcile-voice-transcription.ts:103-123`.
7. **Transport rejected as cause:** the current responsive subscriber listens to both `ledger-content-change` and `card-content-change` and rejects mismatched project, ledger, and thread identities before hydration: `frontend/src/app/responsive/thread.js:470-490`. This closes the older missing-event defect documented in `documentation/working-documents/remote-task-collaboration-rca-2026-07-29.md:17-23`.
8. **Coverage omission:** existing tests prove direct voice-status reconciliation and prove that a newer local terminal optimistic note survives an older server `uploading` snapshot: `frontend/test/runtime/voice-transcription-reconciliation.integration.test.ts:39-56`, `frontend/test/runtime/voice-transcription-runtime.integration.test.ts:805-843`. No test exercises the inverse incident boundary: local optimistic `uploading` plus incoming same-ID server `transcribed` through `loadActiveThreadSlice()`.
9. **Non-causal backend drift:** `/api/voice-upload` awaits a second Tasks `recordContentContribution()` before ending its `202` response at `backend/src/business/transcription/http/transcription-routes.ts:95-109`, although the accepted note mutation already captures changed content through `persistTaskLedgerMutation()` at `backend/src/business/server/runtime/create-project-controller-runtime.ts:153-180`. This can extend the visible `uploading` phase, but the available static evidence does not prove that this await remained blocked in the reported request. It is not the selected root cause.

## D. Remediation Paths

1. **Selected patch:** change `mergeLocalThreadNotes()` in `frontend/src/runtime/ledger/helper/merge-local-thread-notes.ts` so a same-ID incoming voice note is admitted through the existing `shouldApplyVoiceServerNote(local, incoming)` lifecycle comparator. When admitted, retain the incoming message, voice lifecycle fields, revision, and `optimistic: false`; preserve only client-owned fields that remain locally necessary, including `localVoiceUploadId` and locally measured `imageSizes`.
2. **Preservation rule:** keep the current generic optimistic overlay for a note absent from the incoming slice and for an incoming same-ID note that is causally older. This retains the existing protection against stale reloads and delayed append-after-update writes required by `documentation/specs.json:2686-2695`.
3. **Regression:** add one focused case to `frontend/test/runtime/ledger-content-refresh.integration.test.ts` that seeds the active Tasks thread with same-ID `optimistic: true`, message `Voice note captured. Uploading audio...`, status `uploading`; returns a causally accepted thread slice with transcript text, `voiceFileRef`, status `transcribed`, revision `4`; runs `loadActiveThreadSlice()`; then asserts the active note has the transcript, terminal status, revision `4`, and `optimistic: false`.
4. **Reverse regression:** retain and explicitly pair the existing older-server coverage so a local terminal voice note still rejects an incoming backward lifecycle state. The patch must correct directionality, not disable optimistic preservation.

## E. Operator Decision Summary

1. **SITUATION:** durable transcription and scoped publication complete, but the open frontend can retain the optimistic `uploading` object.
2. **CAUSE:** `mergeLocalThreadNotes()` gives the optimistic flag more authority than the incoming voice lifecycle revision and overwrites the terminal server note during live thread hydration.
3. **DECISION:** patch the existing merge boundary with the existing voice lifecycle comparator; do not redesign the voice component, add a transport, add polling, and do not change persistence authority.
4. **PROOF LIMIT:** static analysis establishes the causal overwrite and exact change map. No implementation, automated verification, browser interaction, server restart, commit, push, subtask closure, and no master-task closure was performed.
