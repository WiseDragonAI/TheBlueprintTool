## A. Requested Specifications

1. **IDE-independent review:** Let the operator complete Git reviews inside Decision OS on mobile without opening a separate IDE.
2. **File links:** Let cards hold durable links to workspace files and open the linked file inside Decision OS.
3. **Markdown widget:** Embed Git review through a native `::git-diff` Markdown directive inside card content; keep `::html` iframe previews unchanged.
4. **Configurable repository:** Configure a workspace-relative Git repository root independently from the repository-relative review target so nested repositories are supported.
5. **Directive contract:** Use `::git-diff[Review changes](git-diff:?repo=packages%2Ffrontend&path=src%2Freview.ts)`; use `repo=.` and `path=.` for the workspace root repository.
6. **Unified diffs:** Render each target's working-tree Git diff with line numbers, syntax highlighting, inline additions and deletions, and collapsed unchanged context.
7. **Hunk carousel:** Present changed code as a previous-and-next carousel of reviewable hunks with file position and review progress.
8. **Card-content boundary:** Render overview, hunk review, voice recording, saved Git review notes, and staged confirmation inside the card Markdown widget without changing thread recorder state.
9. **Exact context:** Let the operator select a file, hunk, and exact line range, then persist repository, target, file, hunk, selected lines, quoted code, and patch hash.
10. **Voice reviews:** Let each hunk and selected line range receive one or more durable voice review notes stored on the card widget, never as thread notes.
11. **Shortcut ownership:** Keep `X` exclusively assigned to thread recording. Start, cancel, and send Git review recordings only through controls inside the Git widget.
12. **Capture exclusivity:** Permit only one active microphone capture; a thread recording blocks Git capture and a Git recording blocks the thread `X` command without opening the thread.
13. **Agent context:** Include each voice review's code-review context, transcript, and prior notes in the next agent turn.
14. **Validation as staging:** Let the operator validate a selected hunk by staging it while preserving every unstaged change.
15. **Stale protection:** Reject staging when the current patch hash differs from the displayed patch and require a refresh.
16. **Staged protection:** Mark staged hunks as accepted, inject the cached patch into agent instructions, and require the agent to leave accepted code unchanged.
17. **Agent contract:** Add the staged-code protection rule to the workspace `AGENTS.md`.
18. **Review state:** Show changed files and hunk position and provide explicit staging controls.
19. **Mobile evidence:** Provide four `390x844` mobile UX mockups and adjacent screenshot references that render as a Decision OS carousel.
