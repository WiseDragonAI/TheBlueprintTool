## A. Scope

1. **Backend boundary:** Extend the existing project catalog settings contract in `backend/src/business/server/helper/project-catalog.ts` and `PATCH /decision-os/projects/:projectId`.
2. **Editable metadata:** Persist `name`, `description`, and `color` overrides in the master workspace `.decision-os/projects.json`.
3. **Stable identity:** Keep `id`, `root`, `decisionOsRoot`, and `relativePath` derived from discovery and unavailable to the update payload.

---

## B. Implementation Contract

1. **Settings shape:** Store project overrides by project id so one atomic project update contains the complete editable metadata record.
2. **Fallbacks:** Return the directory basename when no name override exists, an empty string when no description exists, and the existing palette color when no color override exists.
3. **Validation:** Trim names, require `1..120` characters, limit descriptions to `1000` characters, and require colors to match `^#[0-9a-fA-F]{6}$`.
4. **Atomic behavior:** Validate the complete payload before writing; a rejected field must leave all persisted metadata unchanged.
5. **Compatibility:** Read the existing `colors` map so current project colors remain intact, then write the canonical metadata shape on the next successful update.

---

## C. Acceptance Criteria

1. **Catalog response:** `GET /decision-os/projects` returns `name`, `description`, and `color` for every project.
2. **Update response:** `PATCH /decision-os/projects/:projectId` returns the updated project after persisting all three editable fields.
3. **Reload:** A new catalog discovery returns the saved metadata.
4. **Isolation:** Updating one project does not change another project or any derived identity field.
5. **Tests:** Unit and server integration tests cover fallback metadata, legacy color migration, successful updates, validation failures, and no partial write.
