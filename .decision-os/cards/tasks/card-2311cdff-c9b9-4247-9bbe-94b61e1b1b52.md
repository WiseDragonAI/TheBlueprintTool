## A. Scope

1. Add one backend recovery operation for a source project and its latest synchronization run.
2. Reconcile the conflict owner against durable run state before mutation.
3. Retry the same failed run when it still owns the participant lock.
4. When the participant reports a different stale owner, conditionally cancel that owner, release its lock, and admit one fresh run with a new idempotency identity.
5. Serialize concurrent recovery requests per origin so only one run advances.

---

## B. Acceptance criteria

1. The reproduced `failed` workstation run plus stale phone lock progresses into one active recovery run.
2. A live conflicting owner remains untouched and the response identifies the active run.
3. Participant-offline failure leaves durable state unchanged and returns an actionable error.
4. Process restart resumes the single admitted recovery run without producing a second run.

---

1. `backend/src/business/project-sync/controller/start-project-sync.ts`

3. Project-sync controller integration tests covering two participant stores.
