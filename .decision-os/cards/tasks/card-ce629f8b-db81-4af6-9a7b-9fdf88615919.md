## A. Objective

Determine whether Decision OS can provide one genuinely unified Markdown editing and Git-diff surface instead of separate source, preview, split, or tabbed presentations.

The study must compare the internal document, state, rendering, transaction, decoration, diff, and lifecycle models of the pinned CodeMirror Markdown stack and Pierre diff stack. It must identify a technically coherent model that merges editable Markdown semantics with inline historical additions and removals without replacing the existing authoring guarantees.

This master task is a feasibility study only. It does not authorize production implementation.

---

## B. Required Investigation

1. Trace CodeMirror 6 and @codemirror/lang-markdown internals used by Decision OS: document state, syntax tree, transactions, history, selection, decorations, view plugins, virtualization, line wrapping, read-only behavior, and disposal.
2. Trace @pierre/diffs internals used by Decision OS: patch parsing, file and line models, unified and split rendering, shadow DOM, change indicators, syntax rendering, expansion, overflow, lifecycle, and supported extension points.
3. Compare both libraries against the canonical Decision OS Markdown renderer, including headings, lists, code blocks, tables, links, media, embedded HTML, Git-review blocks, and accessibility semantics.
4. Define one merged interaction and rendering model. The target is a single surface where authored Markdown remains editable while Git changes are represented within that same model. Two tabs, two independent panes, and a source/preview toggle do not satisfy the objective.
5. Identify structural blockers, dependency constraints, license implications, accessibility risks, performance risks, persistence implications, and the minimum proof needed before implementation is approved.

---

## C. Deliverables

1. A source-backed internal architecture comparison with exact package versions, repository paths, module symbols, and relevant upstream source references.
2. A selected unified model describing ownership of document bytes, syntax state, diff ranges, rendered semantics, transactions, undo and redo, selection, scrolling, focus, accessibility, and cleanup.
3. A feasibility verdict: feasible with the selected model, infeasible with verified blockers, or feasible only after explicitly named prerequisite changes.
4. A bounded proof-of-concept plan that tests the hardest integration boundary without introducing the production feature.
5. A production implementation plan only when the feasibility verdict supports it.

---

## D. Acceptance Criteria

1. The analysis compares actual CodeMirror, Pierre, and Decision OS renderer internals rather than surface CSS.
2. The proposed model is one integrated surface and does not reduce the request to separate tabs, panes, or modes.
3. The study preserves the current persistent editor-session guarantees: draft bytes, history, selection, search, wrapping, scroll, focus, read-only behavior, and cleanup.
4. The study explains how Git additions and removals map through Markdown edits and document transactions without corrupting source ranges.
5. The final recommendation selects one architecture and records the evidence that rules out the rejected models.
6. No production implementation occurs under this feasibility master task.
