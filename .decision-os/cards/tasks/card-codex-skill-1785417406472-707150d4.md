## A. Goal and Product Contract

1. **Goal need:** the live thread must replace stale optimistic voice state with the durable transcription state for the same note identity. The affected product area is the **thread voice-note lifecycle**.
2. **Actor and workflow:** the **operator** records a thread-scoped voice note, sees an immediate optimistic row, retains captured audio through pre-acceptance failure, receives live upload and transcription progress, then sees the durable transcript, terminal failure, and retry state on the same row after refresh and reload.
3. **Relevant context:** `requestTranscription()` creates one optimistic note ID, persists the audio in browser storage, and records that ownership in `localVoiceUploadId` before upload at `frontend/src/runtime/voice/effect/request-transcription.ts:40`. The backend advances that same ID through `queued`, `transcribing`, `finalizing`, and terminal state at `backend/src/business/transcription/controller/start-voice-upload-orchestration-controller.ts:307`.
4. **Current behavior:** `loadActiveThreadSlice()` passes the durable thread slice through `mergeLocalThreadNotes()` at `frontend/src/runtime/thread/effect/load-active-thread-slice.ts:148`. For a same-ID optimistic local note, `mergeLocalThreadNotes()` overlays the complete local record onto the incoming server record at `frontend/src/runtime/ledger/helper/merge-local-thread-notes.ts:51`, so stale local `message`, `status`, `revision`, lifecycle timestamps, and `optimistic` can replace a newer durable terminal state.
5. **Expected behavior:** a same-ID optimistic voice note remains one visible row, while accepted forward server lifecycle fields become authoritative. Browser-only audio ownership remains governed by the local upload cleanup result. Non-voice optimistic notes retain their existing reconciliation behavior.
6. **Acceptance signal:** before the server response, the row is visible as optimistic and busy. After a same-ID durable `transcribed`, `transcription failed`, and `execution launch failed` state arrives through a live thread refresh, the row shows the server message and terminal status, stops showing busy progress, preserves retry inputs required by the terminal failure, then reloads with the same durable state. Successful browser-audio cleanup clears `localVoiceUploadId`; failed cleanup retains it without restoring stale lifecycle fields.

## D. Verified Gaps and Constraints

1. **Contradiction:** the server persists a forward terminal state on the stable note ID, while the generic optimistic merge gives stale local fields precedence over the incoming same-ID record. The separate voice acceptance helper explicitly rejects backward lifecycle movement at `frontend/src/runtime/voice/helper/voice-transcription-lifecycle.ts:62`.
2. **Source gap:** current tests verify targeted polling reconciliation, revision ordering, local upload retention, retry, and reload restoration. They do not verify voice lifecycle authority through `mergeLocalThreadNotes()` in either caller.
3. **Ownership gap:** voice transition rules belong to `shouldApplyVoiceServerNote()`, while state installation is owned by `mergeLocalThreadNotes()`, `loadActiveThreadSlice()`, and `reconcileActiveLedgerState()`. The generic installation boundary currently has no voice-specific acceptance handoff.
4. **Product-boundary decision:** source evidence identifies `localVoiceUploadId` as the browser-owned voice discriminator. Extending voice transition authority to generic optimistic text notes is unsupported by the linked specifications.
5. **Technical constraint:** replica revision order alone does not authorize a backward voice transition. `shouldAcceptReplicatedTaskState()` separately enforces voice lifecycle direction at `frontend/src/runtime/refresh/helper/task-projection-acceptance.ts:40`.
6. **UX constraint:** `renderThreadNotes()` derives busy presentation, terminal labels, errors, and retry controls directly from the installed note fields. A stale merge therefore changes operator-visible behavior, not only internal state.
7. **Data constraint:** server lifecycle fields are enumerated by `voiceLifecycleFields`; `localVoiceUploadId` is intentionally absent and remains browser-owned. Whether it persists after cleanup failure is source-backed; its eventual cleanup deadline is **unknown**.
8. **Dependency constraint:** live correction depends on the backend thread-content write, the scoped refresh event, active-thread slice loading, same-ID merge acceptance, rendering, and durable reload. Static source inspection verifies these boundaries; served-route behavior remains **unverified** in this analysis stage.
