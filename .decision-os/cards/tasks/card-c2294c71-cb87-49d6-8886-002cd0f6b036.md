## A. Corrected Goal

1. **Goal:** complete repository, linked-specification, and memory analysis before asking the operator any clarification question.
2. **Critical correction:** `Questions` is not a pipeline skill input to linked-spec analysis. It is an operator stage generated by the completed codebase analysis.
3. **Planning correction:** the generic `Plan review` stage is removed. Pipeline 2 ends with a precise explanation of the problem and a presentation of the solution selected as best.
4. **Boundary:** analysis and task definition only. No product code, installed skill, saved pipeline, UI, or persistence behavior is changed.
5. **Deferred item:** automatically enqueueing the recorded continuation pipeline remains deferred.

---

## B. Corrected Lifecycle

1. **`Spec clarification`:** normalize the original request without inventing missing answers.
2. **`Linked specs analysis`:** identify and analyze every specification connected to the affected behavior.
3. **`Memory review`:** compare the request and linked specification context with every applicable project and global memory.
4. **`Codebase analysis`:** inspect the implementation, combine repository evidence with linked specs and memory findings, define the complete problem context, and emit only the remaining questions.
5. **`Questions`:** operator stage; present the codebase-analysis questions and persist the answers.
6. **`Tasks`:** create, order, and completeness-audit tasks using the full analysis plus operator answers.
7. **`Maximum architecture`:** construct the most complex compliant solution.
8. **`Hackish baseline`:** construct the smallest dirty shortcut for the same behavior.
9. **`Over-engineering review`:** compare the real task plan with both extremes and select the smallest correct solution.
10. **`Problem and solution explanation`:** explain the exact problem being solved and present the selected solution with its evidence, tradeoffs, and rejected extremes.
11. **`Execution`:** implement the operator-accepted solution.
12. **`Check and commit`:** test, correct code quality, and commit.
13. **`Report`:** produce the implementation report.
14. **`QA`:** operator validation stage.
15. **`Lessons`:** persist qualified reusable lessons after QA acceptance.

---

## C. Pipeline 1 — Context Analysis

1. **Ordered machine stages:** `Spec clarification` → `Linked specs analysis` → `Memory review` → `Codebase analysis`.
2. **Input:** original operator message, source-card context, repository, linked specifications, and applicable memories.
3. **Combined analysis:** codebase analysis must link concrete implementation evidence to specification requirements, missing coverage, memory warnings, affected workflows, runtime state, data boundaries, and acceptance signals.
4. **Output:** a complete context package plus a structured question set containing only facts that remain unresolved after all available evidence has been exhausted.
5. **Terminal transition:** Pipeline 1 stops at operator stage `Questions`. No downstream skill consumes unanswered questions.

---

## D. Operator Gate 1 — Questions

1. **Source:** every question is emitted by `Codebase analysis` and cites the unresolved evidence gap and downstream impact.
2. **Interaction:** the operator answers through the choice-based question UX; answers are persisted against the exact context-package revision.
3. **Completion:** the answered context package becomes the sole input to Pipeline 2.
4. **Revision:** operator feedback that invalidates the analyzed context restarts Pipeline 1; unanswered questions block Pipeline 2.

---

## E. Pipeline 2 — Solution Design

1. **Ordered machine stages:** `Tasks` → `Maximum architecture` → `Hackish baseline` → `Over-engineering review` → `Problem and solution explanation`.
2. **Input:** the complete Pipeline 1 context package and its persisted operator answers.
3. **Tasks:** task inventory, dependency grouping, and completeness audit must cover the codebase analysis, linked specifications, memory findings, and answers.
4. **Adversarial comparison:** maximum architecture and hackish baseline are isolated artifacts used to test the real plan from both extremes.
5. **Selected solution:** over-engineering review identifies the smallest correct solution.
6. **Terminal output:** problem-and-solution explanation presents the precise problem, why it exists, affected behavior, selected solution, why it is best, concrete tradeoffs, and why both extremes were rejected.

---

## F. Operator Gate 2 — Problem and Solution Explanation

1. **Presented evidence:** exact problem statement, relevant codebase evidence, linked specifications, memory findings, operator answers, task coverage, architecture extremes, selected solution, and verification strategy.
2. **Continue:** operator acceptance binds the selected solution revision as the sole input to Pipeline 3.
3. **Request revision:** operator feedback is persisted and Pipeline 2 restarts from `Tasks` using the same answered context package.
4. **Removed concept:** there is no generic `Plan review` stage or label.

---

## G. Pipeline 3 — Implementation Delivery

1. **Ordered machine stages:** `Execution` → `Check and commit` → `Report`.
2. **Input:** the operator-accepted problem-and-solution revision.
3. **Output:** implementation, verification evidence, focused commit, operator-facing report, and manual QA instructions.
4. **Terminal transition:** successful completion enters operator stage `QA`; it does not mark the master task done.

---

## H. Operator Gate 3 — QA

1. **Accept:** authorize Pipeline 4 `Lessons`.
2. **Reject:** persist QA feedback and restart Pipeline 1 at `Spec clarification`, ensuring the entire context is reassessed.
3. **Safety:** report completion and automated checks never substitute for operator QA.

---

## I. Pipeline 4 — Lessons

1. **Ordered machine stage:** `Lessons`.
2. **Input:** original request, analyzed context, questions and answers, selected solution, implementation evidence, report, QA outcome, and feedback history.
3. **Output:** qualified reusable lessons persisted with memory identifiers and source provenance.
4. **Terminal rule:** completion ends the execution lifecycle but does not close the master task automatically.

---

## J. Stage Label Contract

1. **Displayed labels:** `Spec clarification` → `Linked specs analysis` → `Memory review` → `Codebase analysis` → `Questions` → `Tasks` → `Maximum architecture` → `Hackish baseline` → `Over-engineering review` → `Problem and solution explanation` → `Execution` → `Check and commit` → `Report` → `QA` → `Lessons`.
2. **Operator stages:** `Questions`, `Problem and solution explanation`, and `QA` remain visible while awaiting operator action.
3. **Lifecycle separation:** queue position and machine lifecycle status remain separate from the stage label.
4. **Skill separation:** the skill name remains diagnostic detail and never replaces the stage label.

---

## K. Acceptance Signals

1. **Evidence first:** Pipeline 1 exhausts repository, linked-specification, and memory evidence before producing questions.
2. **No invalid handoff:** linked-spec analysis, memory review, and codebase analysis never receive unanswered operator questions as input.
3. **No premature tasks:** Pipeline 2 cannot start until every blocking question has a persisted answer tied to the analyzed context revision.
4. **No generic plan review:** the operator receives a precise problem explanation and best-solution presentation.
5. **No premature execution:** Pipeline 3 cannot start until that selected solution revision is accepted.
6. **QA feedback:** rejected QA restarts the complete context analysis.
7. **Master lifecycle:** no pipeline or operator stage closes the master task automatically.
