## A. Outcome and Boundary

1. **Outcome:** the complex execution lifecycle is split into four machine pipelines separated by three mandatory operator gates.
2. **Implemented foundation:** Decision OS now renders Senior-compatible questions as a native card widget and persists revision-bound answers.
3. **Current implementation boundary:** the widget and its `ledger-cli` write contract are implemented; the saved pipeline definitions and remaining planned skills are not implemented in this card.
4. **Deferred continuation:** automatic enqueueing of the recorded next pipeline remains a separate future decision.

---

## B. Context-First Lifecycle

1. **Pipeline 1:** `Spec clarification` → `Linked specs analysis` → `Memory review` → `Codebase analysis` → `Master task synthesis`.
2. **Operator Gate 1:** `Questions`.
3. **Pipeline 2:** `Tasks` → `Maximum architecture` → `Hackish baseline` → `Over-engineering review` → `Problem and solution explanation` → `Master task synthesis`.
4. **Operator Gate 2:** accept the presented problem and selected solution, then launch Pipeline 3.
5. **Pipeline 3:** `Execution` → `Check and commit` → `Report`.
6. **Operator Gate 3:** `QA`.
7. **Pipeline 4:** `Lessons`.

---

## C. Pipeline 1 — Context Analysis

1. **Evidence order:** exhaust the original request, linked specifications, applicable project and global memories, and repository implementation before asking the operator anything.
2. **Codebase analysis output:** a revisioned context package containing verified behavior, affected workflow, data and runtime boundaries, conflicts, missing coverage, risks, acceptance signals, and unresolved questions.
3. **Master task synthesis:** write the context package as a CTO decision brief and mount its question set in the owning card.
4. **Stop condition:** Pipeline 1 ends after the card is written. No machine stage receives unanswered questions.

---

## D. Operator Gate 1 — Questions

1. **Source:** questions are emitted only by completed codebase analysis after evidence exhaustion.
2. **Widget declaration:** the owning card mounts `::questions[Operator questions](questions:?id=<questionnaire-id>)`.
3. **Question payload:** every question has a stable `id`, precise question text, exactly four emoji-labeled choices, and one free-text placeholder.
4. **Durable state:** card field `questionnaires[questionnaireId]` stores `version: 1`, `contextRevision`, questions, `currentQuestionId`, and responses.
5. **Revision gate:** changing `contextRevision` requires clearing prior non-pending responses; stale answers cannot authorize Pipeline 2.
6. **Interaction:** mouse, touch, `W/E/S/D`, `X`, `C`, and `Ctrl+Enter` use the same selection, irrelevant, skip, and custom-answer behavior as Senior.
7. **Completion:** every blocking answer must be persisted against the current context revision before Pipeline 2 launches.

---

## E. Pipeline 2 — Solution Design

1. **Input:** the complete Pipeline 1 context package plus its revision-valid operator answers.
2. **Tasks:** inventory, dependency grouping, and completeness audit cover code evidence, specifications, memories, and answers.
3. **Adversarial artifacts:** maximum architecture constructs the most complex compliant design; hackish baseline constructs the smallest dirty shortcut.
4. **Selection:** over-engineering review compares the real plan with both extremes and selects the smallest correct solution.
5. **Decision explanation:** state the exact problem, root cause, affected behavior, selected solution, tradeoffs, verification strategy, and reasons both extremes were rejected.
6. **Master task synthesis:** update the CTO brief with the selected solution and operator decision request.

---

## F. Operator Gate 2 — Solution Decision

1. **Continue:** acceptance binds the selected solution revision as Pipeline 3 input.
2. **Request revision:** feedback is persisted and Pipeline 2 restarts from `Tasks` with the same answered context revision.
3. **Removed stage:** no generic `Plan review` label remains.

---

## G. Pipeline 3 — Implementation Delivery

1. **Execution:** implement only the accepted solution revision.
2. **Check and commit:** run tests, correct code quality, and create focused commits.
3. **Report:** summarize implemented behavior, evidence, remaining limits, and manual QA instructions.
4. **Stop condition:** successful reporting enters operator `QA`; it does not complete the master task.

---

## H. Operator Gate 3 — QA

1. **Accept:** authorize Pipeline 4 `Lessons`.
2. **Reject:** persist QA feedback and restart Pipeline 1 at `Spec clarification`.
3. **Authority:** automated checks never substitute for operator QA.

---

## I. Pipeline 4 — Lessons

1. **Input:** original request, evidence package, questions and answers, selected solution, implementation evidence, report, QA result, and feedback history.
2. **Output:** qualified reusable lessons with source provenance and memory identifiers.
3. **Terminal rule:** lessons end the execution lifecycle without automatically closing the master task.

---

## J. CTO Master Task Contract

1. **Executive summary:** state the decision required, current stage, recommended action, and material consequence in the first screen.
2. **Outcome:** define the operator need, affected actor, workflow, and measurable acceptance signals.
3. **Verified context:** cite current code behavior, linked specifications, memory findings, data boundaries, runtime state, and conflicts.
4. **Decision gaps:** show only unresolved facts with impact, recommended choice, and revision-bound question controls.
5. **Solution:** present the exact problem and root cause, selected solution, task coverage, dependencies, risks, tradeoffs, and rejected adversarial extremes.
6. **Delivery evidence:** retain commits, verification results, implementation limits, QA instructions, QA feedback, and lessons provenance.
7. **Signal discipline:** exclude raw logs, repeated narrative, generic process advice, and implementation detail that does not change a CTO decision.

---

## K. Master Task Synthesis Skill

1. **Invocation 1:** run after `Codebase analysis` to create the evidence-backed CTO brief and question widget.
2. **Invocation 2:** run after `Problem and solution explanation` to update the same brief with the selected solution and Gate 2 decision.
3. **Inputs:** original request, revisioned context package, linked specs, memories, code evidence, questions and answers, task artifacts, architecture extremes, and selected solution.
4. **Output discipline:** preserve evidence provenance, stable section identities, questionnaire identity, context revision, operator decisions, and existing delivery evidence.
5. **Failure:** missing evidence is stated as a blocker; the skill never fills a gap with a supposition.
