## A. Scope

1. **Objective:** Preserve every completed voice recording in browser-local durable storage before the first network upload.
2. **Recovery:** Expose retry for an upload that fails before the server returns a `voiceFileRef`.
3. **RCA evidence:** The captured note entered `upload failed` without a `voiceFileRef`; the prior renderer only marked `transcription failed` notes with a server `voiceFileRef` as retryable.

## B. Contract

1. **Persistence order:** Write the captured `Blob` to `IndexedDB` before calling `POST /api/voice-upload`.
2. **Retry identity:** Associate the local recording with the stable optimistic `noteId`, `threadId`, ledger identifier, card identifier, MIME type, and `queueCodex` value.
3. **Cleanup:** Delete the local recording only after the server accepts and durably preserves the upload.
4. **Reload recovery:** Restore retry availability from `IndexedDB` after a fresh page load.
5. **Failure safety:** Retain the local recording after network rejection, non-success HTTP response, malformed response, and metadata failure before server acceptance.

## C. Acceptance Criteria

1. **Pre-upload failure:** A failed `POST /api/voice-upload` leaves a visible `Retry` control backed by the original audio.
2. **Optimistic timing:** The local recording exists before the upload request begins.
3. **Success cleanup:** A successful accepted upload removes the matching local recording.
4. **Reload:** A failed upload remains retryable after a fresh page load.
5. **Regression:** Automated tests cover persistence-before-fetch, failure retention, retry reuse, reload discovery, and accepted-upload cleanup.
6. **Target route:** The changed frontend module is served at `http://127.0.0.1:50150/` without restarting the server.
7. **Operator gate:** Exercise one real-device `record → failed upload → reload → Retry` path before authorizing master completion.
