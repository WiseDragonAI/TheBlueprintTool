## A. Outcome

Deliver **safe skill and pipeline-prompt authoring inside Decision OS** without putting `main` or production federation at risk. Operators create, edit, save, and inspect revision history from the Skills interface; every successful content save creates a scoped Git revision.

---

## B. Authoring Surface

1. Add creation to the existing Skills interface.
2. Open content in a reusable CodeMirror 6 modal sized `80vw` by `95vh`.
3. Pin and locally bundle CodeMirror with Markdown syntax, history, search, keyboard commands, dirty state, accessible focus handling, and a toolbox.
4. Keep loading, Git persistence, federation, and pipeline injection outside the editor adapter.
5. Add a code comment naming future thread-attachment click-to-edit reuse; do not implement attachment editing in this task.

---

## C. Git Revision Experience

1. After each successful content save, create one scoped Git commit containing only that authored file and the required metadata file for a pipeline-only prompt.
2. Expose the current file plus its complete Git commit history through project-scoped APIs.
3. Add previous and next revision controls in the editor and render the selected revision against its successor with the existing `@pierre/diffs` `1.2.12` integration.
4. Show removals in red and additions in blue. Do not use red and green as the sole distinction; preserve textual signs, line numbers, and accessible labels.
5. A failed save or failed commit must not report a new revision. Preserve the file and Git evidence needed for explicit recovery.

---

## D. Content Kinds and Synchronization

1. Use `SKILL.md` frontmatter `name` as identity for agent-visible skills.
2. Support `federated-skill`: stored in the server skill root, discoverable by agents, and synchronized through the existing federation package.
3. Support `workspace-skill`: stored in the active workspace skill root, discoverable by agents in that workspace, and excluded from federation.
4. Support `pipeline-prompt`: stored in the pipeline library, excluded from every Codex, cloud-agent, workspace-skill, workstation-skill, and federation discovery path, and injected only when a pipeline step explicitly selects it.
5. The creation control selects one content kind explicitly. Do not represent pipeline-only prompts as `.skills` directories.

---

## E. Canary Boundary

1. Start from the current `main` tip on a dedicated `dev` branch and isolated worktree.
2. Run the canary on port `50151` through its own MultiTerm registration without stopping or replacing production `50150`.
3. Use a distinct Wrangler `dev` relay environment, Worker identity, Durable Object namespace, credentials, logs, and ignored settings.
4. Prove the canary boundary before feature implementation. Promotion remains an explicit later operator decision.

---

## F. Documentation and Proof

1. Document creation, save, history, revision-content, revision-diff, content-kind, pipeline injection, Git commit, conflict, and federation contracts.
2. Document the dev branch, worktree, MultiTerm registration, relay environment, settings, deployment, verification, rollback, and cleanup.
3. Test creation, discovery exclusion, injection, path containment, revision conflicts, Git history, commit failure, Pierre rendering, red/blue accessibility, export invalidation, and canary isolation.
4. Verify the complete served interaction on the canary before claiming the feature works.
