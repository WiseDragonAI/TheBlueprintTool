## A. Outcome

Deliver **safe skill creation and editing inside Decision OS** without putting `main` or the production relay at risk. The Skills interface must create a valid `SKILL.md`, open editable files in a reusable editor, save through revision-aware APIs, and expose whether the skill is local or federated.

---

## B. Product Boundary

1. Add skill creation to the existing Skills interface.
2. Open skill files in an editor modal sized `80vw` by `95vh`.
3. Use **CodeMirror 6**, pinned and locally bundled, for Markdown editing, keyboard behavior, search, history, syntax highlighting, and extensible toolbar actions.
4. Keep the editor adapter reusable. Add a code comment naming the future thread-attachment click-to-edit use case, but do not implement attachment editing in this task.
5. Preserve existing skill discovery and revision-aware save behavior.

---

## C. Skill Identity and Synchronization

1. Use the existing `SKILL.md` frontmatter `name` as skill identity.
2. Let the creation checkbox select ownership once: server-owned `.skills` content is federated; active-workspace `.skills` content remains local.
3. Do not add a second registry, replication manifest, persisted replication boolean, or parallel relay protocol.
4. Invalidate and republish the existing skill export index after successful federated creation or modification.
5. Reject revision conflicts and unsafe paths without overwriting durable content.

---

## D. Canary Boundary

1. Start from the current `main` tip on a dedicated `dev` branch and isolated Git worktree.
2. Run the canary server on its own port and register it in MultiTerm without stopping or replacing the production server.
3. Provision a distinct Wrangler `dev` relay environment using the current federation packages and protocol.
4. Keep canary state, relay bindings, logs, and credentials isolated from production. Promotion requires passing automated checks and explicit operator validation.

---

## E. Documentation and Proof

1. Document every new or changed HTTP contract, payload, validation error, revision-conflict response, and synchronization side effect.
2. Document the `dev` branch, worktree, server, MultiTerm, relay, environment variables, deployment, verification, rollback, and cleanup procedures.
3. Add focused tests for creation, root ownership, path containment, editing, conflict rejection, cache invalidation, publication, and canary isolation.
4. Verify the served Skills route with complete browser interaction evidence before claiming the editor works.
