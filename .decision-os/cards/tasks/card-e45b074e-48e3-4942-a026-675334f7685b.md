## A. Incident Summary

On 2026-07-23, Mobile sent a Decision OS node message to Workstation asking a new Codex process to read the active or most recent Decision OS epoch-4 implementation session log. The request remained silent for approximately 29 minutes. Mobile displayed one active requester stream, but received no acceptance, run ID, progress, answer, or failure. The local CLI was terminated at approximately 2026-07-23T10:23:19Z.

The surviving evidence proves only that Mobile retained a pending federation request. It does not prove that Workstation admitted the request, created a run, spawned Codex, or confirmed cancellation.

---

## B. Confirmed Defects

1. The relay forwards `request-open` without an owner acceptance acknowledgement. `requesterStreamCount` therefore represents a waiting caller, not confirmed execution.
2. Workstation creates the node-message run ID and writes a `running` manifest before process spawn, but withholds the run ID until terminal completion. The requester cannot inspect or poll the run.
3. All relay frames share one serialized promise queue. An unbounded task-state merge can block later RPC frames while the Workstation socket still appears online.
4. The node-message HTTP route does not publish an admitted or started lifecycle response before awaiting the complete Codex turn.
5. Cancellation is fire-and-forget. The relay deletes its stream immediately after forwarding `cancel`, without confirmation that Workstation received it, terminated a child, or persisted terminal state.
6. Admission, execution, federation, and CLI deadlines cluster around 30 minutes, creating a long silent interval and timeout races.
7. Federation diagnostics expose neither remote server build identity nor remote node-message execution state.
8. Existing cancellation coverage verifies stream counters but does not prove remote process termination or a cancelled manifest.

---

## C. Required Outcome

Replace the synchronous opaque RPC with a durable, acknowledged node-message lifecycle. A requester must learn within a short bounded interval whether Workstation accepted the operation, receive a stable request and run identity, observe progress independently of the original connection, and receive verified terminal or cancellation state.

---

## D. Acceptance Criteria

1. Workstation returns an authenticated durable receipt containing `requestId` and `runId` immediately after persisting admission.
2. Node-message state exposes at least `accepted`, `waiting_for_capacity`, `spawned`, `running`, and terminal phases with timestamps.
3. A status endpoint retrieves the same run after requester disconnect or relay reconnect without launching a duplicate process.
4. RPC request handling cannot be blocked by task-state replication callbacks; each processing class has an explicit bounded failure boundary.
5. Cancellation remains correlated until Workstation confirms terminal cancellation or reports that no process was created.
6. Workstation build identity and node-message phase are visible in federation diagnostics.
7. Admission fails visibly within a short timeout. The longer execution deadline begins only after durable admission and does not keep the initiating HTTP request open.
8. Regression coverage proves behavior when state-frame processing is blocked, the requester disconnects after admission, cancellation occurs before and after spawn, and Workstation reconnects before result retrieval.
9. No UI or CLI status labels a request as running based only on a requester-side stream count.
