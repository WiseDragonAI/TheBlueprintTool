## A. Context and objective

1. Repeated test failures persist because the repository has **partial safeguards, not one end-to-end verification contract**.
2. The objective is to make **every test and typecheck derive code, configuration, working directory, admission, and cleanup from the active worktree through one enforced entry point**.
3. The attached failure occurred while validating a backend prompt change in a worktree: inherited TypeScript configuration resolved the primary checkout instead of the changed worktree.

---

## B. What was actually built

1. On May 26, `c6856214` added the server launcher and set `TSX_TSCONFIG_PATH` to an absolute backend config under the launcher checkout. This value is inherited by Codex workers.
2. On July 10, `1a99fb1c` fixed frontend aliases by setting `TSX_TSCONFIG_PATH=tsconfig.json` in three frontend test scripts. Backend scripts were unchanged.
3. On July 12, `73175ddd` required isolated worktrees for tests. It defined Git isolation and cleanup, not runtime environment construction.
4. On July 14, `e93632e6` added a read-only workload diagnostic.
5. Later on July 14, `e647f09b` simplified it to repository-scoped admission and documented that simultaneous `GO` results remained possible.
6. On July 15, `6d65410a` added `decision-os-verify`: a repository-wide `flock`, direct-command validation, shared lock resolution across worktrees, and signal forwarding.
7. Also on July 15, `b86182b2` made the launcher executable.
8. On July 16, `57e8af65` capped direct Node test runners at concurrency three.
9. The history contains **eight material commits around this failure chain**, but they address separate concerns.

---

## C. Why the same failure still occurs

1. `decision-os-verify` is worktree-aware only for the shared lock. It **passes the parent environment unchanged** and does not derive a worktree-local TypeScript config.
2. The server exports an absolute primary-checkout `TSX_TSCONFIG_PATH`; Codex executions inherit it.
3. Backend test scripts invoke `tsx` without replacing it. A worktree test can therefore import primary-checkout source while the changed file exists only in the worktree.
4. Frontend scripts fixed this locally; backend scripts and direct backend commands did not. The system is **asymmetric by package and dependent on manual overrides**.
5. The full gate is chained npm. The lease accepts one `npm` process, but its concurrency rewrite recognizes only direct `node --test`, so it does not own inner runners.
6. The cleanup failure is separate. The screenshot establishes emission after a temporary directory was removed; the thread lacks the test name, assertion, and raw output, so **its exact cause is not verified**.
7. The core defect is **missing executable ownership of environment and lifecycle at the verification boundary**.

---

## D. Chosen direction

1. Make `decision-os-verify` the single authority: derive the active worktree root, replace inherited repository variables, select package config, retain the lease, and own concurrency.
2. Route repository, frontend, and backend verification through that authority.
3. Add a real-worktree regression that injects a primary-checkout config and proves a worktree-only backend change is loaded.
4. Add a cleanup regression after the raw failing test is identified.
5. This advances the objective because **one executable boundary replaces package-specific fixes and agent memory with a testable invariant**.

---

## E. Expected outcome and operator question

1. Verification must not load code or config from a sibling checkout, bypass the lease, or exceed the owned concurrency limit.
2. Implementation must preserve package-relative working-directory behavior while replacing inherited repository paths.
3. To close the cleanup defect, provide the raw failure block containing the test name and assertion. The source-resolution defect is fully traced.
4. The master task remains open; audit and failure proof are verified, while implementation is not completed.
