## A. Operator Request Summary

1. **Card title:** Rename this card so it directly describes the Decision OS control room.
2. **Primary surface:** Make the control room the main Decision OS page, with a mobile-first interface organized into multiple tabs.
3. **Waiting-task stack:** Use the first tab for the stack of tasks waiting to be processed.
4. **Task hierarchy:** Every task is linked to a master task represented by a master card. Opening the master card shows its subtasks and each subtask status; opening a subtask opens its card directly.
5. **New-task action:** Put a `New task` button at the top of the control room.
6. **Task intake:** Pressing `New task` opens a new thread where the operator can record voice notes and attach files.
7. **Codex handoff:** From the intake thread, the operator launches Codex. Codex categorizes the task, selects the correct ledger, creates a new zone with a new master-task card, and then navigates the operator directly to that task card.
8. **Mandatory new zone:** Each new task creates a new zone. Codex must not reuse an existing zone.
9. **Queue order:** Show waiting master tasks in `FIFO` order so the oldest waiting task is immediately visible and can be handled first.
10. **Manual priority:** Allow drag-and-drop reordering of tasks in the waiting list.
11. **Ledger filters:** Generate dynamic filter buttons from discovered ledger names.
12. **Cross-project discovery:** A single Decision OS server must discover ledgers in subdirectories, removing the need to run one server per project.

## B. Control Room Information Architecture

1. **Default route:** The Decision OS root opens the control room rather than a specific ledger canvas.
2. **Mobile shell:** Use a sticky top action area, a scrollable content region, and a bottom tab bar that remains reachable with one hand.
3. **First tab — `Queue`:** Show master-task cards waiting for treatment. This is the default selected tab.
4. **Second tab — `Active`:** Show master tasks with at least one subtask currently being processed, including progress and elapsed state.
5. **Third tab — `Done`:** Show recently completed master tasks so the operator can reopen their cards without searching a ledger canvas.
6. **Top action:** Place the full-width primary `New task` button above the active tab content. Keep it visible while the queue scrolls.
7. **Filter row:** Place a horizontally scrollable row beneath `New task`, beginning with `All`, followed by one filter chip per discovered ledger name.
8. **Desktop adaptation:** Preserve the same hierarchy on wider screens, move tabs into a compact navigation rail, and keep the task list as the primary column.

## C. Queue UI and Interaction

1. **Default ordering:** Order waiting master tasks by the time they entered the waiting state, oldest first. The first card is therefore the next task to treat.
2. **Master-card summary:** Each queue item shows the master-task title, ledger name, waiting age, aggregate progress such as `2/5 complete`, current overall status, and the next actionable subtask.
3. **Visual priority:** Give the oldest untouched item the strongest queue emphasis and show its waiting age without requiring expansion.
4. **Expand behavior:** Tapping the body of a master-task item expands it in place to reveal its subtasks while preserving the operator's queue position.
5. **Subtask row:** Each subtask row shows its title and exact status. Tapping the row opens that subtask's card directly in its source ledger.
6. **Master-card navigation:** A distinct `Open master task` action opens the master card itself. Expansion must not accidentally navigate away.
7. **Manual reordering:** A dedicated drag handle reorders master-task items. A completed drop persists the explicit queue rank and immediately updates the visible list.
8. **FIFO after reordering:** Manual rank takes precedence for reordered items; tasks without a manual rank remain ordered by waiting-entry time. This preserves a deterministic queue after an operator reprioritizes it.
9. **Touch accessibility:** Support long-press on the drag handle, provide a visible lifted state and insertion marker, and expose `Move up` and `Move down` actions for non-drag input.
10. **Filtering:** Selecting a ledger chip limits every task tab to master tasks from that ledger. `All` clears the ledger filter, and the selected filter persists while moving between tabs.
11. **Empty state:** When no waiting task matches the selected ledger, show `No waiting tasks` and retain the `New task` action and ledger filters.

## D. New Task User Journey

1. **Start:** The operator presses `New task`; Decision OS immediately creates a draft intake thread and opens it as a focused composer.
2. **Capture:** The composer provides `Record voice note`, file attachment, and text entry in the same chronological thread. Each successfully saved input appears as a thread message.
3. **Draft safety:** The intake remains a draft until Codex is launched. Closing the composer retains the draft and exposes it in the control room for later continuation.
4. **Launch readiness:** Enable `Launch Codex` after the thread contains at least one saved voice note, attachment, or text message.
5. **Processing state:** After launch, lock duplicate launches, keep the thread readable, show the active Codex state, and provide a return path to the control room.
6. **Categorization:** Codex reads the complete intake thread and attachments, determines the destination ledger from the ledgers discovered by the server, and assigns the task to that ledger.
7. **Creation contract:** Codex creates exactly one new zone in the selected ledger and exactly one master-task card in that zone. The intake thread becomes the master card's thread so the captured context remains attached to the task.
8. **Subtask creation:** Codex creates the actionable subtask cards inside the new zone and links each one to the master-task card.
9. **Successful destination:** Once creation succeeds, Decision OS navigates directly to the new master-task card with its subtask list visible.
10. **Failure recovery:** If classification or creation fails, keep the intake thread intact, display the concrete failure, and allow the same launch to be retried without creating a second zone or master card.

## E. Cross-Ledger Discovery Contract

1. **Single server scope:** The Decision OS server scans its configured workspace root and discovers valid ledger files in nested project directories.
2. **Stable identity:** Identify each discovered ledger by its canonical ledger file path in addition to its ledger name so identical names in different projects do not collide.
3. **Display labels:** Filter chips use the ledger name. When names collide, append the shortest distinguishing project path.
4. **Unified task index:** Build the control-room task collection from every discovered ledger and retain each task's source ledger path, card ID, zone ID, status, waiting-entry time, and manual queue rank.
5. **Direct navigation:** Opening a master task or subtask resolves its source ledger first, then opens the exact card without requiring the operator to switch servers.
6. **Refresh behavior:** Refresh discovery when the server starts and when ledger files are added, removed, or renamed under the configured root.
7. **Unavailable source:** If a queued task's ledger becomes unavailable, keep the task visible with an `Unavailable ledger` state and disable navigation until discovery resolves it.

---

## F. Task and Status Model

1. **Master-task marker:** A master card carries an explicit master-task type and owns the ordered list of linked subtask card IDs.
2. **Subtask relationship:** Every subtask stores the master-card ID and shares the master card's zone ID.
3. **Queue eligibility:** A master task appears in `Queue` when it has work waiting for operator treatment and no active processing state supersedes that wait.
4. **Active eligibility:** A master task appears in `Active` when Codex is processing its intake or at least one linked subtask has an active status.
5. **Done eligibility:** A master task appears in `Done` when all linked subtasks have a completed status.
6. **Progress derivation:** Derive aggregate progress from linked subtask statuses; do not maintain a second manually edited progress value.
7. **Waiting timestamp:** Record the timestamp at which the master task enters the waiting state. Preserve it across server restarts and use it for default `FIFO` ordering.
8. **Manual rank:** Persist operator reordering separately from the waiting timestamp so removing a manual priority restores deterministic `FIFO` behavior.

## G. Acceptance Criteria

1. **Main page:** Opening Decision OS displays the control room and selects the `Queue` tab on mobile.
2. **Oldest first:** With three untouched waiting tasks, their visible order matches ascending waiting-entry timestamps.
3. **Persistent reorder:** Dragging the third waiting task to first place preserves that order after a reload and does not alter its creation or waiting timestamp.
4. **Master drill-down:** Expanding a master task displays every linked subtask with its current status.
5. **Direct subtask access:** Selecting a subtask opens its exact card in the correct source ledger.
6. **Intake tools:** `New task` opens a draft thread that accepts voice notes, file attachments, and text before Codex launches.
7. **Creation result:** A successful Codex launch creates one new zone, one master-task card, linked subtask cards, and navigates to the master card.
8. **No zone reuse:** Task creation never places the new master task in a pre-existing zone.
9. **Dynamic filters:** Adding a discoverable ledger makes its filter chip appear without deploying another Decision OS server.
10. **Cross-ledger routing:** Two tasks from ledgers in different subdirectories can be listed together and each opens in its own source ledger.
11. **Name collision:** Two ledgers with the same name receive distinct filter labels and route to their correct canonical paths.
12. **Failure safety:** Retrying a failed launch does not duplicate the task's zone or master card and does not discard intake messages or attachments.
