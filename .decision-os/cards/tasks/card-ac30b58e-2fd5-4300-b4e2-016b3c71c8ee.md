## A. Required Change

1. Extend `parseMasterTaskMarkdown` in `frontend/src/app/responsive/control-room.js` to expose the single parent master task for a card whose JSON labels contain `subtask`.
2. Resolve the parent only from a canonical relationship with `label === 'subtask'`, `to === childCardId`, and a source card labeled `master-task`.
3. Add a pure destination resolver in `frontend/src/app/responsive/navigation-ownership.js` that returns the canonical parent card route using the parent card's containing zone.
4. Update `renderCard` and the `.back-to-zone-button` handler in `frontend/src/app/responsive/application.js` to consume the resolved destination instead of the literal `zone` fallback.

---

## B. Engineering Constraints

1. **Canonical ownership:** the relationship graph owns task ancestry; Markdown links, browser history, DOM ancestry, and button text must not infer it.
2. **Determinism:** reject ambiguous ancestry in the presentation diagnostics when more than one valid master source targets the same child.
3. **Route fidelity:** preserve `projectId`, replica query state, ledger ID, the parent's zone ID, and parent card ID.
4. **Fallback:** a non-subtask card retains its existing zone destination; an invalid labeled subtask exposes a diagnostic and uses the verified containing zone.

---

## C. Completion Checks

1. Unit coverage proves valid reverse ancestry, missing source card, invalid source label, and ambiguous parent relationships.
2. Integration coverage proves `renderCard` does not write `dataset.destination` and the click handler consumes the resolved immutable destination.
3. A browser scenario opens a master task, opens its relationship-backed subtask, clicks Back, and observes the parent master-task route and title.

---

1. **None.** This is the root defect and the first implementation task.
