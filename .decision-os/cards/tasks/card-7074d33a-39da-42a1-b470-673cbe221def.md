## B. Verified Current Lifecycle

1. **Capture and upload:** `stopVoiceRecording` creates a WAV blob, then `requestTranscription` adds an optimistic `uploading` note and posts the audio plus `ledgerId`, `threadId`, `cardId`, and `noteId` to `POST /api/voice-upload`.
2. **Server acceptance:** `startVoiceUploadOrchestrationController` writes the audio synchronously, persists the note as `transcribing`, publishes a scoped `card-content-change` SSE event, starts the OpenAI request asynchronously, and returns `202`.
3. **Browser acceptance:** After `202`, `requestTranscription` patches the note to `transcribing`, immediately resets the recorder-level status to `idle`, and performs one thread-slice fetch through `reconcileAcceptedVoiceNote`.
4. **Server completion:** The server replaces the note body and status with `transcribed` or `transcription failed`, persists the thread Markdown, and publishes another scoped SSE event.
5. **Browser completion:** `subscribeLedgerContentEvents` is the only continuous completion signal. It refreshes the active thread slice when the completion SSE arrives. There is no per-note completion poll, SSE replay, `online` catch-up, visibility catch-up, or focus catch-up.
6. **Local timeout:** `expireStaleVoiceTranscription` changes browser memory to `transcription failed` after `30_000ms`; it does not persist that failure, query server truth, or abort the provider request.

## C. Evidence and Root Findings

1. **Contradicted states:** The attached mobile screenshot shows `Voice uploaded.` with `TRANSCRIBING`, while the corresponding durable thread note becomes `transcribed` after reload. This proves persistence can finish without the open browser applying the terminal state.
2. **Synchronization gap:** The post-acceptance fetch can legitimately observe the intermediate `transcribing` state. After that fetch, a missed SSE event leaves the browser stranded because no second authoritative read is scheduled.
3. **Non-recovering stream:** `/api/ledger-content-events` sends no event IDs, replay buffer, heartbeat, or reconnect reconciliation. `events.onerror` records telemetry only. Native EventSource reconnection therefore cannot recover an event emitted during disconnection.
4. **False local authority:** The `30s` browser timeout can report failure while the server request remains active and may later persist success. The timeout is not a durable terminal transition and creates two competing owners of status.
5. **Missing progress model:** The durable note exposes only `transcribing` between acceptance and completion. The UI shows a raw status string without elapsed time, provider phase, finalization phase, expected recovery action, or confirmed server freshness.
6. **Unattributed delay:** The two voice files in this thread were persisted at `2026-07-13T05:34:13.383Z` and `2026-07-13T05:34:59.219Z`; their persisted `transcriptionStartedAt` values are `2026-07-13T05:34:45.543Z` and `2026-07-13T05:36:09.650Z`. The observed gaps are about `32.16s` and `70.43s`, but current telemetry has no phase timestamps capable of locating that time inside encoding, upload parsing, file persistence, ledger persistence, provider dispatch, or provider response.
7. **Coverage gap:** Existing tests cover upload acceptance, scoped SSE refresh, and a synthetic `30s` expiry. They do not cover a missed completion event, stream reconnection, completion after the local timeout, foreground recovery, elapsed phase rendering, or a terminal state surviving reload.
8. **Served target:** The existing server process serves `HEAD /specs` with `200` on port `50150`; it was inspected without a restart.

## D. Selected Repair Contract

1. **Single authority:** The server owns every durable voice lifecycle transition and deadline. The browser renders server state and may show an optimistic upload phase only until the `202` response supplies the persisted note identity and timestamps.
2. **Explicit phases:** Persist `uploading`, `queued`, `transcribing`, `finalizing`, `transcribed`, and `transcription failed` with phase timestamps and one stable note revision.
3. **Narrow reconciliation:** Add a note-scoped status read for `ledgerId`, `threadId`, and `noteId`. Keep scoped SSE as the fast path, then poll only non-terminal voice notes and reconcile immediately on EventSource recovery, `online`, and return to visible state.
4. **Server deadline:** Replace the browser-only `30s` mutation with a server-side `120_000ms` provider deadline enforced with `AbortController`; persist the resulting terminal failure and retain `voiceFileRef` for retry.
5. **Progress UI:** Render a human label, elapsed time, and current phase inside each voice note. Do not show a fabricated percentage because the transcription provider returns no intermediate completion percentage.
6. **Ordering:** A server note with a newer revision always replaces optimistic fields for the same `noteId`; stale fetches and stale SSE payloads cannot regress a terminal note to a busy phase.
7. **Live display clock:** Derive elapsed time from the server phase timestamp, then update the visible label locally every `1_000ms` between reconciliation reads. Maintain one shared interval, query current DOM nodes on every tick, and stop when no pending voice phase remains.

---

## E. Acceptance Criteria

1. **Missed-event recovery:** If the completion SSE is dropped, the visible note reaches the persisted terminal state without a page reload.
2. **Foreground recovery:** A note completed while Brave is backgrounded reconciles immediately when the page becomes visible.
3. **Honest progress:** The note displays its exact server-owned phase and elapsed time, with no false percentage and no recorder-level `idle` message competing with note progress.
4. **Durable timeout:** A provider deadline produces one persisted failure, retains retryable audio, and survives a fresh reload.
5. **No stale regression:** Late intermediate responses cannot replace `transcribed` or `transcription failed` with `transcribing`.
6. **Latency evidence:** Telemetry records timestamps for capture completion, upload receipt, audio persistence, note acceptance, provider dispatch, provider settlement, thread persistence, event publication, and browser reconciliation.
7. **Target verification:** On the served mobile Brave route, observe the optimistic UI before the upload response, successful terminal persistence after reload, and failed-request reconciliation to server-confirmed state.
