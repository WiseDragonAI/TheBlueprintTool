#master-task

Ledger: Specs

## A. Scope

1. **Mobile bottom action:** Fix the thread control that scrolls the conversation to its bottom on mobile.
2. **Follow-bottom activation:** When the operator presses that control, mark the thread as following the bottom.
3. **Persistent following:** While follow-bottom is active, keep the conversation pinned to the bottom whenever new thread input is rendered.
4. **Distinct behaviors:** Treat the immediate button-driven scroll and subsequent input-driven bottom following as separate requirements.

---

## C. Findings

1. **One-off action only:** `frontend/src/runtime/input/controller/handle-action-click.ts` calls `pinThreadFeedToLastMessage()` for `jump-thread-bottom` but does not persist a follow-bottom mode for the active thread.
2. **Render restores stale position:** `frontend/src/runtime/thread/effect/render-thread-panel.ts` saves the current conversation offset before rendering and restores it afterward unless `threadPinOnRender` is set. New optimistic inputs therefore remain at the previous offset.
3. **Mobile viewport contract:** The rendered mobile conversation scroll owner is `.thread-conversation-scroll`; the regression test must exercise this primary selector instead of only the legacy `.chat` fallback.

---

## D. Implementation Plan

1. **State contract:** Add a per-thread `threadFollowBottomByThreadId` record to runtime state.
2. **Action contract:** On `jump-thread-bottom`, enable follow-bottom for the active thread and immediately pin `.thread-conversation-scroll`.
3. **Render contract:** When follow-bottom is enabled for the active thread, bypass saved-offset restoration and pin again after thread notes render and browser layout settles.
4. **User-scroll contract:** Disable follow-bottom when the operator intentionally scrolls the conversation away from the bottom, preserving normal manual navigation.
5. **Verification:** Add integration coverage for the primary mobile scroll element, activation from the jump action, continued pinning after new input renders, and cancellation after manual upward scrolling.

---

## E. Acceptance Criteria

1. **Mobile jump:** Pressing the visible thread bottom button moves `.thread-conversation-scroll` to its bottom.
2. **Follow activation:** Pressing the button sets follow-bottom for the active thread.
3. **New inputs:** Subsequent thread note renders keep the viewport at the bottom while follow-bottom remains active.
4. **Manual escape:** Scrolling more than `72px` away from the bottom disables follow-bottom for that thread.
5. **Regression gate:** Focused frontend integration tests and TypeScript type checking pass.

## G. Mobile Reproduction Finding

1. **Root cause:** `frontend-mobile/src/mobile-thread.js` owns mobile thread clicks and does not route `jump-thread-bottom`; its delegated handler silently ignores the button.
2. **Deployment state:** Merge commit `73911fb` is present on `main`, and the running server on port `50150` serves frontend source with `cache-control: no-store`. A server restart cannot correct the missing mobile route.
3. **Coverage gap:** The first regression covered the shared canvas action controller and the primary scroll selector, but did not exercise the separate mobile click dispatcher.

---

## H. Corrective Plan

1. **Mobile routing:** Import the shared pin effect into `frontend-mobile/src/mobile-thread.js` and route `jump-thread-bottom` to `pinThreadFeedToLastMessage({ follow: true })`.
2. **Mobile regression:** Extend `frontend-mobile/test/mobile-thread.test.mjs` to require this exact action route.
3. **Verification:** Run the mobile test suite, focused shared thread integration tests, and frontend TypeScript checking before merging the correction into `main`.
