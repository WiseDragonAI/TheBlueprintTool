2. **Confirmation:** Add a focused confirmation controller that configures the shared modal with the session warning and routes confirmation through `frontend/src/runtime/input/controller/handle-action-click.ts`.

## B. Interaction Contract

1. **Availability:** Keep the delete control actionable in `running`, `complete`, `failed`, `cancelled`, and `unavailable` states; disable only the confirmation action while its deletion request is pending.
2. **Success reconciliation:** Clear thread-scoped run summaries, events, announcements, scroll state, disclosure state, and stop state for the deleted run; refresh canonical ledger state and rerender the Codex Log as empty with `START`.
3. **Failure reconciliation:** Close the pending state, retain the run log and ownership, and render an inline error with no optimistic removal.
4. **Accessibility:** Provide an explicit accessible name, focus the destructive modal action, return focus safely after cancellation, and keep the control reachable at the end of keyboard traversal.
5. **Styling:** Reuse the established destructive terminal-button and shared modal visual language; keep the action visually separated from chronological events at the bottom of the independent log scroller.

## C. Acceptance Criteria

1. **Rendering tests:** Assert the action follows the stream, appears for every owned-run status, and is absent when the card has no run id.
2. **Routing tests:** Assert modal cancel is non-mutating and confirm submits the exact ledger, card, and run identity once.
3. **State tests:** Assert success produces empty/`START`, failure preserves the current log with an inline error, and a repeated render does not restore deleted cached events.
