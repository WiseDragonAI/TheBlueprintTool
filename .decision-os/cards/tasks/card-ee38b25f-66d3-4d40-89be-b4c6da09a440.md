#master-task

Ledger: Specs
Queue rank: 1

## A. Scope

1. **Objective:** Make task reordering in the mobile Control Room queue respond continuously during drag and persist the final `Queue rank` order optimistically.
2. **Surface:** Change the queue implementation in `frontend-mobile/src/mobile.js`, its presentation in `frontend-mobile/assets/mobile.css`, and focused coverage under `frontend-mobile/test/`.
3. **Lifecycle:** Keep this master task at `#task-active` until every linked subtask has ledger status `done` and every acceptance criterion passes.

---

## B. Verified Current Behavior

1. **Drag feedback:** Queue rows only add the `drag-target` class while the pointer crosses a row; the DOM order does not change during the gesture.
2. **Persistence gate:** `moveTask()` waits for all `patch-card` mutations, then waits for `loadControlRoom()`, and only then calls `renderControlRoom()`.
3. **Persisted contract:** Queue order is encoded as `Queue rank: <positive integer>` in each master task Markdown body through `withQueueRank()`.

---

## C. Requirements

1. **Live movement:** Reorder the visible queue model and rows as the dragged task crosses insertion positions, for both fine-pointer native drag and touch pointer gestures.
2. **Animation:** Animate displaced rows from their previous positions to their new positions without delaying pointer handling.
3. **Optimistic state:** Render the final order immediately and update the in-memory task Markdown and `queueRank` values before network persistence completes.
4. **Persistence:** Persist the normalized ranks for the reordered visible queue without forcing a blocking full control-room reload on the success path.
5. **Failure reconciliation:** On any failed rank mutation, restore a server-confirmed queue state and expose the existing request failure through the application error path.
6. **Interaction safety:** Preserve direct task navigation, queue filtering, the `next-task` marker, and scroll-anchor behavior while delegating the gesture lifecycle to vendored `SortableJS 1.15.7`.

---

## D. Acceptance Criteria

1. **Continuous reorder:** During a drag, crossing a queue row immediately moves the dragged row to that insertion position and animates every displaced row.
2. **Immediate drop result:** Releasing the drag leaves the queue in its new visual order without waiting for a server response.
3. **Successful persistence:** After all rank mutations succeed, the optimistic order remains visible and the persisted Markdown contains contiguous `Queue rank` values beginning at `1` for the reordered visible queue.
4. **Failed persistence:** A rejected mutation reloads server-confirmed state, removes transient drag styling, and does not leave stale optimistic ranks in memory.
5. **Regression coverage:** Automated tests verify the vendored `SortableJS 1.15.7` touch fallback contract, optimistic success, persistence failure reconciliation, filtering, and rank normalization.

---

## E. Root Cause and Decision

1. **Observed failure:** The screenshot attached in the card thread shows the custom floating card and placeholder simultaneously active after the touch gesture stopped progressing.
2. **Root cause:** The custom implementation captured the pointer on a queue card, then removed and reparented that captured element to `document.body`; the mobile browser cancelled the subsequent pointer stream and left the custom floating and placeholder state uncleared.
3. **Structural correction:** Remove the hand-written pointer capture, reparenting, placeholder, midpoint, and cancellation state machine.
4. **Library decision:** Vendor `SortableJS 1.15.7` with its MIT license and configure `forceFallback: true`, `fallbackOnBody: true`, `fallbackTolerance: 4`, `delay: 300`, `delayOnTouchOnly: true`, `touchStartThreshold: 8`, and `animation: 180`.
5. **Persistence boundary:** Read the library-owned DOM order in `onEnd`, update the queue model immediately, then schedule optimistic rank persistence in a microtask after SortableJS completes its drop cleanup.
