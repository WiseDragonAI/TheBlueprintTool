## B. Verified Root Cause

1. The Control Room ETag hashed replica content revisions but omitted owner presence, so online-state changes could return `304` for a changed response.
2. The 15-second maintenance timer re-enqueued every remote project even when its replica was current, making healthy cards repeatedly show `synchronizing`.
3. One serial worker handled every project for a node, so one slow request blocked all later project replicas.

---

## C. Synchronization Correction

1. Bind the federated projection fingerprint to project owner presence and replica content.
2. Preserve current hash-confirmed replicas during periodic maintenance and retry only missing or already-pending work.
3. Refresh project replicas independently so a slow project cannot block every card on the node.
4. Send the current SHA-256 replica revision and accept HTTP `304` confirmation without retransmitting an unchanged snapshot.
