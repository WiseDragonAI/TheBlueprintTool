## A. Root cause

1. **First incorrect transition:** `projectContext()` registers one project and immediately calls `resumeCodexPipelineRuns()`. The first empty project starts a shared global schedule that reaches no candidate and resolves before later project contexts are registered.
2. **Lost wake-up:** Later startup calls see `runtime.globalCodexSchedulePromise` and reuse that already-resolved promise. Their persisted `pending` items are never scanned after their contexts enter `projectContexts`.
3. **Visible result:** Durable items remain `pending`, so the Control Room continues to display queue positions even though no Codex child process owns them.

---

## B. Regression evidence

1. **Reproduction:** `backend/test/codex/codex-process-restart-recovery.test.ts` starts a catalog with an empty project followed by a project containing one durable pending thread run.
2. **Pre-fix result:** The test times out waiting for the fake Codex invocation after `3` seconds.
3. **Boundary proven:** The queued project is discovered and its durable queue file remains readable; the missing transition is the shared scheduler wake-up after project registration.
