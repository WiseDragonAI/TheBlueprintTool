## A. Ranked trends

1. **State, lifecycle, and ownership consistency — 11 lessons, 36.7%.** The largest cluster says workflow defects arise when logical state is represented differently across the UI, hydration, polling, routing context, generated cards, event publication, timers, and the master gate. Supporting lessons: `Review stateful UI through post-action hydration`; `Use the exact complete master projection literal`; `Recheck runtime blockers during repeated closeout`; `Project shared run ownership onto the user-selected card`; `Treat generated pipeline results as master-gate dependencies`; `Persist workflow state at the mutation boundary`; `Enumerate every consumer of shared run ownership`; `Hydrate parent context on direct routes`; `Reconcile terminal protocol events with wrapper lifetime`; `Publish ledger refresh events for every ordinary settlement`; `Anchor UI timers to the logical lifecycle`. **Implication:** define one authoritative lifecycle, project it deliberately to every consumer, and test each transition through terminal settlement.
2. **Verification at the real execution boundary — 7 lessons, 23.3%.** Tests produced false confidence when they exercised the primary checkout instead of the worktree, the wrong TSX aliases, backing values instead of visible controls, stale process state, only one server layer, or static inspection instead of the actual gesture. Supporting lessons: `Verify patch destination in isolated worktrees`; `Pin TSX tsconfig when testing a linked worktree`; `Round-trip ledger Markdown after scripted mutation`; `Verify frontend and backend runtime freshness separately`; `Recheck volatile runtime state before reporting it`; `Verify visible hydration state`; `Require target gestures for interaction claims`. **Implication:** every success claim needs evidence from the same artifact, runtime layer, rendered state, and interaction path the operator will observe.
3. **Preserve authoritative boundaries and complete contracts — 7 lessons, 23.3%.** Correct changes preserve transactional ownership, file modes, persisted per-object values, semantic control colors, validated component boundaries, reference styling, and usable defaults. Supporting lessons: `Provision server-owned registries inside the first write transaction`; `Preserve file modes when synchronizing executable skill resources`; `Match the full styling boundary of named reference components`; `Keep persisted zone colors authoritative`; `Keep dedicated control colors outside theme inheritance`; `Preserve validated components during behavior fixes`; `Initialize visual controls to usable state`. **Implication:** identify the authority and the full component or persistence contract before editing, then change the smallest responsible boundary.
4. **Operator intent and governance are executable requirements — 5 lessons, 16.7%.** Card hierarchy, concise positive instructions, closeout authority, skill dependencies, and approval timing directly determine whether work is usable and legitimate. Supporting lessons: `Keep master task cards as operator summaries`; `Use positive workflow instructions instead of anti-prompts`; `Map closeout authorization directly to the atomic command`; `Plan runtime dependencies with skill contracts`; `Install the exact operator-approved artifact`. **Implication:** encode operator intent in the task structure and atomic commands; do not invent gates, install before approval, or bury the decision under implementation detail.

## B. Cross-cutting conclusion

1. **The dominant pattern is incomplete end-to-end propagation.** Most failures were not isolated algorithm errors; they were mismatches between authoritative state and one downstream projection, consumer, runtime layer, rendered control, or lifecycle transition.
2. **The recurring correction is boundary-first verification.** The lessons repeatedly converge on locating the authoritative mutation or state boundary, enumerating its consumers, preserving validated contracts, and proving the operator-visible result on the served target.
3. **Recommended default for subsequent work:** map `authority → mutation → consumers → rendered state → persistence → terminal event`, then attach one verification item to each link before claiming completion.
