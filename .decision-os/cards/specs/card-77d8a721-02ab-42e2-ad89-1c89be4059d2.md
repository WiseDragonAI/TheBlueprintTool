## A. Selected Cloudflare Transport

1. **Relay runtime:** Use one Cloudflare Worker and one SQLite-backed Durable Object per federation. A stateless Worker cannot coordinate the two long-lived node connections; the Durable Object is the authoritative socket router.
2. **Connection model:** Each Decision OS server opens one outbound `WSS` connection on port `443`. The Worker forwards the upgrade to the Durable Object, which accepts both connections with `acceptWebSocket()` so they remain hibernatable.
3. **Node client:** Keep pinned `ws@8.21.0`, MIT, through npm in each Decision OS server. The Cloudflare relay uses the platform WebSocket API and does not ship the `ws` server library.
4. **Socket identity:** Tag each accepted socket with its `nodeId` and serialize attachment metadata containing `nodeId`, credential version, and connection epoch. Store larger manifests in SQLite because an attachment is limited to `16,384` bytes.

---

## B. Version 1 Frames

1. **Session:** `hello`, `hello.accepted`, `manifest.replace`, `presence.changed`, and `error` are JSON control frames.
2. **Request:** `request.open` carries `requestId`, target global project key, method, path, query, and allowlisted headers. `request.data` carries ordered binary chunks; `request.end` closes the body; `request.cancel` aborts the owner request.
3. **Response:** `response.open` carries status and allowlisted headers. `response.data` carries ordered binary chunks. `response.end` carries the terminal result.
4. **Flow control:** `flow.window` grants bytes for one request direction. A sender transmits data only within the receiver's granted window; the receiver grants replacement credit only after its local sink accepts the bytes.
5. **Live events:** SSE uses the same response state machine with an open-ended body. Browser disconnect produces `request.cancel`; reconnect creates a new request and refreshes authoritative state.

---

## C. Ordering and Backpressure

1. **Identity:** Generate a UUID `requestId` at the requester. Reject a duplicate active ID and retain terminal mutation metadata for `10 min`.
2. **Ordering:** Sequence chunks per request and reject gaps, repeats, data after end, and terminal frames before open.
3. **Chunking:** Keep `64 KiB` binary chunks, far below Cloudflare's `32 MiB` received-message limit, and interleave active streams.
4. **Credit:** Start each direction with a `1 MiB` window. Track outstanding bytes in the Durable Object and close the offending request at `4 MiB`; do not depend on an unavailable relay-side `bufferedAmount`.
5. **Admission:** Allow at most `32` simultaneous remote streams per node and reject excess work with `503 federation_capacity`.

---

## D. Recovery and Hibernation

1. **Liveness:** Use WebSocket protocol ping from each Node connector. Cloudflare automatically replies with pong without waking the Durable Object. Do not run Durable Object timers or application heartbeat handlers while idle.
2. **Reconnect:** Retry with jittered exponential delay from `1 s` to `30 s`; publish a full manifest after authentication.
3. **Safe replay:** Automatically recreate only `GET`, `HEAD`, and SSE subscriptions. Never automatically replay a mutation, upload, cancellation, or Codex launch after an ambiguous disconnect.
4. **Ambiguous mutation:** Return `502 federation_outcome_unknown`, refresh the authoritative ledger or run status after reconnection, and present the result before retry.
5. **Runtime replacement:** Treat Cloudflare runtime replacement as relay loss. Both nodes reconnect, replace manifests, and reconstruct routing from socket attachments plus SQLite state.
