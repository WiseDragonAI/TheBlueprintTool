## A. Corrected decision

1. **Use the existing JSON card model as the complete machine-readable master-task model:** `cards[].labels` classifies cards, `cards[].status` stores completion, and `relationships[label=subtask]` binds each subtask to its master.
2. **Set the canonical labels to `master-task` and `subtask`.** `labels` is the persisted field already supported by `ledger-cli mutate --card-labels`; the frontend accepts `tags` only as a compatibility alias.
3. **Remove master-task classification and status from Markdown parsing.** Markdown retains operator-facing content, lifecycle timestamps, and generated navigation links during compatibility migration.
4. **Do not restore the reverted structured-task fields.** `cardType: master-task`, `taskState`, task timestamps, queue rank, and `subtaskIds` duplicate existing card status, labels, runtime state, and relationships.
5. **Add one atomic `master-task-progress` command** that writes study or implementation content, applies canonical labels, marks verified subtasks, appends the thread answer, and returns the gate result.

---

## B. Verified current model

1. **Label storage exists:** cards persist a `labels` string array in ledger JSON; `ledger-cli mutate` exposes `--card-labels`.
2. **Compatibility alias exists:** the frontend reads `card.labels`, falling back to `card.tags`; new writes use `labels`.
3. **Current semantic boundary is narrower:** the existing label specification calls labels decorative metadata, so using them for task classification requires updating that contract.
4. **Master-task code has not adopted labels:** Control Room projection and validation parse `#master-task` and `#task-*` from Markdown.
5. **Status already belongs to JSON:** subtask and master completion persist in `cards[].status`; Control Room derives visible waiting, active, and complete state from JSON plus live run state.
6. **Membership already belongs to relationships:** direct `label: subtask` relationships identify the canonical children of a master. A `subtask` card label alone cannot identify its parent.

---

## C. Current reliability gap

1. **`ledger-cli done` updates only JSON.** It cannot update the `— Status:` suffix generated in the master Markdown.
2. **`master-task-gate` treats the Markdown suffix as a required projection.** A correct JSON update is rejected as `stale_subtask_projection` until an agent rewrites the master body.
3. **The injected instruction says “sync projections,” but no such CLI command exists.** Agents fall back to whole-card `mutate`, which cannot bind content, labels, status, thread, and gate checks into one transaction.
4. **Master classification remains duplicated.** The JSON label facility exists, but current master-task discovery reads the Markdown `#master-task` marker instead.

## D. Six-session evidence

1. **Selection:** the six newest prior run JSONL files were selected by `codex-run-audit`, excluding the active study run.
2. **Aggregate:** `94` completed shell calls, `65` `ledger-cli` invocations, and `5` failed shell calls.
3. **Highest-cost run:** a seven-subtask study used `9` generic content mutations, `7` real `done` writes, `2` validations, `3` gates, and `1` answer: `22` lifecycle/write calls.
4. **Manual duplicate:** that run embedded seven `Status: complete` values into the master Markdown in addition to setting the seven JSON statuses.
5. **Closeout pattern:** three authorized retrospective runs ultimately needed one `master-task-complete` each but used `5`, `6`, and `12` total CLI invocations because of help, repeated context reads, and gates around the transaction.

## E. Minimal implementation contract

1. **Classification source:** `cards[].labels` contains `master-task` on a master and `subtask` on each child.
2. **Status source:** `cards[].status` remains the only persisted completion status.
3. **Membership source:** existing `label: subtask` relationships define the canonical master-to-child set.
4. **Invariant:** every relationship child has the `subtask` label; every master endpoint has the `master-task` label. The relationship remains authoritative when a label and relationship disagree.
5. **Markdown boundary:** stop generating and validating `#master-task`, `#task-*`, and `— Status:` tokens; ignore legacy tokens during compatibility reads.
6. **Progress command:** `ledger-cli master-task-progress --ledger "$DECISION_OS_LEDGER_FILE" --plan-stdin --json` accepts structured card updates, verified subtask IDs, canonical label updates, and one agent reply.
7. **Atomic result:** the command preflights every ID, label, and relationship, snapshots all affected files, writes card bodies, updates JSON labels and statuses, regenerates links, appends the reply, rolls back on failure, and returns the post-write gate.
8. **Closure guard:** progress never completes the master; the explicitly authorized `master-task-complete` remains the only closeout command.

---

## F. Compatibility sequence

1. **First release:** make Control Room discovery, validation, and the gate read `cards[].labels`, `cards[].status`, and `subtask` relationships; accept legacy Markdown classification only for cards without JSON task labels.
2. **Template update:** make `master-task-apply` write `master-task` and `subtask` labels, generate canonical relationship-backed links without status suffixes, and update launch instructions to name the progress command.
3. **Touch migration:** add canonical JSON labels and strip legacy task tokens when a master is next applied, progressed, or completed; do not rewrite untouched cards in bulk.
4. **Completion update:** make `master-task-complete` validate JSON labels and relationships and return its post-transaction gate result.

---

## G. Expected simplification

1. **Representative reduction:** the observed `22` lifecycle/write calls become `1`, a `95%` reduction.
2. **Whole-run reduction:** with unrelated reads unchanged, the observed `28` CLI invocations become `7`, a `75%` reduction.
3. **Data-model impact:** no new status field, task type, or duplicated subtask array is required; the only semantic extension is promoting existing card labels from decorative metadata to task classification.

---

## H. Implementation acceptance

1. **JSON classification:** a card with the `master-task` label is discovered without a Markdown task marker.
2. **JSON authority:** a status change affects the gate and Control Room without a Markdown status edit.
3. **Relationship safety:** a `subtask` label without a canonical relationship does not attach a card to a master; mismatched relationship endpoints are diagnosed.
4. **Atomic rollback:** one invalid update leaves the ledger, all affected cards, and the thread byte-identical.
5. **Legacy safety:** stale legacy task tokens cannot block a valid JSON state.
6. **Command budget:** the seven-subtask progress fixture performs one CLI invocation and one ledger write.
7. **Authorization:** the progress transaction cannot set the master status to `done`.
