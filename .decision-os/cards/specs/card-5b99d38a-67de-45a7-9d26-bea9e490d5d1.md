## C. Behavioral Contract

1. **Placement:** Render `Delete session` after the Codex event stream so it is the final control at the bottom of the Codex Log.
2. **Availability:** Show the control whenever the selected card owns a `codexThreadRunId`; allow activation for `running`, `complete`, `failed`, `cancelled`, and `unavailable` log states.
3. **Confirmation:** Open the shared destructive-action modal and state that deletion stops an active run and permanently removes its context and log.
4. **Ownership:** Accept deletion only when `ledgerId`, `cardId`, and `runId` identify the same thread-owned run in the selected workspace ledger.
5. **Running deletion:** Send `SIGTERM` to a live server-owned child, wait for process settlement and stream closure, then perform cleanup so late close handlers cannot recreate deleted artifacts.
6. **Cleanup:** Remove the runtime run entry, `codexThreadRunId`, `codexThreadRunOutputFile`, and every file owned by that run beneath `.decision-os/runs/codex-skills/<ledger>/`; publish the ledger change after persistence succeeds.
7. **Fresh launch:** After successful deletion, clear the browser's cached log and stop state, refresh the ledger projection, show the empty Codex Log state, and expose `START`; the subsequent request must use the normal thread launch endpoint and `resolveCodexCommand`, never `codex resume`.
8. **Failure:** Preserve the existing session association and surface an inline error when ownership validation, cancellation, persistence, or artifact cleanup fails.

## D. Acceptance Criteria

1. **Terminal session:** Confirming deletion removes the owned run fields and files, and the old run status request no longer resolves as an owned run.
2. **Active session:** Confirming deletion stops the child before cleanup, leaves no active runtime entry, and does not recreate a summary or log after settlement.
3. **Isolation:** A mismatched ledger, card, or run id cannot stop a process, mutate a card, or delete files.
4. **Fresh context:** The first launch after deletion receives a newly generated run id and invokes a fresh Codex command without the deleted session id.
5. **UI:** The bottom action is available across every owned-run state, uses the shared confirmation modal, reports failure without clearing the visible session, and changes to the empty/`START` state only after success.
6. **Regression coverage:** Backend controller and HTTP-route tests cover terminal deletion, active deletion, isolation, cleanup failure, and fresh relaunch; frontend integration tests cover placement, modal routing, pending state, success reconciliation, and failure reconciliation.
7. **Target verification:** On the served operator-facing project route, verify the full confirmation and deletion flow for a terminal run and an active run with representative Chromium input; record the route, HTTP result, stop observation, cleared log, and newly generated run id after relaunch.
