## A. Contradicted Success RCA

1. **Observed state:** After the operator restart, the durable queue contained the pre-crash thread and continuation claims as `interrupted`; each record said the process was not relaunched.
2. **First incorrect transition:** `recoverCodexProcessQueue()` converted persisted `running` claims to `interrupted` during project-context startup.
3. **Dispatch boundary:** `nextPendingCodexProcessCreatedAt()` and `scheduleCodexProcesses()` select only `pending` records, so the interrupted claims could never re-enter processing.
4. **Regression gap:** The first correction tested a synthetic `pending` record discovered after an empty project. It did not exercise a record that had already transitioned to `running` before the crash.

---

## B. Corrected Recovery

1. **Claimed thread:** Startup projects the claim into a `continuation` with the original run ID and returns it to `pending` FIFO scheduling.
2. **Claimed continuation:** Startup preserves its durable run identity and returns it to `pending` scheduling.
3. **Session behavior:** Recovery uses `codex exec resume` when the JSONL contains a Codex session ID. If the crash occurred before session capture, the continuation controller reconstructs a new session from durable card context.
