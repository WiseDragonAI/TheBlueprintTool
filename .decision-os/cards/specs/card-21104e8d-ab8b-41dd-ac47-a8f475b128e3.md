## A. Projection Responsibility

1. **Goal:** Build the reusable server projection store and serve `GET /api/control-room` without full-ledger hydration.
2. **Authoritative inputs:** Read project metadata, `state.json`, declared ledger JSON, master-task card Markdown, relevant master-thread metadata, linked subtask ledger statuses, compact run summaries, and pipeline lifecycle revisions.
3. **Storage boundary:** Keep ledger JSON and Markdown authoritative. Persist only disposable projection snapshots at `.decision-os/cache/control-room-v1.json`; do not add SQLite.
4. **Measured baseline:** The previous Control Room path transferred approximately `7.15 MB` of hydrated ledger JSON plus `10.47 MB` of run responses for roughly `42` master tasks.

---

## B. Control Room Read Model

1. **Response envelope:** Return `schemaVersion`, `projectorVersion`, aggregate `revision`, `generatedAt`, `stale`, project summaries, task collections, and diagnostics.
2. **Collections:** Return `queue`, `active`, `backlog`, and `done` from one validated aggregate.
3. **Task identity:** Include `projectId`, project name and color, `ledgerId`, ledger title, `cardId`, title, canonical navigation identity, and persisted card status.
4. **Task state:** Include derived lifecycle, queue rank, waiting timestamp, active timestamp, completion timestamp, compact run id and status, queue position, and processing state.
5. **Subtasks:** Include canonical linked card ids, ledger-backed statuses, completed count, total count, and next incomplete subtask.
6. **Diagnostics:** Preserve missing `#master-task`, invalid lifecycle label count, missing ledger, invalid timestamps, invalid queue rank, and unresolved canonical subtask links.
7. **Parsing boundary:** Parse master-task Markdown and thread timestamps on the server. The browser receives no master-task Markdown for classification.

---

## C. Immutable Cache Lifecycle

1. **Key:** Key snapshots by `projectId`, projection kind, and resource id; key the global aggregate by its ordered project-slice revisions.
2. **Manifest:** Store schema version, projector version, generation timestamp, canonical dependency paths, byte size, nanosecond modification time, `SHA-256` file hashes, and monotonic runtime revision tokens.
3. **Fingerprint:** Hash the projection key, schema version, projector version, sorted file hashes, and sorted runtime tokens.
4. **Hot read:** Serve a `ready` in-memory snapshot with zero source-file reads and zero hash computations.
5. **Invalidation:** Use reverse dependency indexes to mark exact snapshots `dirty` and deduplicate concurrent rebuilds.
6. **Rebuild:** Build a complete replacement from one coherent source read, validate its schema, then atomically swap memory state and rename the disk snapshot.
7. **Concurrent request:** Serve the previous immutable revision with `stale: true` while a replacement builds.
8. **Failure:** Keep the last valid revision, record the failing dependency and error, and retry on the next event and reconciliation pass.
9. **Warm start:** Accept a disk snapshot only when dependency hashes, runtime tokens, schema version, projector version, and projection fingerprint match.
10. **Cold start:** Wait for the first valid build before returning `stale: false` state.

---

## D. Watchers And Multi-Project Lifecycle

1. **Catalog supervisor:** Discover every `.decision-os` project below the launch root before the global projection becomes ready.
2. **Project context:** Maintain independent revisions, dependency indexes, watchers, pending builds, and projections per stable `projectId` and canonical `.decision-os` path.
3. **Coverage:** Observe `state.json`, declared ledger files, referenced card files, referenced thread files, project identity and metadata, and persisted runtime dependencies consumed by projections.
4. **Runtime events:** Invalidate run dependencies directly from skill-run and pipeline-run lifecycle callbacks.
5. **Added project:** Attach watchers, build its initial slice, then advance catalog and aggregate revisions without waiting for a scoped request.
6. **Removed project:** Close watchers, cancel pending builds, remove memory and disk slices, then advance catalog and aggregate revisions.
7. **Moved project:** Preserve `.decision-os/project.json` identity, close old-path watchers, attach the new path, and rebuild before marking the slice ready.
8. **Isolation:** Prevent identical ledger, card, and thread ids in separate projects from sharing dependency keys.
9. **Reconciliation:** Every `30 seconds`, diff the project catalog and compare dependency stat tuples; hash changed candidates and rebuild mismatches.
10. **Shutdown:** Close every watcher, timer, event client, and pending build without leaving project contexts alive.

---

## E. Endpoint, Events, And Observability

1. **Read route:** Add global `GET /api/control-room`; project and ledger filtering remains a presentation operation over the compact aggregate.
2. **Revision stream:** Extend `/api/control-room-events` with one event containing aggregate revision and affected project ids after a successful swap.
3. **Request contract:** Support conditional revision reads so an unchanged client receives a bodyless response.
4. **Metrics:** Record build duration, source counts, response bytes, warm hits, cold builds, stale hits, invalidation reason, reconciliation repairs, failed builds, and active watcher count.
5. **Path safety:** Resolve every manifest dependency below its owning canonical `.decision-os` root and reject ambiguous ownership.

---

## F. Verification Gates

1. **Performance:** Warm server response remains below `100 ms`; measured payload remains below `250 KB`.
2. **Correctness:** Automated coverage proves queue ordering, timestamps, active status, backlog, completion, subtask progress, malformed diagnostics, and navigation identity.
3. **Invalidation:** Card Markdown, thread Markdown, ledger status, project metadata, run lifecycle, pipeline lifecycle, schema changes, and projector changes invalidate the correct slice.
4. **Recovery:** A deliberately suppressed watcher event is repaired by the next `30-second` reconciliation.
5. **Concurrency:** Parallel invalidations produce one build, readers see one complete revision, and failed publication never replaces good state.
6. **Multi-project:** Automated tests add, remove, and move projects after startup, verify duplicate-id isolation, and verify watcher cleanup.
7. **Traffic:** Control Room requests perform no universal ledger hydration and return no run event history.
