## A. Implemented policy

1. **A running thread or continuation claim is never converted back to `pending` during server startup.**
2. Startup persists the claim as `interrupted`, preserves `startedAt`, and records `interruptedAt` plus the exact reason: `Decision OS server restarted while this Codex process was running. The process was not relaunched.`
3. Pending work remains pending and keeps normal FIFO scheduling.
4. Pipeline recovery already marks an unowned running skill failed and does not relaunch that skill.

---

## B. Status recovery

1. `readCardSkillRunController` maps a recovered `interrupted` queue claim to public status `failed`, `active: false`, `queuePosition: null`, and returns the persisted restart-interruption reason.
2. Persisted terminal evidence still wins: a recorded `complete`, `failed`, or `cancelled` event remains authoritative.
3. Interrupted claims are excluded from queue position, scheduler selection, queued run IDs, and capacity launches.
