## A. Corrected selected contract

1. **Use `cards[].labels` for task classification.** A master has `master-task`; every child has `subtask`. New writes use the canonical `labels` field, not the frontend compatibility alias `tags`.
2. **Keep `cards[].status` authoritative for completion.** No new task-state field is required.
3. **Use existing `label: subtask` relationships as authoritative master-to-subtask membership.** Labels classify cards; relationships identify the parent and child set.
4. **Derive visible master waiting, active, and complete state from `cards[].status`, live queue state, and live process state.**
5. **Stop writing and validating Markdown task tokens.** Legacy `#master-task`, `#task-*`, and `— Status:` tokens remain readable during migration but never override JSON labels, JSON status, or relationships.

---

## B. Verified label boundary

1. **Persistence:** ledger cards already accept a JSON `labels` string array.
2. **CLI:** `ledger-cli mutate --card-labels <labels>` already writes that array.
3. **Rendering:** the frontend renders `labels` and falls back to legacy `tags`.
4. **Current limitation:** the label specification declares labels decorative metadata, and current master-task projection and validation still parse Markdown. The implementation must promote the two task labels to classification semantics.
5. **Parent identity:** a `subtask` label does not encode its master; the existing relationship is required and remains canonical.

---

## C. One progress transaction

1. **Add:** `ledger-cli master-task-progress --ledger "$DECISION_OS_LEDGER_FILE" --plan-stdin --json`.
2. **Input:** `masterCardId`, structured master sections, structured subtask updates keyed by existing card ID, `verifiedSubtaskIds`, canonical label changes, and one `agentReply`.
3. **Preflight:** verify the master label, child labels, direct `subtask` relationships, every update ID, every verified ID, section formatting, and thread role before writing.
4. **Commit boundary:** snapshot the ledger, affected card files, and thread file; render sections; apply labels; set every verified card to `done`; regenerate relationship-backed links; append the reply; write all files; roll back every file on failure.
5. **Result:** return the post-write gate document. The gate checks JSON labels, JSON statuses, relationship integrity, canonical link coverage, and thread roles.
6. **Authorization boundary:** this command never sets the master card to `done`; `master-task-complete` remains the only explicit master closeout operation.

---

## D. Command reduction

1. **Representative study:** `9` mutations + `7` status writes + `2` validations + `3` gates + `1` answer become one progress transaction: `22` lifecycle/write calls become `1`, a `95%` reduction.
2. **Whole observed run:** keeping its other help and context reads unchanged, total `ledger-cli` invocations fall from `28` to `7`, a `75%` reduction.
3. **Simple summary update:** content, classification, status, gate, and answer changes become one transaction.

---

## E. Compatibility sequence

1. **First release:** make discovery and the gate use JSON labels, JSON status, and relationships; fall back to legacy Markdown classification only when JSON task labels are absent.
2. **Template update:** make `master-task-apply` write canonical task labels and relationship-backed links without Markdown status suffixes.
3. **Touch migration:** add labels and strip legacy tokens when a master is next touched; do not bulk-rewrite untouched cards.
4. **Completion update:** make `master-task-complete` validate labels and relationships and return its post-transaction gate.

---

## F. Acceptance evidence

1. **Classification truth:** a JSON-labeled master is discovered without `#master-task` in its body.
2. **Status truth:** changing `cards[].status` changes the gate and Control Room result without a Markdown edit.
3. **Relationship integrity:** an unlinked `subtask` label cannot attach a card to a master; inconsistent endpoints are diagnosed.
4. **Atomicity:** one invalid card ID leaves JSON, every card file, and the thread byte-identical.
5. **Legacy tolerance:** stale Markdown task tokens cannot block progress or completion.
6. **Authorization:** progress cannot complete the master; completion still requires the dedicated authorized command.
7. **Regression metric:** the seven-subtask fixture completes progress through one CLI invocation and one ledger write.
