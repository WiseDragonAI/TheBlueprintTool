## A. Objective

1. **Outcome:** Make Process Card skill runs use the same card-owned run identity across Codex Log and Control Room.
2. **Operator-visible result:** A running Process Card skill preserves the source thread, appears in the source card's Codex Log, and moves its master task from Queue to Active.

## B. Contradicted-Success RCA

1. **Reported failure:** After restarting the server and launching a skill, the operator saw the skill running inside the card while the master remained in cards to process.
2. **Persisted source state:** `card-34288c99-cf14-4d5f-8840-83bc957c9a36` stored current Process Card run `codex-skill-1784030180133-084a9051` in `codexActiveRunId` and `codexRunId`. Its Markdown was `#task-active`.
3. **First incorrect transition:** `frontend-mobile/src/mobile.js` loaded Control Room with `card.codexThreadRunId` only. Process Card projection intentionally clears that legacy thread field, so Control Room sent no status request for the current skill and classified the task as waiting.
4. **Why the first implementation missed it:** The regression scope stopped at backend ownership, desktop card detail, and Codex Log rendering. It did not inspect Control Room as a downstream consumer of card run ownership. The Control Room fixture covered only `codexThreadRunId`, so it could not fail for a Process Card run.
5. **Captured route:** Android Termux Chromium `138.0.7204.168` loaded `http://127.0.0.1:50150/?tab=queue` at a `412 × 915` touch viewport.
6. **Captured DOM:** Before the correction, `Synchronized Server Skills` rendered under Queue as `3m waiting`; Active did not contain that card.
7. **Captured request boundary:** Before the correction, Control Room issued no status request for `codex-skill-1784030180133-084a9051` on the source card.

## C. Corrected Ownership Contract

1. **Resolver:** `frontend-mobile/src/mobile-control-room.js` now resolves `codexActiveRunId`, then `codexThreadRunId`, then `codexRunId`.
2. **Consumer:** `loadControlRoom()` uses that resolver before requesting run status.
3. **Classification:** A `#task-active` master with the resolved current run and status `running` is placed in Active.
4. **Scope:** The change does not modify pipeline execution, source-thread Markdown, generated output cards, run status derivation, or queue ordering.
