## A. Required outcome

1. **A failed project synchronization must never leave either participant blocked by an orphaned origin lock.**
2. Starting synchronization after a failure must follow one deterministic recovery sequence: reconcile the failed run and retry it when its ownership is valid; when its lock owner is stale, cancel that stale owner with compare-and-release semantics, then admit a fresh run.
3. The operator must see the active run identity, recovery action, and terminal result in Project Settings instead of the generic `Repository origin already has an active synchronization run.` dead end.

4. `start-project-sync.ts` releases a remote lock only from the admitted run's terminal path. A prior initiator failure can therefore strand a participant lock.
5. The backend exposes retry but no project-sync cancellation endpoint. The responsive Project Settings UI starts a new request after failure and exposes no failed-run recovery control.

---

## C. Recovery contract

1. Treat the lock owner `syncId` and `originFingerprint` as the compare-and-release identity.
2. A participant conflict response must return the owning `syncId` without mutating the lock.
3. The initiator must classify that owner from durable run state. A matching failed run is retried. A missing or terminal stale owner is conditionally cancelled and released before exactly one fresh admission.
4. Cancellation must be idempotent, must not release a lock acquired by a newer run, and must persist a terminal `cancelled` result for an existing run.
5. SSE, GET status, Project Settings, and reload restoration must present the same authoritative state.

---

## D. Acceptance evidence

1. Backend tests prove failed-run retry, stale remote-owner cancellation, compare-and-release protection, participant unavailability, duplicate recovery requests, and restart restoration.
2. Frontend tests prove the failed state exposes a recovery action, prevents duplicate submissions, renders the recovered run, and reports cancellation failure without losing the authoritative failed run.
3. Repository-wide leased typechecks and focused suites pass.
4. Served-route verification observes the complete failed-run recovery flow without restarting the server.
