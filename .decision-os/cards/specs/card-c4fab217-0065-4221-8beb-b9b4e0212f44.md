## A. Scope

1. **Mobile routes:** Add `/projects` and `/projects/:projectId` to `frontend-mobile/src/mobile.js` and render dedicated index and detail surfaces in `frontend-mobile/index.html`.
2. **Project selection:** Preserve the existing project cookie/header selection mechanism behind an explicit `Open project` action.
3. **Project settings:** Add a native `<dialog>` settings form for display name, description, and color.

---

## B. Interaction Contract

1. **Index cards:** Render each project with display name, description, relative path, color accent, and an accessible active-project indicator.
2. **Detail route:** Selecting a card navigates to `/projects/:projectId` without changing the active project.
3. **Open action:** `Open project` selects the project, resets the Control Room project and ledger filters, and navigates to `/`.
4. **Settings action:** `Settings` opens the native modal prefilled from the selected catalog project.
5. **Save action:** Disable duplicate submission, show server validation feedback in the dialog, update local catalog state from the successful response, and rerender the index, detail, brand, and project-colored task filters.
6. **Modal behavior:** Rely on native `<dialog>` focus containment, close on cancel and `Esc`, restore focus to `Settings`, and keep form state local to the selected project.

---

## C. Acceptance Criteria

1. **Route resilience:** Direct entry, refresh, browser back, and browser forward preserve both project routes.
2. **Missing project:** An unknown project id produces the existing error surface without selecting another project.
3. **Persisted edit:** Saving all three fields survives a fresh catalog load and updates visible projections immediately.
4. **Failed edit:** A rejected update leaves the dialog open, shows the error, and preserves server-confirmed catalog state.
5. **Tests:** Mobile tests cover route parsing, direct entry, detail selection, modal prefill, successful save, failed save reconciliation, and `Open project` behavior.
