## A. Purpose

1. **Goal:** Commit completed changes attributable to the supplied card IDs.
2. **Boundary:** Leave unrelated, ambiguous, and incomplete changes unchanged.

---

## B. Scope Reconstruction

1. **Supplied cards:** Read the full supplied `cards` before inspecting repository changes.
2. **Iteration chain:** Traverse inbound Decision OS relationships recursively from every supplied card to each linked `implementation-orchestrator` result. From each result, follow the inbound `implementation-orchestrator` relationship to its `task-dependency` grouping card, then follow the inbound `task-dependency` relationship to its `task-list` card.
3. **Planning context:** Read the full resolved cards, including `Task Inventory`, `Independent Task Groups`, `Worker Results`, and `Implementation Batch Handoff`.
4. **Iteration scope:** Treat the linked plan and completed worker results as the authoritative scope. Include every completed task and changed file from the full iteration; exclude blocked, incomplete, unrelated, and untraceable work.
5. **Diff mapping:** Inspect repository `git status` and `git diff` only after reconstructing the iteration scope, then map every in-scope task and worker-reported file to explicit changed `files` and `hunks`.
6. **Chain blocker:** Stop and report the exact missing relationship when a supplied card does not resolve unambiguously to the iteration's `implementation-orchestrator`, `task-dependency`, and `task-list` cards.
7. **Repositories:** Detect each `git` repository that owns changed paths, including nested repositories.
8. **Repository conventions:** Analyze branch conventions, protected branch expectations, default branch names, current branch state, and recent commit patterns before committing. Do not assume `main` or `master` is the correct target branch.
9. **Decision OS cards:** Include every related `.decision-os` card markdown change that documents the in-scope implementation.

---

## C. Commit Rules

1. **Classes:** Use `PKG` for package, dependency, plugin, lockfile, and package-manager changes; `FT` for features; `FIX` for defects; `DOC` for documentation-only changes.
2. **Decision OS classification:** Classify every in-scope `.decision-os` card markdown change as `DOC` and place it in a `DOC` commit, never in a `PKG`, `FT`, or `FIX` commit.
3. **Separation:** Keep `PKG`, `FT`, `FIX`, and `DOC` in separate commits; use hunk staging when one file contains multiple classes.
4. **Order:** Commit `PKG` first, then `FT`, then `FIX`, then `DOC`.
5. **Nested repositories:** Commit nested repository changes before the parent repository gitlink change.
6. **Subject format:** Write commit subjects as `<PREFIX> - <imperative summary>`, with exactly one space, one hyphen (`-`), and one space between prefix and summary.
7. **Examples:** `FT - add card-scoped commit grouping`; `FIX - preserve unrelated staged changes`; `PKG - add repository discovery dependency`; `DOC - record commit skill contract`.

---

## D. Safety And Completion

1. **Staging:** Stage explicit paths and hunks; do not use `git add .` and `git add -A` in a dirty workspace.
2. **History safety:** Do not run `git reset`, `git commit --amend`, `git rebase`, `git push`, and force-update commands.
3. **Commit-only scope:** Review every staged diff before committing; do not run `tests`, `build`, or broad validation commands from this skill.
4. **Commit hooks:** Let configured `commit hooks` run normally and do not bypass them with `--no-verify`. If a hook blocks the commit, report its output.
5. **Iteration completion:** Create the required commit set only when its combined staged content covers the entire completed iteration and plan reconstructed in section B.
6. **Finish:** Verify each commit with `git show --stat --oneline HEAD` and `git status --short`, then report commits, hook results, blocked in-scope work, and remaining unrelated changes.
