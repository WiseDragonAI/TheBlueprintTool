## A. Skill Purpose

1. **Installed skill:** `visual-mockup-generator` is installed at `/home/jbb/.codex/skills/visual-mockup-generator/SKILL.md`.
2. **Primary job:** Convert a `screen-content-planner` output, UX plan, product analysis card, or equivalent screen description into visual mockups that can be inspected in Decision OS.
3. **Pipeline position:** Use this skill after `screen-content-planner`; if `bloating-analysis` has tightened the source plan, use the tightened plan as the mockup source of truth.
4. **Output boundary:** Produce visual artifact files only; do not implement production routes, backend endpoints, durable app state, or product code unless the operator explicitly asks.

---

## B. Source And Design Analysis

1. **Screen contract extraction:** Identify each screen, purpose, route or surface, actor, required sections, controls, data, states, edge cases, and source grounding before writing mockup files.
2. **App-context verification:** Inspect the repo structure, package files, framework config, native directories, routes, build targets, README, product docs, and existing screens before deciding whether the target is web, mobile, desktop, extension, kiosk, or another surface.
3. **Platform guardrail:** Do not infer `web` only because the repo contains JavaScript or TypeScript; React Native, Expo, Ionic, Electron, Capacitor, and hybrid apps also use JS/TS.
4. **Format selection:** Choose the render viewport before designing, for example mobile portrait `9:16`, mobile landscape `16:9`, tablet `4:3` or `3:4`, desktop app `16:10`, or the product's existing viewport when known.
5. **Recent-commit audit:** Inspect recent commits related to the mocked feature or relevant style/component paths, using commands such as `git log --oneline -n 20 -- <path>` and `git show <commit> -- <path>` when paths are known.
6. **Visual-system audit:** Inspect the target app or provided artifacts for colors, typography, spacing, border radius, shadows, density, layout conventions, component styles, controls, empty states, and icon usage.
7. **Language verification:** Inspect existing UI copy, locale files, i18n config, screenshots, product docs, route content, and recent commits to determine the target UI language; do not assume English from English card or analysis prose.
8. **Frontend-design reuse:** Apply the design quality principles from `frontend-design`, but keep the result coherent with the audited app, verified platform, and target UI language instead of inventing a detached visual direction.

## C. Artifact Contract

1. **Source location:** In a Decision OS workspace, write generated mockups under `.decision-os/ui-mockups/<mockup-slug>/`.
2. **HTML contract:** Create exactly one `.html` file per screen, for example `.decision-os/ui-mockups/<mockup-slug>/<screen-slug>.html`.
3. **CSS contract:** Create one separate linked `.css` file for each HTML screen, for example `.decision-os/ui-mockups/<mockup-slug>/<screen-slug>.css`.
4. **Screenshot contract:** Render each screen to `.decision-os/ui-mockups/<mockup-slug>/screenshots/<screen-slug>.png` using the selected viewport dimensions.
5. **Renderer helper:** Use `/home/jbb/.codex/skills/visual-mockup-generator/scripts/render-html-screenshots.mjs` when Playwright is available, or an equivalent browser automation path when it is not.

---

## D. Decision OS Card Output Rules

1. **Card headings:** Use `H2` main headings prefixed with uppercase section letters, for example `## A. Scope`.
2. **Subheadings:** When subsections are necessary, prefix them with the parent letter and a number, for example `### B.1 Color Tokens`.
3. **Section separators:** Put `---` horizontal rules between sections.
4. **Numbered content:** Use numbered lists for normal card requirements and output prose.
5. **Important labels:** Start important items with bold labels, for example `1. **Viewport:** \`390x844\`.`.
6. **Exact tokens:** Use backticks for file paths, config keys, API routes, statuses, viewport dimensions, and literal values.
7. **Image carousel:** Add screenshots as adjacent standalone image-only Markdown lines so Decision OS renders them as a carousel.

---

## E. Validation Checklist

1. **Grounding:** Every generated mockup maps to a source screen definition or explicit assumption.
2. **App-context evidence:** The final answer names the repo files, configs, native directories, docs, or routes used to determine the actual target platform.
3. **Recent-commit evidence:** The final answer names the recent commits or commit-scoped paths inspected for current style and product direction.
4. **Style evidence:** The final answer names the app style files, screenshots, components, or existing mockups inspected before design.
5. **Language evidence:** The final answer names the source used to determine UI language, or states the unresolved language blocker before generating visible copy.
6. **Complete artifacts:** Every screen has one `.html`, one `.css`, one rendered `.png`, and one card image reference when the output is for Decision OS.
7. **Viewport match:** Every rendered screenshot uses the selected aspect ratio and dimensions.
8. **Layout inspection:** Screens are nonblank, unclipped, and do not have text overlapping controls or adjacent content.
9. **No prose bloat:** Card and thread answers should report concrete paths, dimensions, constraints, and verification results only.
