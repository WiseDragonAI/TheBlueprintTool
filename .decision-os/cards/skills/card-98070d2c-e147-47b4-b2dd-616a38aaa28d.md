## A. Task List Skill

1. **Purpose:** Convert clarified source cards into granular engineering tasks after the `goal`, mockups, codebase analysis, specs, and implementation boundaries are understood.
2. **Output:** Produce task records for concrete work such as modifying state files, creating database migrations, implementing scenario `A`/`B`/`C`, adding fixtures, or writing targeted test files.
3. **Dependencies:** Requires clarified specs, the relevant source cards, current codebase context, and accepted constraints; feeds the `Task Dependency Skill`, `Task Group Completeness Skill`, and later test failure attribution.

---

## B. Task Dependency Skill

1. **Purpose:** Analyze task relationships so the pipeline knows which tasks block each other, which tasks are independent, and which tasks must remain in the same implementation context.
2. **Output:** Produce independent task groups with explicit dependency edges, shared-file risks, ordering constraints, and group boundaries that can be implemented side by side.
3. **Dependencies:** Requires the `Task List Skill` output and enough codebase context to detect shared ownership; feeds the `Task Group Completeness Skill` and `Implementation Orchestrator Skill`.

---

## C. Task Group Completeness Skill

1. **Purpose:** Audit every proposed task group for missing implementation details, forgotten files, uncovered scenarios, absent migrations, or test tasks that should exist before agents start work.
2. **Output:** Produce a completeness report that either approves each group or adds required tasks back into the group with a concrete reason and source evidence.
3. **Dependencies:** Requires the task list, task dependency map, clarified specs, mockups or analysis cards when present, and current codebase context; gates the `Implementation Orchestrator Skill`.

---

## D. Implementation Orchestrator Skill

1. **Purpose:** Launch implementation sub-agents from complete independent task groups and coordinate the batch until every group has returned an implementation result.
2. **Output:** Produce a dispatch plan, group-to-agent assignments, implementation status, and follow-up repair requests when later test or RCA reports identify group-specific failures.
3. **Dependencies:** Requires complete task groups from the `Task Dependency Skill` and `Task Group Completeness Skill`; invokes the `Implementation Worker Skill`, then hands the completed batch to the `Test Run And Failure Attribution Skill`.

---

## E. Implementation Worker Skill

1. **Purpose:** Implement one assigned task group with the smallest coherent mental context needed by a software engineer, staying inside that group scope.
2. **Output:** Produce changed files and an implementation note that identifies completed tasks, touched paths, assumptions, and any unresolved blocker for the orchestrator.
3. **Dependencies:** Requires one dispatch package from the `Implementation Orchestrator Skill`; must not run global tests and must not create commits because multiple workers may be active in parallel.

---

## F. Test Run And Failure Attribution Skill

1. **Purpose:** Run the test suite only after the parallel implementation batch is complete, then read failures without colliding with active implementation workers.
2. **Output:** Produce a test report that maps each failing command, failing file, stack trace, or scenario back to the responsible task group using the file paths already listed in the task records.
3. **Dependencies:** Requires the completed implementation batch from the `Implementation Orchestrator Skill` and the original task list from the `Task List Skill`; reports back to the orchestrator for fix or RCA dispatch.

---

## G. Root Cause Analysis Skill

1. **Purpose:** Investigate failures that are not obvious from the test report by collecting evidence, forming hypotheses, checking the execution chain, and identifying the fundamental cause.
2. **Output:** Produce an RCA report with observed evidence, rejected hypotheses, confirmed root cause, affected task group, and the smallest structurally correct fix path.
3. **Dependencies:** Requires the `Test Run And Failure Attribution Skill` report, related task group context, relevant code paths, and any available project RCA methodology from `DroidFleet` or Decision OS playbooks.

---

## H. Code Quality Report Skill

1. **Purpose:** Audit the implemented code against project quality rules after functional implementation is stable enough to inspect.
2. **Output:** Produce a quality report covering file organization, import hygiene, function boundaries, useful comments, files over `300` lines, unclear ownership, and violations of Executor or Master Ledger criteria when applicable.
3. **Dependencies:** Requires the current implementation snapshot, accepted specs, and known project code quality criteria; feeds the `Quality Improvement Orchestrator Skill`.

---

## I. Quality Improvement Orchestrator Skill

1. **Purpose:** Convert the code quality report into independent refactor or cleanup groups and coordinate agents that improve code quality without changing the intended behavior.
2. **Output:** Produce an improvement dispatch plan, group boundaries, non-functional acceptance criteria, and a re-test or re-audit request after improvement workers return.
3. **Dependencies:** Requires the `Code Quality Report Skill` output and invokes the `Quality Improvement Worker Skill`; can send the result back through the `Test Run And Failure Attribution Skill` when verification is needed.

---

## J. Quality Improvement Worker Skill

1. **Purpose:** Apply one assigned quality improvement group, such as splitting oversized files, reorganizing functions, cleaning imports, clarifying comments, or aligning files with the intended tree structure.
2. **Output:** Produce refactor changes and a concise note explaining which quality findings were resolved, which files changed, and whether any finding needs a follow-up group.
3. **Dependencies:** Requires one dispatch package from the `Quality Improvement Orchestrator Skill`, the relevant `Code Quality Report Skill` findings, and current code context; does not own the global test run.
