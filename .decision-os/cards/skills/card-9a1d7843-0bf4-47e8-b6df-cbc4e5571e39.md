## B. Local Codex Skills Retained From First Pass

1. **`openticket`.** Planning skill for a broad operator-reported problem. It performs code-first static analysis, drafts `REQ-*` requirements, scope, codebase impact intent, dependency blockers, an `Ideal Control-flow DAG`, and acceptance checks, then opens a GitLab issue only after operator approval.
2. **`improveticket`.** Planning skill for an existing weak GitLab issue. It rewrites the issue into the OpenTicket structure, asks for operator approval, updates the issue, applies factory-actionable labels, and removes `improve`.
3. **`product-analysis`.** Pre-planning analysis skill. It maps a goal to affected workflow, actor, linked specs, missing specs, and spec gaps from code evidence. It explicitly does not recommend an implementation path or approval gate.
4. **`ticket-solver`.** Execution-first DroidFleet skill. It solves an existing GitLab ticket end to end, but it still creates a working document and full control-flow DAG before implementation. It belongs after a ticket exists, not at the start of a broad goal.
5. **`executor-precheck`.** Checks whether an operator goal has enough approved `Specs`, `Data Model`, `Runtime State`, repo facts, and scope boundary before stack planning.
6. **`executor-stack`.** Analyzes specs/data/runtime, identifies `Root Blocks`, validates stack choices, creates an agnostic directory scaffold, and asks blocking operator questions.
7. **`executor-spec`.** Builds the `Master Ledger`: domains, one test suite per spec, inputs, effects, helpers, screens/pages, components, state, control-flow entries, unresolved questions, and spec candidates. This is the strongest executor-side `goal -> implementation structure` splitter.
8. **`executor-implement`.** Implementation skill that consumes the `Master Ledger`. It should not infer architecture or split a broad goal by itself.
9. **`decision-os-treat-open-notes`.** Inbox-treatment skill for answering operator notes and updating cards/threads. It can perform ledger work, but it is not a general planning splitter.

## C. DroidFleet OpenSpec Planning Skills

1. **`openspec-explore`.** Thinking and investigation mode. It reads code, compares options, surfaces risks, and can capture decisions into OpenSpec artifacts, but it does not implement.
2. **`openspec-new-change`.** Starts a new change from a goal or change name. It creates `openspec/changes/<name>/`, shows artifact status, and displays the first artifact instructions.
3. **`openspec-continue-change`.** Progresses one artifact at a time. In the spec-driven schema, the sequence is `proposal.md -> specs/<capability>/spec.md -> design.md -> tasks.md`; `tasks.md` is the checkboxed implementation task list.
4. **`openspec-ff-change`.** Fast-forwards artifact creation until implementation is ready. This is the strongest OpenSpec `goal -> task list` skill because it creates the required artifacts in dependency order, including `tasks.md`.
5. **`openspec-apply-change`.** Executes tasks from an OpenSpec change. It is implementation, not planning, but it consumes the task list.
6. **`openspec-verify-change`.** Verifies implementation against `tasks`, `specs`, and `design`. It is planning-adjacent quality control, not a splitter.

## D. DroidFactory Planning Roles

1. **`ticket/improver`.** Normalizes an existing weak issue into a factory-ready ticket. Required body structure: `Problem Report`, `REQ-###`, `Scope`, `Codebase Impact Intent`, `Dependency Blockers`, `Ideal Control-flow DAG`, and `Acceptance`. It classifies the issue as `feature` or `bug`; the orchestrator then applies the first pipeline labels.
2. **`product/analyzer`.** Turns a vague product request into a production-grade problem definition with problem statement, goals, non-goals, scope boundaries, key unknowns, and operator-dependent integrations.
3. **`product/rfc-writer`.** Produces the implementation path: proposed solution, alternatives, tradeoffs, integration strategy, and mock/live switches for operator-dependent integrations.
4. **`product/architect`.** Defines components, boundaries, contracts, integration switches, failure handling, observability, and rollout assumptions.
5. **`product/prd-writer`.** Converts approved product architecture into functional requirements, non-functional requirements, acceptance criteria, operator enablement, and release quality expectations.
6. **`product/decomposer`.** Splits an approved product ticket into child epic tickets labeled `pipeline:epic`, `epic:research`, and `status:todo`.
7. **`epic/analyzer`.** Converts an epic body into hard specs, intent interpretation, existing data model constraints, downstream execution contract, and proven gaps.
8. **`epic/architect`.** Produces the epic implementation plan: data model deltas, module decomposition, helper extraction, integration points, dependency injection boundaries, test strategy, and ordered phases.
9. **`epic/quality-planner`.** Red-teams `Epic Architecture`, reduces over-engineering, corrects factorization, and defines quality gates before decomposition.
10. **`epic/decomposer`.** Splits corrected epic architecture into child feature issues labeled `pipeline:feature`, `feat:plan`, and `status:todo`. Each child issue contains problem statement, `REQ-*`, scope, codebase impact, dependency metadata, and acceptance criteria.
11. **`feature/analyzer`.** Maps feature intent to codebase surface area and produces evidence-backed task breakdown, risks, planner TODOs, planner decisions, and recommended implementation order.
12. **`feature/planner`.** Produces the implementation plan for one feature issue: `Spec`, `Codebase Impact Intent`, `Dependency Blockers`, and `Ideal Control-flow DAG`. It does not create child issues.
13. **`bug/rca`.** Produces the pre-fix bug plan: reproduction status, code-path trace, root cause, fix scope, mandatory fix DAG, spec-change check, factorization check, regression test plan, and fixer checklist.
14. **`refactor/analyzer`.** Ranks top refactor candidates and selects the primary set for the run. It is a planning role for refactor work, but it does not create issues.
15. **`prototype/delivery-planner`.** Converts a design package into a delivery plan with milestones, backlog decomposition, dependency map, risk register, and validation gates.

## E. DroidFactory Pipeline Labels

1. **Feature pipeline.** `pipeline:feature` stages include `feat:plan`, `feat:implement`, `feat:audit`, plus recovery stages such as `feat:commit_fix`, `feat:test_fix`, and `feat:merge_solve`. The first actionable planning stage is `feature/planner`.
2. **Bug pipeline.** `pipeline:bug` starts with `bug:rca`, then `bug:fix`, `bug:audit`, and `bug:archive`, with similar recovery stages. The planning stage is `bug/rca`.
3. **Product pipeline.** `pipeline:product` includes `analysis`, `research`, `rfc`, `architecture`, `prd`, red-team stages, and `decompose`. The decomposition stage creates child epics.
4. **Epic pipeline.** `pipeline:epic` includes `research`, `analyze`, `architecture`, `quality`, `decompose`, and `review`. The decomposition stage creates child feature tickets.
5. **Research pipeline.** `pipeline:research` includes `scan`, `summarize`, `deep_dive`, and `conclude`. It is evidence-building rather than implementation task splitting.
6. **Refactor pipeline.** `pipeline:refactor` includes `analyze`, `implement`, and `audit`. The analyzer selects concrete code hygiene targets.

## F. Extracted Decision Information

1. **Best OpenSpec goal-to-task skill.** Use `openspec-ff-change` when the desired output is a complete OpenSpec artifact set ending in `tasks.md`.
2. **Best local ticket planner.** Use `openticket` for a broad operator problem that should become a GitLab issue after approval.
3. **Best local issue-upgrader.** Use `improveticket` when an existing issue is weak and needs OpenTicket structure plus factory labels after approval.
4. **Best Factory issue normalizer.** Use `ticket/improver` when DroidFactory should non-interactively normalize an `improve` issue and classify it for the feature or bug pipeline.
5. **Best Factory product-to-work splitter.** Use `product/decomposer` to split an approved product ticket into epics, then `epic/decomposer` to split corrected epic architecture into feature tickets.
6. **Best single-feature planner.** Use `feature/analyzer` before `feature/planner` when the feature needs grounded codebase surface mapping before the implementation DAG.
7. **Best bug planner.** Use `bug/rca`, because it produces fix scope, fix DAG, regression test plan, and fixer checklist before implementation.
8. **Where `ticket-solver` belongs.** `ticket-solver` remains important, but it is a downstream solver for an existing ticket. It should consume a prepared ticket, create the working DAG, implement, test, and report evidence.
9. **Executor vs Factory distinction.** Executor skills build a local `Master Ledger` implementation scaffold. DroidFactory skills operate through GitLab issues and labels as the workflow state machine.
10. **Correct broad-goal chain in DroidFactory.** `ticket/improver -> product/analyzer/RFC/architecture/PRD -> product/decomposer -> epic/analyzer/architect/quality-planner -> epic/decomposer -> feature/analyzer -> feature/planner -> feature/implementer`.
