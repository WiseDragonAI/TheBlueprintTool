## A. Correction

1. **You are right: I omitted an existing JSON primitive that materially improves the design.** Cards already persist `labels`, and `ledger-cli mutate --card-labels` already writes them.
2. **Why I missed it:** I scoped the first pass around status authority and parent-child membership, then incorrectly retained `#master-task` as harmless Markdown classification without auditing the card-label contract. The current implementation explains the split but does not justify the omission: master-task code parses Markdown, while the existing label specification currently describes labels as decorative metadata.
3. **Canonical field:** the JSON field is `labels`; the frontend accepts `tags` only as a compatibility fallback.

---

## B. Corrected model

1. **Classification:** `cards[].labels` contains `master-task` on the master and `subtask` on every child.
2. **Completion:** `cards[].status` is the only persisted status source.
3. **Membership:** existing `relationships[label=subtask]` remains authoritative because a `subtask` label does not identify which master owns the card.
4. **Markdown:** remove `#master-task`, `#task-*`, and `— Status:` from machine-readable authority; keep legacy parsing only during migration.
5. **CLI:** make `master-task-apply` write the labels and make the proposed atomic `master-task-progress` validate and update labels, statuses, relationships, content, and the thread in one transaction.
