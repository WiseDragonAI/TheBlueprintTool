## A. Why the three jobs did not move

1. **The previous diagnosis covered the wrong queue state:** its regression proved recovery for records still marked `pending`.
2. **Your three jobs had already been claimed:** after the crash, startup converted their durable `running` records to `interrupted` with the explicit rule that they would not be relaunched.
3. **The scheduler ignores `interrupted`:** it selects only `pending`, so those three records could never return to processing. This is why the first merge did not fix your actual restart case.

---

## B. Corrected behavior

1. **Claimed thread jobs:** startup now converts them into pending continuations of the same durable Codex run.
2. **Claimed continuations:** startup requeues them without changing their run identity.
3. **Session continuity:** recovery uses the captured Codex session ID; when the crash happened before session capture, it reconstructs a new session from durable card context.
4. **Integration:** implementation commit `a53d295` is merged into `main` by `b0b6445`.

---

## C. Verification and runtime boundary

1. **Restart regression:** a persisted `running` thread launches through `codex exec resume`, reaches `complete`, and is removed from the durable queue.
2. **After-merge checks:** focused recovery tests pass `10/10`; backend typecheck passes.
