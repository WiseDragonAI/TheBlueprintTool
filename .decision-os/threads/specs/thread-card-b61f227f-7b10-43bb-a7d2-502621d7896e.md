The simplest mental model is: **a Codex plugin is an installable capability pack**. It is a distribution container, not a new AI model and not automatically active just because it appears under `/plugins`.

A plugin can bundle several things:

1. **Skills:** reusable instructions, references, and helper scripts for a particular workflow.
2. **Apps/connectors:** authenticated access to services such as Gmail, Google Drive, Slack, and GitHub.
3. **MCP servers:** tools through which Codex can retrieve structured data and perform external actions.
4. **Hooks:** commands triggered at lifecycle points. These deserve careful review because they can execute commands.
5. **Browser capabilities, assets, and scheduled-task templates:** supporting pieces needed by a packaged workflow.

This is why a plugin can be tiny, such as one specialized skill, or substantial, such as a security workflow with instructions, tools, and hooks.

**What the 500-item list means:** `/plugins` opens a directory assembled from **marketplace catalogs**. OpenAI documents an official curated directory, plus repository and personal marketplaces. A marketplace is essentially a JSON catalog containing plugin names, descriptions, sources, categories, and installation policies. The list is therefore closer to an app store inventory than to a list of 500 components loaded into your conversation.

Nothing in that directory is useful merely because it is listed. A plugin matters only after you select it, review it, install it, enable it, complete any required service authorization, and start a new Codex session. The new session can then discover its bundled skills and tools when your request matches them.

**How to decide whether to install one:** install a plugin when it matches a repeated job and provides something Codex does not already have, such as a tested workflow, access to private service data, or specialized tools. Ignore the rest. Before installation, check the publisher, description, requested capabilities, external authentication, MCP tools, and hooks. You do not need to understand all 500 entries.

The related terms differ as follows:

- A **skill** teaches Codex how to perform a workflow.
- A **connector/app** gives Codex authenticated access to an external system.
- An **MCP server** exposes live tools and data.
- A **hook** enforces automation around lifecycle events.
- A **plugin** packages any combination of those pieces for installation and distribution.

Local verification: `codex plugin marketplace list` currently returns `No plugin marketplaces in scope` in this shell. Therefore, the large list you see is not produced by a project-specific marketplace configured in this CLI environment; the official curated directory documented by OpenAI is the verified built-in catalog source.

You are right: the useful question is not “what can a plugin contain?” but **“what job becomes possible or materially easier after I install it?”**

One caveat before ranking them: there is no trustworthy universal popularity chart yet. OpenAI does not publish plugin install counts. The ecosystem launched recently, marketplace sites use different inventories, and Reddit recommendations are anecdotal. The strongest available signals are OpenAI's highlighted plugins, the `openai/plugins` repository (about `1.3k` GitHub stars when checked), third-party directory visibility, and recurring community mentions.

## The most useful developer plugins

1. **GitHub — turn a ticket into repository work.**

   Concrete flow: ask Codex to read issue `#842`, find the relevant code and earlier pull requests, implement the fix locally, inspect the failed GitHub Actions job, then draft the pull-request description. It can also query code-scanning and Dependabot alerts. This is valuable when important context lives on GitHub rather than in the checked-out files.

   Example prompt: `Read GitHub issue #842, inspect related PRs and the failing CI run, then propose the smallest tested fix in this checkout.`

2. **Sentry — debug a real production failure.**

   Concrete flow: paste a Sentry issue URL; Codex retrieves the event, stack trace, affected release, tags, and surrounding error data, traces the failure into the local codebase, proposes a regression test, and can update the issue after the fix. This removes the manual copying of stack traces and metadata from the Sentry dashboard.

   Example prompt: `Investigate this Sentry issue, identify the first incorrect state transition in our code, reproduce it with a test, and prepare a minimal fix.`

3. **Linear — connect planning to implementation.**

   Concrete flow: Codex reads a Linear ticket and its comments, finds connected issues, builds the implementation, then adds a progress comment and updates the ticket status. Its value is synchronization: the implementation stays tied to the team's actual scope and acceptance criteria.

   Example prompt: `Open ENG-214, verify its acceptance criteria against this repository, implement the missing behavior, then draft a concise Linear update with test evidence.`

4. **Figma — move between design and code.**

   Concrete flow: Codex reads a selected frame's layout, variables, styles, and components; maps them to the repository's design system through Code Connect; implements the screen; and can send a generated interface back to Figma as editable layers. This is much more specific than “access Figma”: it reduces design inspection, token transcription, and generic component generation.

   Example prompt: `Implement the selected Figma frame using our existing components and design tokens; list every visual deviation that remains.`

5. **Vercel — understand and operate a Vercel application.**

   Concrete flow: Codex receives current guidance for Next.js, Vercel Functions, storage, middleware, queues, observability, and deprecated APIs; it can prepare a preview deployment and inspect deployment state. This is most useful for a Vercel-heavy stack because it adds platform-specific knowledge as well as operations.

   Example prompt: `Audit this app for deprecated Vercel and Next.js patterns, fix the verified findings, then create a preview deployment and inspect its status.`

6. **Hugging Face — research models and datasets while building.**

   Concrete flow: ask for a model meeting constraints such as task, size, framework, and license; search datasets and papers; consult current library documentation; then use the findings in the implementation. This is useful for AI applications, not ordinary web development.

   Example prompt: `Find an ONNX-compatible text-embedding model under 500 MB with a permissive license, compare the viable candidates, and integrate the selected model.`

OpenAI's own repository also highlights stack-specific bundles: **Build Web Apps**, **Build iOS Apps**, **Build macOS Apps**, and **Expo**. These teach implementation, debugging, deployment, upgrade, and packaging workflows for a particular stack. They are useful when that stack is central to your project; they add little when it is not. [OpenAI's official plugin repository](https://github.com/openai/plugins) documents these examples, while [Vercel's July 2026 survey](https://vercel.com/i/codex-plugins) provides detailed use-case breakdowns for GitHub, Sentry, Linear, Figma, Vercel, and Hugging Face.

## The plugins that make Codex a work assistant

The strongest community theme is not a coding methodology plugin. It is **connections to the systems where work context already lives**:

- **Slack + Google Drive:** collect an incident discussion, the relevant design document, and meeting notes; turn them into a postmortem, response plan, and engineering tickets.
- **Notion:** search project knowledge, synthesize research, prepare meeting briefs, update plans, and capture decisions back into the workspace.
- **Sales plugin:** combine Salesforce or HubSpot records with Slack and outreach signals; identify accounts needing attention, prepare a meeting brief, draft follow-ups, update the CRM, and flag deals at risk.
- **Data Analytics plugin:** query Snowflake, Databricks Genie, Hex, and Tableau; explain a metric change; produce a report and dashboard.
- **Creative Production plugin:** turn a campaign brief into boards, ad variants, product images, and reviewable creative assets through Figma, Canva, Shutterstock, Picsart, and Fal.
- **Product Design plugin:** audit a live flow, explore alternatives, turn screenshots into an interactive prototype, and carry the result into Figma or Canva.

OpenAI gives these as actual multi-tool workflows, not hypothetical examples. See [OpenAI's role-specific plugin announcement](https://openai.com/index/codex-for-every-role-tool-workflow/).

## What Reddit actually says

The sampled `r/codex` discussion is divided, which is useful evidence in itself:

- Several users say **Slack, Google Drive, Notion, Vercel, Netlify, Stripe, and similar external-service integrations** deliver the clearest value because they remove browser switching and give Codex missing context.
- **Superpowers** is the most repeatedly discussed opinionated workflow pack in that thread. It imposes structured planning and implementation practices. Some users consider that a quality upgrade; others report excessive token and time consumption.
- A substantial group prefers **base Codex plus a few custom skills** and sees large workflow packs as unnecessary context and ceremony.
- Other recurring community tools include **Context7** for current library documentation and **Caveman/RTK** for token-efficient command output, though these are not all equivalent to official Codex plugin bundles.

That means “popular” does not equal “universally recommended.” The community consensus is closest to: **install integrations for services you genuinely use; be skeptical of giant methodology packs.** See the [`r/codex` “Best Codex plugins?” discussion](https://www.reddit.com/r/codex/comments/1sz8id5/best_codex_plugins/). The [independent Codex Plugin Marketplace](https://www.codex-marketplace.com/) also features Figma, GitHub, Notion, Sentry, Linear, and Vercel, but it explicitly states that it is not affiliated with OpenAI, so I treated it as discovery evidence rather than authority.

## My practical recommendation for you

Start with **GitHub** because it extends repository work into issues, pull requests, CI, and security findings. Add **Sentry** only when this project has production errors in Sentry. Add **Linear** only when Linear is the task system you maintain. Add **Figma** when you regularly implement from Figma. Add **Vercel** when Vercel is the deployment target.

Do not install a broad bundle merely because it is highly visible. A plugin earns its place when you can name a repeated workflow that currently requires copying context between Codex and another tool. For a first test, install one plugin, start a new session, run one real end-to-end task, and compare the result with your current workflow.
