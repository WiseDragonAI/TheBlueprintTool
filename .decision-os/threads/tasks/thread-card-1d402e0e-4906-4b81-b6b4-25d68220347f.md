Your impression is partly correct.

A normal Decision OS restart does **not explicitly kill** the active headless `codex exec` PIDs. The restart endpoint exits the backend with `process.exit(0)`; there is no shutdown loop that signals the Codex children. The launcher forwards signals only to its direct backend child, not to the backend's Codex grandchildren.

However, the runs do **not safely survive** the restart:

1. Codex is spawned with `stdio: ['pipe', 'pipe', 'pipe']`, and those pipes are owned by the backend.
2. The child handle, status callbacks, and scheduler ownership exist only in backend memory.
3. When the backend exits, the old Codex process can remain alive at the OS level, but its output pipes lose their reader and Decision OS loses control of that run.
4. On startup, Decision OS resets persisted running thread jobs to pending and schedules them again. That can produce a duplicate: the old OS process may still exist while a replacement starts.
5. Pipeline recovery treats a running skill without a persisted terminal event as interrupted and marks it failed.

So the precise answer is: **restart leaves the PIDs running initially, but interrupts the Decision OS execution contract. Active headless runs must be treated as interrupted, not preserved.**

The safe solution is **not to reconnect the new HTTP server directly to the old Codex child**. That is impossible with the current anonymous stdio pipes: when their owning backend exits, the new backend cannot recover those file descriptors or the old Node `ChildProcess` handle.

We should introduce one separately supervised, catalog-wide **Codex runner service**:

1. The runner, not the HTTP server, owns the Codex queue, concurrency, process groups, stdin, stdout/stderr files, retries, cancellation, and terminal exit status.
2. The HTTP server communicates with it through a protected Unix-domain socket using immutable `runId` values.
3. `submit(runId, ...)` is idempotent. If that run is queued, running, or terminal, the runner returns the existing record and never starts another process.
4. Each run uses a durable prompt file and writes stdout/stderr directly to the existing artifacts. A small per-run wrapper atomically records PID, process start identity, status, exit code, and timestamps.
5. On restart, the new HTTP server first connects to the still-running runner, loads its snapshot, rehydrates runs by `runId`, and replays settlement events from a durable offset. It does not call `codex exec resume`.
6. The existing startup behavior that converts running queue entries back to pending must be removed. Cancellation must go through the runner instead of an in-memory child handle.
7. Pipeline advancement and queued voice continuation must consume persisted settlement event IDs exactly once, so replay cannot launch downstream work twice.

The restart endpoint should ask the runner to flush and confirm durable state. If the runner is unavailable, it returns `503` and keeps the HTTP server running. After confirmation, only the HTTP service restarts; the runner and Codex processes remain untouched.

One deployment constraint is unavoidable: **currently running legacy processes cannot be safely adopted**, because their pipes already belong to the current backend. Those runs must finish before the first deployment of the runner architecture. All runs started afterward can survive HTTP-server restarts without relaunch.

I recorded the detailed contracts, migration order, and seven restart-safety tests in the linked design card. No server restart or implementation change was performed.

Implemented the simpler policy you selected.

On server startup:

1. A persisted `running` thread or continuation claim is changed to `interrupted`, never back to `pending`.
2. Interrupted claims are excluded from scheduler selection, queue positions, queued-run reporting, and capacity launches.
3. The status API reports the recovered run as `failed`, `active: false`, with no queue position and the explicit reason: `Decision OS server restarted while this Codex process was running. The process was not relaunched.`
4. Existing terminal event evidence remains authoritative.
5. Work that was genuinely pending before restart remains pending and follows normal FIFO scheduling.
6. Pipeline recovery already marks a lost running skill failed without relaunching it.

The regression creates a persisted running claim, configures a fake Codex executable, starts a test server, and proves that the executable is never invoked. It also verifies the persisted `interrupted` state and the public failed status.
