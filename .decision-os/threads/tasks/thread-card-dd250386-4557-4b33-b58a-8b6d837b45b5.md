You are right to separate snapshot scope from invalidation scope.

1. **Snapshots are per project.** The endpoint requires `projectId`, the builder filters tasks to that project, the cache is keyed by `projectId`, the replica store persists `peers[nodeId].projects[projectId]`, and the SHA-256 revision covers one project snapshot.

2. **The remaining defect is the change notification.** The owner knows the changed `projectId`, but `publishContentChange()` sends a `content-change` frame without it. The receiver therefore gets only `nodeId` and calls `enqueuePeerProjects(nodeId)`, which queues every project owned by that node.

3. **Impact:** payloads remain project-specific, but one project edit triggers hash requests and temporary `synchronizing` state for all projects on the peer. HTTP `304` avoids retransmitting unchanged snapshots, but it does not remove the unnecessary fan-out. My previous correction fixed the repeated 15-second global requeue, serial blocking, stale presence ETag, and backlog projection; it did not fix this missing `projectId` propagation.

4. **The running server has not loaded that correction.** Its process started at `2026-07-18 23:39:14 +07`; merge `97525fbf` was created at `23:51:57 +07`.

5. **Required structural correction:** include `projectId` in every `content-change` relay frame, propagate it through `onRemoteContentChange(nodeId, projectId)`, enqueue only that exact replica, and publish the same scoped identity to Control Room clients. Add a two-project regression proving that changing project B neither queues project A nor changes project A's replica status.
