## A. Repository Intent

1. **Decision OS treats task state as authoritative, project-scoped state.** The Control Room is a compact projection of that state, not an independently editable ledger. A mutation must converge the task-state store, the Control Room projection, and the client view without making content replication part of the state acknowledgement path.
2. **Control Room refresh is revision-driven.** The canonical projection contract requires an atomic project-slice replacement followed by an aggregate revision event carrying the affected project identities. Clients retain the current screen while revalidating the compact projection.
3. **Master-task deletion is intentionally non-cascading.** The master card, its relationships, thread reference, and thread notes are removed; linked subtask cards remain. The successful interaction closes the detail surface and returns to the Control Room. Rejection must preserve or restore authoritative state.

---

## B. Current Iteration Intent

1. **Reported regression.** Deleting a master task leaves the card visible until the request completes and can leave it visible until a manual task refresh. The intended interaction is immediate optimistic removal followed by silent background convergence.
2. **Requested analysis scope.** Trace the first incorrect transition across frontend state, task-state persistence, Control Room cache invalidation, SSE refresh, and missed-event recovery; then classify all 11 frontend test failures rather than treating the failure count as one symptom.
3. **Canonical acceptance moments.** The complete deletion contract has three observable moments: immediate optimistic disappearance, persistence across a fresh authoritative reload, and server rejection restoring confirmed state with an error. The existing deletion task describes the final success state, while the later Control Room cutover cards make the optimistic and reconciliation requirements explicit.

## C. Findings

1. **Critical Gap — the frontend explicitly waits instead of deleting optimistically.** In `frontend/src/app/responsive/application.js:2352`, the confirm handler disables the button and changes its label to `Deleting task…`, then awaits `ledgerMutation()` before closing the modal and navigating. `ledgerMutation()` at `frontend/src/app/responsive/application.js:593` applies `removedCardIds` only after the HTTP response and only to `state.ledger.cards`. It does not remove the task from `state.controlRoom.queue`, `exec`, `backlog`, `done`, or `allTasks`. Navigation then synchronously paints the retained, stale Control Room state. This is the first incorrect user-visible transition.
2. **Critical Gap — the server invalidates the Control Room before the authoritative mutation commits.** `persistLedgerMutationAndRespond()` at `backend/src/business/server/helper/create-http-server.ts:917` calls projection invalidation, suppresses the next ledger watcher event, and only then awaits the task-state mutation. `invalidate()` in `backend/src/business/server/helper/control-room-projection-store.ts:481` schedules a microtask rebuild. That rebuild can read the old task projection while the journal write is pending and then clear the dirty flag. There is no second post-commit invalidation. The server can therefore cache and serve the pre-delete projection after accepting the deletion.
3. **Critical Gap — no reliable post-swap event exists for this local mutation.** The task mutation path does not call the ledger publication path, and the projection store has no callback that emits an aggregate revision after a successful slice swap. `/api/control-room-events` registers clients, but deletion produces no event tied to the new Control Room revision. This violates the contracts in `.decision-os/cards/tasks/card-21104e8d-*.md` and `.decision-os/cards/tasks/card-dd596665-*.md`: rebuild the owning project slice, swap it atomically, advance the aggregate revision, and only then notify clients.
4. **Drift — the advertised 30-second recovery is request-driven, not background anti-entropy.** `controlRoomProjectionStore.get()` invokes reconciliation only when a Control Room GET happens after the interval. There is no independent timer. Worse, the dependency fingerprint includes legacy `tasks.json` and content files but not the task-state-v2 root hash/current entities. A v2 deletion can therefore remain invisible to reconciliation and warm-start validation. `force: true` on the frontend merely omits `If-None-Match`; it does not force a server rebuild.
5. **Drift — client refresh is route-bound and cannot maintain background convergence.** `subscribeControlRoomEvents()` at `frontend/src/app/responsive/application.js:1725` ignores refresh work unless the current route is `/` or `/done`. It does not reconcile on EventSource `open` after reconnect, on visibility recovery, or on network recovery, and it does not debounce using the canonical aggregate revision. While a task detail is open, the retained Control Room state is allowed to age. A disconnect can strand it indefinitely.
6. **Omission — task-state-v2 deletion leaves thread-note entities behind.** `backend/src/business/task-state/helper/task-mutation-command.ts:179` tombstones the card and relationships and removes `threadFiles`, but does not tombstone every `thread-note` belonging to `thread-${cardId}`. The legacy mutation helper does remove those notes. This creates orphan current-state/replicated notes after a v2 delete.
7. **Lifecycle Gap — deletion has no queued/running execution guard.** The backend guards a separate `todo -> backlog` transition but not master deletion. Removing a master and its relationships while execution is live can hide a still-running process. This is not part of the original deletion acceptance text, but it is an integrity decision that must be encoded rather than left accidental.
8. **Test Gap — existing deletion coverage cannot observe the regression.** `frontend/test-responsive/mobile-control-room.test.mjs:552` is source-pattern coverage: it checks for a `delete-card` action and eventual Control Room navigation. It does not hold the request open, observe immediate removal, reload authoritative state, or exercise rollback. `backend/test/server/control-room-projection.integration.test.ts` does not perform a delete mutation before reading the projection.
9. **Ten of the 11 frontend failures are one deterministic Node web-storage capability mismatch.** The active runtime is Node `v25.9.0`. It exposes `globalThis.localStorage` as an object while `localStorage.setItem` is undefined and warns that `--localstorage-file` lacks a valid path. `persistThreadViewportState()` checks only whether `localStorage` exists and then calls `setItem`. Consequently, 10 cases in `frontend/test/runtime/thread-selection-runtime.integration.test.ts` fail with `TypeError: localStorage.setItem is not a function`. Evidence: the file produced **15 passed / 10 failed** normally and **25 passed / 0 failed** with `NODE_OPTIONS=--no-webstorage`. The repository has no `.nvmrc`, `.node-version`, or package `engines` constraint, so toolchain drift is currently invisible.
10. **The eleventh frontend failure is an independent load-sensitive polling test.** `frontend/test/unit/thread/effect/render-thread-panel.test.ts:835` waits at most one second for a seeded run-log poll. The poll starts through `setTimeout(0)` and the full suite runs files concurrently. It timed out in the full run but passed in isolation in approximately 273 ms. With web storage disabled, the full suite improved from **509/520** to **519/520**, leaving only this timeout. This is test nondeterminism, not evidence of an eleventh product regression.
11. **The failures are causally separate.** The deletion defect is an application state-transition and projection-publication problem. The 10 storage failures are runtime capability detection/toolchain drift. The final failure is scheduler-sensitive test design. Fixing any one category will not fix the other two.

## D. Remediation Paths

1. **Implement one frontend optimistic-deletion path keyed by full task identity.** Before starting the request, snapshot the task and relevant ledger/Control Room state, add an optimistic deletion tombstone, remove the master from all five Control Room collections and `state.ledger.cards`, close the modal, and navigate/render synchronously. Every subsequent `loadControlRoom()` result must be filtered through pending tombstones so a stale response cannot resurrect the row. On authoritative omission, clear the tombstone. On rejection, clear it, force an authoritative read, restore server-confirmed state, and surface the error.
2. **Make projection publication a post-commit server boundary.** Persist task state first. After success, synchronously rebuild and atomically swap the affected project slice, obtain the new aggregate revision, then emit one Control Room change event containing that revision and the affected project IDs. Send the mutation acknowledgement only after the replacement projection is available. Do not rely on a generic ledger watcher echo for client-originated task-state mutations.
3. **Complete task-state-v2 anti-entropy.** Include the task-state store `rootHash()` in projection fingerprints, ETags, persisted cache validation, and reconciliation. Run reconciliation from a real server-owned 30-second timer. If the root changes, rebuild/swap first and publish the repaired aggregate revision afterward.
4. **Keep Control Room state fresh independently of the visible route.** Consume aggregate revision events and refresh `state.controlRoom` even while a detail route is visible; only DOM rendering remains route-dependent. On EventSource `open`, perform a conditional reconciliation to close the disconnect window. Deduplicate refreshes by aggregate revision.
5. **Finish v2 delete semantics.** Tombstone all `thread-note` entities for the deleted card's thread and add a focused current-state projection test. Define and enforce the lifecycle rule for deleting queued/running masters; the safe default is rejection with a clear recovery message until cancellation has completed.
6. **Replace source-pattern deletion coverage with behavioral regressions.** Hold the delete response open and assert immediate disappearance/navigation; then cover successful fresh reload, stale-response non-resurrection, rejection rollback, post-commit projection/ETag change, SSE revision ordering, missed-event timer repair, and v2 card/relationship/thread/note tombstones.
7. **Harden storage access and pin the test runtime.** Centralize web-storage access behind a capability-safe adapter that verifies `getItem`/`setItem` methods and catches access exceptions. Give tests an explicit storage mock or explicitly disabled web storage. Declare and enforce the supported Node version so Node 25 behavior cannot silently alter the suite.
8. **Make the run-log polling test deterministic.** Inject or expose the polling scheduler/clock and await an explicit seeded signal. Avoid treating a one-second wall-clock deadline under parallel suite load as proof of behavior. Raising the timeout alone would reduce symptoms without removing the race.
9. **Implementation order.** First land optimistic tombstones and rejection reconciliation; second establish post-commit projection swap plus revision event; third add v2 root-hash anti-entropy and route-independent client recovery; fourth close thread-note/lifecycle semantics; fifth add the behavioral suite and toolchain/storage hardening. This order restores the user-visible contract early while preserving one authoritative convergence design.

---

## E. Operator Decision Summary

1. **The deletion regression is confirmed and has two primary causes:** the UI awaits the mutation before changing state, and the server can rebuild the Control Room cache before the task-state commit with no reliable post-swap event.
2. **The Control Room is not currently self-healing in the background.** Its 30-second reconciliation is lazy, misses task-state-v2 roots, and the client discards refresh work outside Control Room routes.
3. **The 11 frontend failures are fully classified:** 10 are the same Node 25/localStorage capability mismatch; one is a one-second polling-test flake. The controlled run reached 519/520, and the remaining test passes in isolation.
4. **No implementation change was made during this analysis.** The required correction is the single ordered path in Section D, with behavioral tests proving the three deletion moments and projection revision ordering.
